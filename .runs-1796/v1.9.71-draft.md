# Instant Swift Data 1.9.71

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (`<MERGE>` plus this release record). It carries 1.9.70.

## Before you upgrade

No public API change, no storage change. Two package-level configuration values are new
(`liveQueryAcknowledgementStallMilliseconds`, 5,000, and `liveQueryAcknowledgementLimitMilliseconds`, 30,000).

## Release focus

**A device following another one applies each query's newest result next, its one-shot reads survive a busy applier
and a dying socket, and it measures how far behind it is** (#1796; merge `<MERGE>`).

On 2026-11-04 a tablet followed a live recording on a phone. It held 8,240-11,035 of its own pending writes (left from
its own overnight recording) and drained 25-35 a minute; with that queue each server frame cost about 1.5 s to apply.
In one minute it received 29 `refresh-ok` of the recording list (144 KB each) and 31 `transact-ok` and ran 22 server
applies: 75% of a core in Instant sync, 101% in all, heat serious, 2.5 W. The user read the recording on the tablet about
six minutes behind the phone, whose own outbox held 0-3 pending writes. After a resume, every one-shot read failed as
"Network or live transport failed", the text the playback screen showed.

- **A waiting refresh loses what a newer one restates** (red `bd5d9017`, green `3f66c955`). Every server frame waits in one
  buffer for one applier, in arrival order, and a `refresh-ok` restates each of its queries' whole results, so a
  waiting `refresh-ok` that a newer one restates was applied only to be replaced, and each acknowledgement and one-shot
  answer behind it waited for that apply too. Now, when a `refresh-ok` arrives, every older waiting one loses the
  results it restates, and one left with none leaves the buffer. A frame that carries `attrs`, or reflects a later
  transaction than the newer one, keeps everything. The server does the same with refreshes it has not sent
  (`session.clj`, `combine [:refresh :refresh]`), and `Reactor.js` replaces a query's stored result whole on each
  `refresh-ok`, so the store ends where applying every frame leads.
- **A one-shot read waits while the connection works** (`3f66c955`). It waits for its answer while the connection receives
  or applies frames, up to upstream's 30 s (`QUERY_ONCE_TIMEOUT`), and fails after 5 s in which neither happened. It
  failed at a fixed 5 s, behind the tablet's applies, while the socket was open.
- **A one-shot read whose `add-query` met a dead socket waits for the reconnect** (red `25923d45`, green `1fd79eb8`). After 229
  s suspended, the tablet's socket was dead (POSIX 53) for 12 s while its connection still read as open; a read's
  `add-query` failed on it, and the read failed in 0 ms and dropped its registration. Now the registration stays and
  the next session's init sends it, as it does an observer's, and as upstream sends a queryOnce's `add-query` from
  `_flushPendingMessages` on the next `init-ok`.
- **The follower measures its lag** (red `882448d2`, green `75915233`). `live.receive-summary`, once a minute, adds how old the
  newest server writes were when their frames finished applying (`factLagMedianMilliseconds`,
  `factLagP95Milliseconds`, `factLagMaxMilliseconds`, `factLagFrames`): for each `refresh-ok` carrying a fact newer than
  any applied before, this device's clock minus the newest fact's server time (the fourth element of its join-row
  triples). An answer to `add-query` only moves the mark. It includes the difference between the device's clock and
  the server's. The line also reports the frames' waits from the reader to the applier, the deepest buffer, the
  applier's busy share and longest apply, and the frames and results newer frames replaced; it is a notice when a frame
  waited 1 s or more or the newest writes arrived 10 s or more after the server stored them.

- **A writer and a follower, end to end** (guard `076ed107`). `InstantWriterFollowerLatencyTests` runs a writer runtime and
  a follower runtime over scripted sockets, with the test as the server between them, and replays the tablet's minute
  (29 list refreshes and 31 acknowledgements of its own writes a minute, about 1.5 s an apply) for two minutes on the
  test's clock. Each line's lag, from the writer's write to the end of the apply that first shows it on the follower,
  stays at most 20 s, and the last line's at most 8 s; on the sources before this release it fails (see Checks).

- **A registration that holds the gate says which query it is** (red `fac02655`, green `d7502832`). A standard query's and an
  infinite query page's registration name the gate's phase `reload <namespace>` and `answer <namespace>`, so a stall
  or wait report reads "observe standard live query (phase: answer lineLabels)". At the tablet's launch one
  registration held the operation gate 4,583 ms with its connect and 7 callers behind it, and a page's held it 2,852 ms,
  both unnamed.

## Not run

The release gate, `validation/run-performance-gate.sh live`, did not run (the maintainer's authorization quoted above):
its Swift→TypeScript and TypeScript→Swift wire lanes, memory and throughput were not measured. This release changes
which buffered frames the applier applies, how long a one-shot read waits and when it resends, and what the receive
summary logs, not the wire or the stored format. No two-device run against Instant's server was made before the tag;
the follower's lag is measured on the installed apps after it.

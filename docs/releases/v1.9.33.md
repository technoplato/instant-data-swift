Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The last
code commit is `7699425a`. It carries 1.9.32 (#1012) and 1.9.31 (#654).

## Release focus

**A stored file looked up by id costs one file's work, whatever the account has uploaded** (#654, #932; red `adfaa4bb`,
green `47d980a8`).

`downloadStoredFile(id:name:to:)` and `storedFileContents(id:name:)`, given no name for a file the device holds no record
of, found the file in a one-shot query of every `$files` row the account can see. That list grows with everything the
account uploads (on one phone 9,455 files on 2026-10-24, 892 three weeks earlier), and its answer was about 27 MB. The
answer outlasted the one-shot query's 5 s, so the download failed and was tried again on the app's next pass, and the
answer landed anyway: a server apply wrote about 75,000 facts, their ownership rows and the result's JSON while holding
the operation gate (2.3-5.8 s on the phone), and the next session prune dropped the closed result again (3.8-6.0 s).
While a recording's media downloaded this ran about once a minute on an iPhone and every 10-20 s on a Mac, and every
write and read in the app waited behind it. The lookup now asks for that file alone: a `$files` query on its id, which
the server answers with one row.

**The answer of a one-shot query that ended before it landed is not applied** (#654, #932; red `146334dd`, green
`f8f39ca0`, narrowed in `7699425a`).

A one-shot query that waited past its 5 s, or was cancelled, removes its query; its answer could still land afterwards,
and the runtime applied it for no query, then the prune dropped it. Upstream `Reactor.js` keeps an `add-query-ok`'s
result only for a query `querySubs` still holds. The runtime now drops the answer of a one-shot query that ended and is
not registered again (the newest 256 such queries), with an info event, `query.answer-dropped`. An answer for a query
the runtime never registered is applied as before.

## Measured

On a copy of an iPhone's own store (9,455 files, 75,640 file facts; 45,369 resident facts at launch), driven by a
recording's shape for each simulated minute: 15 transcript lines written 5 times each, every write answered by the
server's refresh of the live transcript page (256 lines a page, earlier pages kept open); one picture another device
added, looked up by id with no name, while the account gains 2 files a minute; and one session prune. The server is
scripted in-process and the copy keeps no sign-in. MacBook Pro (M1 Max), debug build, on a machine other builds kept
busy. Before is main at 1.9.32 (minutes 1-3 of the run); after is `7699425a` at minutes 5, 60 and 120 of a 120-minute
run.

| Each minute | Before | After: minute 5 / 60 / 120 |
| --- | --- | --- |
| The lookup | fails at 5 s, 11.7 s | 44 / 35 / 44 ms |
| Its server apply's gate hold | 3,042-6,033 ms: 9,457 changed entities, 25.2 MB of result JSON | 0 / 1 / 1 ms: 1 entity, 2.8 KB |
| The prune's gate hold | 6.6-6.8 s, 75,656 facts dropped | 1 / 2 / 2 ms, 8 facts |
| Longest server-apply gate hold | 3.0-6.0 s | 70 / 32 / 43 ms |
| Longest wait of a read behind the gate | 6.6-6.8 s | 68 / 199 / 97 ms |
| Bytes written | 699-858 MB | 7.3 / 9.5 / 12.7 MB |
| Peak footprint | 598 MB | 282 MB for the whole run |

Process CPU per minute was 15.0-15.6 s before. After, it follows the lines in the live transcript page, from about
2.8 s on a new page to 13-20 s when the page nears its 256 lines, page after page: each write's refresh restates its
whole page, as Instant's server sends it. That cost is bounded by the page, and this release does not change it.

## What stays the same

No schema, migration or public API change. A lookup returns the same record (its stored name, content type and URL),
and a file storage does not hold fails as it did ("No remote file exists for id"). `storedFiles()` and
`observeStoredFiles()` still return the whole list they ask for. Offline, a lookup reads the device's cache as before.

A device that ran 1.9.32 may keep the whole list's last result among its unloaded results, about 25 MB; nothing reads it
unless `storedFiles()` asks for the list again, and the pruning policy collects it with the rest.

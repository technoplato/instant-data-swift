# Instant Swift Data 1.9.34

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The last
code commit is `607d64bf`. It carries 1.9.33 (#654, #932).

## Release focus

**A stored file deleted by id is found by its own record or by its id, not in every file the account holds** (#654,
#932; red `78e0c30d`, green `607d64bf`).

The device lab watched build 123, the first build with 1.9.33, and found one whole-`$files` query left in its first
minutes: `deleteStoredFile(id:)` found its file through `storedFiles()`, every file the account can see. The consuming
app deletes a chunk it has just uploaded when the chunk's row cannot be written; that list (about 9,500 files) timed out
at 5 s, so the delete failed and the uploaded chunk also stayed in storage. A delete now uses the device's own record of
the file (an upload always leaves one) and asks no query; a file the device holds no record of is found by a `$files`
query on its id, one row. Offline, a file the device has no record of reads as missing, as the list's local fallback
did.

`storedFiles()` and `observeStoredFiles()` still return the whole list: that is what they are for, and nothing should call
them on a schedule. A list of the device's own records is `localStoredFiles()`, or the local reader's `storedFiles()`.

## Measured: 1.9.33 and 1.9.34 over a two-hour recording

The 1.9.33 changes (the lookup by id and the dropped late answer) measured over a recording's shape for each minute: 15
transcript lines written 5 times each, every write answered by the server's refresh of the live transcript page (256
lines a page, earlier pages kept open); one picture another device added, looked up by id with no name, while the account
gains 2 files a minute; one session prune. Before is 1.9.32, after is 1.9.33.

On an idle Mac mini (M4), release build, a made-up account of 9,455 files:

| Minute | 5 | 60 | 120 |
| --- | --- | --- | --- |
| The lookup's server apply, gate hold: before | 523 ms | 816 ms | 959 ms |
| after | 0 ms | 0 ms | 0 ms |
| The prune, gate hold: before | 1,509 ms | 1,846 ms | 2,043 ms |
| after | 0 ms | 5 ms | 0 ms |
| Longest wait of a read behind the gate: before | 1.5 s | 1.8 s | 2.0 s |
| after | 4 ms | 10 ms | 17 ms |
| Bytes written in the minute: before | 465 MB | 441 MB | 512 MB |
| after | 8.3 MB | 9.9 MB | 11.8 MB |

Peak footprint: 559 MB before, 61-107 MB after. Before, the costs grew with the recording (the store grew under the same
list); after, the gate holds stay flat.

On a copy of an iPhone's own store (75,640 file facts; 45,369 resident facts at launch), MacBook Pro (M1 Max), debug
build, on a machine other builds kept busy, minutes 5 / 60 / 120: before, the lookup failed at its 5 s every minute, its
late answer held the gate 2.4 / 2.6 / 7.1 s, the prune 6.4 / 5.7 / 12.6 s, a read waited 6.3 / 5.6 / 12.6 s, and about
690-700 MB were written a minute (peak 765 MB); after, the lookup's apply held 0 / 1 / 1 ms, the prune 1 / 2 / 2 ms, the
longest server apply 70 / 32 / 43 ms, and 7.3 / 9.5 / 12.7 MB were written a minute (peak 282 MB).

Process CPU per minute after the change still grows with the recording: 0.63 / 1.54 / 2.36 s on the mini. A transcript
line's first write re-materializes its page from every line of the recording (#1056); that cost is not in the prune or
the commit, and this release does not change it.

## What stays the same

No schema, migration or public API change. A delete removes the same file from storage, by its stored name, and the same
record; the record it returns is the device's own when it has one. A file neither the device nor storage holds fails as it
did ("No local or remote file exists for id").

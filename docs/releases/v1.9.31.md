they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `f4dfb8ee`.

## Release focus

The live-query prune costs in proportion to what it drops, not to the store (#654).

Every 64 live results the runtime prunes the stored results no open query watches, and the facts only they held. Each
prune batch copied the whole hot store (`InstantStore.snapshot()`), built a dictionary of every fact to find the few
it drops, diffed the whole store into SQLite, then replaced the hot store and indexed every fact again
(`replaceSnapshot`). A consuming app's iPhone, on its build of 1.9.26, held the operation gate 1,385 ms and 4,168 ms
in this prune in its first minutes (a local write waited 1,740 ms behind it), and its energy ledger named the prune the
top cost.

A batch now has four steps, under the operation gate as before (red `add72672`, green `f4dfb8ee`):

1. **SQLite chooses the batch from the results' own rows** (`liveQueryResultPruneBatch`): the policy's selection is
   unchanged (closed queries' results unloaded, #1006; then age, entry and triple limits, oldest first, about 5,000
   triples per batch), and it reads the facts the chosen results hold. It reads no other fact.
2. **The hot store hands over its facts of only the entities those results name** (`facts(of:)`).
3. **SQLite drops the results and each entity no remaining result holds, in one transaction**
   (`applyLiveQueryResultPruneBatch`). The decisions are the ones the whole-store prune made, from the same facts:
   ownership per released fact (the ownership index), and the whole-entity rule, so an entity with any fact no result
   released stays whole (#259). A dropped entity's rows go by its id, as the whole-store diff deleted them, deferred
   payloads included. The memory cache moves past the batch instead of adopting a rebuilt state; a batch chosen at
   other revisions is chosen again.
4. **The hot store retracts the dropped facts in place** (`retractFactsReleasedByPrune`).

The bootstrap prune runs the same batch, unbounded, once. Callers without a hot store keep
`SQLitePersistenceStore.pruneLiveQueryResults`, which returns the whole state after the prune; it is now built from the
same selection and decisions, and its unused `currentStoreSnapshot` parameter is gone.

## What stays the same

The same results are kept, unloaded and deleted, and the same facts leave memory and SQLite: the test below checks the
sets, and checks that the pruned store answers queries exactly as a store built from the same facts does. Batches
release the operation gate between them, and a fact a batch released but kept (its entity still had a fact a later
batch releases) is carried into that batch. The prune still refreshes no observer: like `replaceSnapshot`, the in-place
retraction marks every observer's result unverified, so the next change refreshes any observer that could show a
dropped entity. Sync is untouched: nothing in the outbox, delivery or the live session changed.

By reading the old code (not measured): when the persistence memory cache was stale, the session prune pruned against
SQLite's scoped view of the store and then replaced the hot store with that view, which could drop facts the hot store
held and the view did not. That path is gone with the replacement.

## Checks

- **Red, then green.** `InstantPruneCostTests/aPruneOnAFortyThousandFactStoreCopiesNothingTheSizeOfTheStore`: an open
  query's result holds 40,002 facts and 24 closed queries' results hold 10,803 more. On 1.9.30 the prune kept and
  dropped the right sets but made 6 full copies of the store and replaced and re-indexed it 3 times; now 0 and 0, with
  the same sets.
- **Measured in the test** (`aPruneHoldsTheGateForMillisecondsWhateverTheStoresSize`, `.measurement`, debug build, a
  Mac mini, alone): the longest batch's hold of the operation gate 167 ms at 4,002 kept facts and 515 ms at 40,002 on
  1.9.30; 124-132 ms and 126-133 ms now. It fails when the larger store's hold is twice the smaller's.
- **The whole suite** (a Mac mini, `scripts/known-failing-tests.sh`, idle, on `fe1f2821`, the same change before its
  rebase onto `0ae10a95`, which brought only #1012's progressive media and documents): 1,405 tests, 1 failing
  (`binaryCodecRemovesBase64AndJSONCPU`, on `Tests/known-failing.txt`, #1028); compare: no new failures. The prune,
  stored-result reload, compact-ownership, residency and actor-hop suites, and the prune tests of `InstantStoreTests`,
  `InstantLiveTransportTests` and `InstantOutboxHydrationTests`, pass on the rebased tree.
- **Measured in a release build** (a Mac mini M4, `-c release -enable-testing`, the prune alone, medians of 3): the
  same 24 closed results (10,803 facts, 3 batches) dropped beside 10,002, 40,002 and 100,002 kept facts.

## Not run

- `validation/run-performance-gate.sh` and the Swift→TypeScript and TypeScript→Swift boundary checks: this release
  changes no wire format, schema or delivery path. The prune's memory and throughput are the measurements above; the
  memory figure is malloc's peak above where the prune started.
- `scripts/validate-release-version.sh 1.9.31` failed on this document's wording before this section was added, as it
  does for 1.9.28-1.9.30; the tag was already pushed.
- On a device: the next build of the consuming app carries this release, and the device performance lab (#1005)
  measures idle and recording CPU and the gate holds behind the prune there.

## Not changed here

- A batch still decodes each removed result's stored JSON to learn the facts it held, and the hot store's in-place
  retraction costs about 8 µs a fact in a release build (40 ms for 4,950 facts on the Mac mini): both grow with what a
  batch drops, and are most of a batch now.
- After a prune that drops facts, observers stay unverified until they are materialized again, so their next refresh
  cannot skip a change it would otherwise skip, as before.
- #654's other items (the hot store's bytes per fact, re-hydration of unchanged rows, rows held twice, the frame
  pipeline) are separate.

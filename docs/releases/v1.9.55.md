## Before you upgrade

A one-time conversion at the first open, no public API change. The outbox's table changes shape: `instant_outbox`
becomes a narrow WITHOUT ROWID row of a write's delivery state, and the write's body (`json`, `lifecycle_json` and the
quarantine copies) moves to a new table, `instant_outbox_bodies`, keyed by the mutation id and deleted with its row.
A stored body no longer carries the write's status, server transaction id or confirmation source, which the row's
columns hold; every reader in the library decodes the body with them. The conversion runs once, decided by the table's
own columns (a restore that rebuilds the old shape converts again), as SQLite's twelve-step rebuild in one transaction,
checked against the old table before it goes. An app that reads the library's tables with its own SQL must read the
body through `instant_outbox_bodies` (or follow the layout it finds, as the consuming app's recovery export now does).

**One way only.** A store this version has opened does not open with 1.9.54 or older: their launch reads
`instant_outbox.json`, which the converted table no longer has. A rollback of an app past this release needs its store
reset (the consuming app's Reset Local Cache moves the store aside whole and, from its build with this version, exports
the unsent writes of either layout), or the bodies folded back into their rows by hand.

## Release focus

**A claim and an acknowledgement write the outbox row alone** (#1435). The consuming app's phone wrote 108 MB an hour
of claims and 154 MB an hour of acknowledgements while recording (its energy ledger, 2026-10-30 12:00-17:14). A claim
sets a write's claim columns and an acknowledgement its delivery columns; neither changes what the write is. But the
body shared their row, and each step changed the record's size (a NULL claim token becoming text, a token cleared), so
SQLite rewrote the whole cell with every overflow page of the body and freed the old pages; the acknowledgement also
re-encoded the body, because it carried the status, server transaction id and confirmation source as well as the
columns. Now the body is written at the save and again only when the write itself changes (a rebase's new rollback, a
failure, a quarantine), and a claim or an acknowledgement updates the narrow row and the indexes whose columns it sets.

Measured on a Mac mini (debug, the StorageIO shim's log frames, `StorageIOWriteCycle`: Scribe's line writes answered by
a scripted server), before and after, frames per write:

| Step | Before | After |
| --- | --- | --- |
| Claim | 4.17 (row, delivery index, 1.33 freed pages, page 1) | 2.00 (row, delivery index) |
| Acknowledgement | 6.17 (row, delivery, watermark, revision, 1.33 freed, page 1) | 4.00 (row, delivery, watermark, revision) |
| Save | 15.33 | 16.17 |
| Echo (the server's answer) | 18.50 | 19.17 |

The save and the echo still write nine outbox b-trees each (the body's table takes the place of the old table's text
key index) and now write page 1 for the body's overflow pages every time; their fact pages moved by noise. #1436 takes
the save's and the echo's b-trees next.

## The conversion on a copy of a phone's store

The library's own conversion on a scratch copy of the consuming app's phone store (laptop only, counts only) follows
here. A rehearsal of the same SQL on such a copy: 730 rows (2 waiting, 728 refused), 14 MB of bodies, 1.06 s on a
laptop under load, no foreign-key violation; the plans of the hot reads afterward are primary-key and index searches.

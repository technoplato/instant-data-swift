## Before you upgrade

One public API addition, source compatible: `InstantProgressiveMediaWriter.init(stream:ownerUserID:spool:storage:)`
gains `continuing:` (an `InstantProgressiveMediaStreamRow?`, default `nil`). No storage change: a spool record written
by this release is the same JSON as before.

## Release focus

**A delivered progressive media stream that is continued goes on where its stored row ends** (#632; red `af95eb36`,
green `418ff841`).

- A stream delivered to its end leaves the spool. Continuing it later (a recording resumed after it stopped) found no
  record, so the writer started over at index 0: it encoded and stored every segment and the initialization segment
  again, and an app's rules may refuse each of those rows with the transaction around it, since a stored stream keeps
  its `createdAtMs` and a stored segment every field: one rejection a re-sent segment, and stored files that may no
  longer match the rows that describe them.
- Now the writer takes the stream's stored row. With no spool record and a row of this stream that has segments, the
  spool begins from the row (no initialization file): the next segment takes index `segmentCount` at
  `durationSeconds`, the initialization segment counts as stored, the row keeps its `createdAtMs`, stamps go on from
  `updatedAtMs`, and the stream takes the stored format. The spool's own record still wins; a row with no segments or
  of another stream starts the stream as before.

```swift
let stored = try await reader.refresh().stream
let writer = try InstantProgressiveMediaWriter(
  stream: stream, ownerUserID: user.id, spool: spool, storage: .live(client), continuing: stored
)
```

# Instant Swift Data 1.9.72

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (d7dcf707 plus its ledger and this record): every source
change on `main` since `v1.9.71` is now marked ready for a build. It carries 1.9.71 (#1796) and 1.9.70.

## Before you upgrade

No public API change. One storage change: `instant_live_query_results` gains a nullable `unloaded_at_ms` column (one
`ALTER TABLE ... ADD COLUMN`, added once after the ownership compaction). A store an older build wrote keeps its
unloaded copies in `instant_unloaded_live_query_results`; a reopening still reloads them, and no new copy is written.
An older build opening this store reads past the column and holds every stored result as loaded, rows and facts
intact, so a rollback loses nothing; its first prune copies closed results again as that build did.
`InstantRuntimeConfiguration` gains an internal `residencySweepWriteInterval` (64; `Int.max` turns the sweep off).

## Release focus

**A closed query's result is unloaded where it is** (#1500; red `f87d77b6`, greens `623a8a8b`, `93e79459` and `bbf40f04`;
merge `cfd74320`).

- Upstream's `PersistedObject.unloadKey` unloads a closed query's stored copy without deleting it. Here the session
  prune copied each closed result whole, as JSON, into `instant_unloaded_live_query_results`, deleted its ownership
  rows and its facts, and wrote them all back when the query opened again. On a phone's store (2026-10-30) the copies
  were 207 MB of a 598 MB file, 65.5% of their facts duplicates of another copy's. On 2026-11-04 the copy, release and
  reload writers wrote 149.2 MB an hour of the device's 2,700 (the phone's energy ledger, 188 minutes of the consuming
  app's builds 247-249) and 413.8 MB an hour of 5,392 on build 253 (33.5 minutes of recording).
- Now the prune marks the result's row (`unloaded_at_ms`) and writes nothing else: its row, its ownership rows and its
  facts stay on disk. Memory releases its entities under the batch's gates by the residency sweep's rule (below); the
  rest stay sweep candidates. A reopening reads the marked row as a stored result is read, clears the mark, writes no
  ownership rows and loads the entities memory lacks whole from `instant_triples`. A server answer's save clears the
  mark too.
- A marked result owns nothing for retractions, the prune's release, the refusal resolution (#441, #445) or the
  launch's residency, as its copy owned nothing. The policy (1 year, 1,000 results, 1,000,000 facts) counts marked
  results and collects them oldest first; the whole-entity rule reads from SQLite the entities memory does not hold.

**A write to an entity kept on disk reads it first** (#1165; red `53e30f9f`, green `68045937`, test `f46d1e0e`).

- After a relaunch memory holds the facts the stored results own and the outbox's effects; the rest stay on disk
  (#1006). A write prepared against memory alone handled such an entity as a new one: its save read every row of the
  entity and deleted each one the write did not restate (a one-attribute write to a line erased its id and recording
  from this device), a strict update of it threw, a strict create of it passed, and a server result that selected some
  of its fields took the same whole-entity save.
- Now a local write (and the retry and refused-write rebases) reads, in the persistence turn that already read its
  deferred values, every fact SQLite keeps of each entity it names that memory holds no fact of; the facts join the
  prepared indexes and stay, so memory never holds part of an entity. A server apply does the same for an entity absent
  from both its own prepared store and memory. With deferred values configured a write takes no new turn; without
  them a write takes one more store turn, and one that creates an entity one more persistence turn (the local
  benchmark's exact actor-hop counts moved by that).

**A long session's memory is a relaunch's** (#1145; red `213a7563`, greens `ef358515` and `221512b9`).

- On a phone recording (2026-11-04, build 248) the store's resident facts grew 44,127 -> 64,874 and its heap in use
  135.8 -> 187.3 MB in 95 minutes; the next relaunch started again near 45,000. Nothing released a row this device
  wrote once no open result showed it.
- Every 64 local writes or result-carrying frames a background sweep releases from memory, never from disk, the
  entities no stored result owns, no outbox row touches and no observer shows: one read without a gate, then at most
  500 entities a hold of the server-apply and operation gates at background priority; never while a prune releases a
  result; stopped before a suspension and by a close. A later write reads a released row first (above); a local read
  finds it on disk (#1006).

**A closed live query's acknowledgement entries go** (#541; red `31d0e156`, green `820d412a`).

- Each live query the server answered left its key in the acknowledgement state after its last registration ended; a
  phone's agent replies restarted about 380 times in 16 minutes (2026-10-04), each with a new key, and the memory audit
  measured 3,151 B kept per closed lease (E06). Now the key goes when the last registration ends (an observation's, an
  infinite chunk's or a one-shot read's) unless a one-shot read still waits on it; revisions come from one counter, so
  a key forgotten and answered again still moves past any revision read before.

**A file record is read where it is kept, and only the ones asked for** (#1104, #1105; reds `277a9203` and `dfe16998`,
greens `69ceae52` and `79a90b8b`; merge `f504ed51`).

- `evictStoredFiles(ids:)` reads the records of its ids alone (at most 500 ids a statement) instead of decoding every
  record into a dictionary, and `storageSnapshot(appID:)` counts and sums the held copies in one SQL statement. On a
  phone's store (2026-10-30) both read 47,393 records and 19.1 MB of JSON to find 13 copies; the consuming app evicts
  after each launch.
- The three readers of `instant_files` (the device's list, the id read, eviction's ids) read the id, app, name and
  times from the record's columns and the size, copy, owner, content type and URL with `json_extract`, instead of
  `JSONDecoder` (about 25 allocations and 5 us a record in #1072's measure); a record whose JSON holds one of those in
  another form than the encoder writes is decoded as before. The full list (`storedFiles()`) stays whole: the app reads
  every record by design.

**A launch keeps the newest ten stored results loaded** (#1107, #1149; red `9da1fbf5`, green `83446b22`; plan
`68ec5712`).

- Upstream `PersistedObject` preloads the ten most recently updated query results (`Reactor.js` passes
  `preloadEntryCount: 10` for `querySubs`) and loads any other when its query subscribes. Here a launch loaded the
  entities of every stored result: on a copy of a phone's store (2026-11-04, the consuming app's build 253) 46 loaded
  results held 1,915 entities and 48,202 facts after each relaunch, where the newest ten own 677 entities and 31,070.
- Now the bootstrap unloads where it is every stored result past the newest
  `InstantRuntimeConfiguration.preloadedLiveQueryResultCount` (10) by `updated_at_ms`, with one `UPDATE` of
  `unloaded_at_ms`, before the store's state loads; a result being released over later batches (#1129) is left to
  them. A query that subscribes again reloads its result from disk before it registers (#1131, #1500), offline included.

**A launch finds what it loads in the ownership rows** (#1149; red `44fc0c03`, green `518b7418`).

- A launch read each loaded result whole (its header and every ownership row decoded into a fact), ran the query's
  nested include limits over those facts again and bound every entity id it found as a parameter of the facts' read. A
  save keeps ownership of only the facts the nested limits keep, so the ownership rows already name those entities.
- Now the facts' read selects them with one subquery over the loaded, unreleased results' ownership rows and the
  outbox's entities, and the check for any ownership row is `EXISTS`, not a `COUNT(*)` that read every ownership row,
  unloaded results' included (#1500).
- E07 (the phone-shaped fixture's launch, Mac mini, release, one job), before (M2 `f504ed51`) -> after (`518b7418`,
  with #1107): resident facts 54,720 -> 9,728; allocations 634,027 -> 163,454; allocated 221.3 -> 70.4 MB; retained
  24.9 -> 9.0 MB; 234 -> 59 ms. Its bound is now 5 MB plus 540 B a resident fact (`7982385d`): so few facts leave the
  runtime's fixed cost most of what a launch retains.

**What the landing gate found** (red `708ded11`, green `74e65b56`; tests `caf33f20`, `b6a80186`, `7982385d`; red
`cb0e8578`, green `6779994f`).

- The whole bundle at the merge found 22 tests still expecting #1500's copy (20), #1165's old stamp for a fact adopted
  from another runtime's write (1) and a by-id file lookup's prune deleting facts (1). Each is restated for the property
  it guards: released rows, batched releases, ownership rows going with their batches and the residency reads (#654,
  #1129, #1319) are now tested on the policy's collection, the path that still deletes; the unload is tested as an
  unload.
- A session prune unloaded every closed result in one batch, so memory released all their entities under one gate
  hold, #303's shape (5.8-13.2 s with a write queued behind it). A bounded batch now unloads within the triple budget
  it collects with, oldest first, and the batches go on while unloads remain.
- The store's own prune (`SQLitePersistenceStore.pruneLiveQueryResults`, for callers without a hot store) returned
  before marking a closed result when it collected nothing; it now unloads as the runtime's batches do, and reads from
  SQLite the entities its snapshot lacks.
- A collection of results unloaded where they are, whose entities memory had let go, deleted their facts from disk but
  reported none and left the store revision unmoved; the count and the revision now follow the disk.

Merged over 1.9.68 (#1513, #1480, #1109), 1.9.69 (#653, #1517, #1523, #1142, #1648) and 1.9.70 (#1523): #1480's reuse of the
retractions' comparison feeds the same ownership write that records #1145's releases; a local write's commit claims
its own write at save (#653) and then counts it toward the next residency sweep (#1145); the local benchmark's seed takes
9 actor hops (8 before both: #1648 one store turn less, #1165 one store and one persistence turn more). It also carries 1.9.71 (#1796; merge `6ed41621`): a follower applies each query's newest result next and a one-shot read
waits while the connection receives or applies frames; the merge conflicted in two files' history headers only, and
1.9.71's runtime changes touch no prune, unload, reload, sweep or write-load path.

## Before you upgrade

Additive public API, source compatible: `InstantQuarantinedMutationVerification` (with its `Verdict`, `NotApplied` and
`CannotTell`), and `verifyQuarantinedMutation(id:)`, `completeQuarantinedMutation(id:)` and
`discardQuarantinedMutation(id:)` on `InstantRuntime` and `InstantSwiftDataClient`. `InstantSlotCoverage` and its
`Operation` and `Coverage` gain `Codable`.

Storage: `instant_outbox_quarantined` gains a `resolution_json` column the first time a held write is completed or
discarded (an `ALTER TABLE ... ADD COLUMN` on a store that already has the table; a new table is created with it), and
`resolution` takes `completed` and `discarded` besides `sent-again`. No outbox change, no migration: a store that never
settles a held write is not written to.

## Release focus

**A held write ends known: the server's own rows decide whether it completes, is discarded, or stays held and says
why** (#696, with the criteria merged from #134; red `e48ab65d`, green `9d26d2ca`, guide `339ca746`).

- Before: since 1.9.10 launch holds each retained mutation whose local cache effect is unknown (no SQLite-owned
  preparation receipt, which includes a row that predates durable optimistic-overlay metadata), and every other write
  synchronizes. An application could list, export and send one again; nothing settled one. #134 asked for a public,
  documented recovery API that verifies the authoritative server effect, then completes or discards the mutation,
  without guessing at the local cache effect.
- Now: `verifyQuarantinedMutation(id:)` reads, for each entity the held write set, the rows the server's answer
  carried, and returns a verdict with every slot's evidence:
  - **applied**: the server holds every value the write set, or a newer one that a later write of this device, which
    the server accepted, set (the rule #445 applies to a failed write). `completeQuarantinedMutation(id:)` records it
    completed; its observers see it accepted.
  - **not applied**: its kept outbox row says it never left this device (`delivery_started = 0`), or the server refused
    it with a client-error status and its rows do not hold what it set. `discardQuarantinedMutation(id:)` records it
    discarded; its observers see it failed. Send Again (1.9.10) remains for one that should be delivered.
  - **cannot tell**: it was sent and the server holds another value, it has a deletion, retraction or lookup step, or
    the server could not be read. It stays held, and the verdict says why.
- Complete and discard verify again before they write and refuse any other verdict. Each records the verification it
  acted on as JSON beside the kept row; the body is never touched (each body's SHA-256 is the same before and after).
- A retained mutation whose effect is unknown and that launch left in the outbox (an application on
  `.blockSynchronization`, or a row whose overlay is inactive) is held first, whole, when it is verified.

```swift
let verification = try await client.verifyQuarantinedMutation(id: mutation.id)
switch verification.verdict {
case .applied: try await client.completeQuarantinedMutation(id: mutation.id)
case .notApplied: try await client.discardQuarantinedMutation(id: mutation.id)
case .cannotTell: break  // It stays held; the verdict says why.
}
```

Two facts decided the design:

1. **This device's view is not evidence.** `queryOnce` answers from the local store once the server's answer is
   applied, so unsent later writes overlay it, and a held write's own leftover effect can still be in the triples. A
   verification that read it could call applied a write the server never got (the test
   `theHeldWritesOwnLeftoverEffectIsNotEvidence` is that case). The read takes the `add-query-ok` answer's rows where
   they arrive, before they join this device's view, and decodes them with the same translator a refresh uses.
2. **A value that differs is not proof that a write never landed.** A later write may have replaced it, and the server
   keeps a value's first-insert time, not its last update (upstream `triple.clj`: an EA update leaves `created_at` unless
   `overwrite-t`), so no timestamp rules a later write out. Only the delivery record can say not applied.

## Upgrade guidance

`docs/held-writes.md`: what launch does to an existing outbox (unchanged since 1.9.10), and how an installed iPhone or
iPad settles its held writes in place: launch online and let every other write drain, list and export the held ones,
verify each on the server, then complete, discard, send again, or leave held by verdict. No uninstall, no reinstall, no
reset, no deleted rows.

## Not run

- Instant's hosted server: the verification's reads are proven against a fake server that answers each `add-query`
  from rows it holds (protocol evidence), not against a credentialed live app. An answer shaped differently by the
  hosted server could not make a verification say applied: a value missing from an answer leaves its slot uncovered.
- The consuming application's held writes: they are listed in its Sync view, and verifying them is its owner's call.

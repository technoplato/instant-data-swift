## Before you upgrade

A one-time conversion at the first open, no public API change. A stored live-query result is its ownership rows, its
facts and a narrow header: `instant_live_query_results` gains `page_info_json`, its `json` is empty, and the markers
1.9.54 wrote in `instant_sync_metadata` for a result whose JSON waited (`live-query-result-json-waiting:<key>`) are
gone. The conversion runs once, decided by the table's own columns (a restore that brings back the old shape converts
again): each header takes the page info its marker holds, or else its JSON's, and then the JSON goes. A closed
query's unloaded copy (`instant_unloaded_live_query_results`) keeps its JSON, built from the rows once as it closes.

`flushPendingLiveQueryResults()` writes nothing: no stored result waits to be written. An app that calls it on
background and termination needs no change. An app that reads the library's tables with its own SQL reads a result's
facts through `instant_live_query_triples` joined to `instant_triples` on the fact's key, and its page info from
`page_info_json` (the consuming app's query audit now does).

**One way only.** A store this version has opened does not open with 1.9.55 or older, which read each result's JSON
(and 1.9.54 or older cannot read 1.9.55's outbox either). A rollback of an app past this release needs its store reset.

## Release focus

**A stored result is what every refresh already writes** (#1426, #1440). The rule for this release: a write is not
batched or delayed, and its cost is fixed at the source. 1.9.54 stopped writing a changed result's whole JSON every
five minutes by letting it wait in memory for the app's flush, with a marker for its page info and a repair from the
ownership rows after a kill: a deferral, and a second form of the result that a running process and a reader after a
kill saw differently (in the red, the running process's result carried the last frame's transaction on facts the
store holds with the stamps of the writes that made them). The ownership rows were already exact after every save.
Now they are the result:

- Every save writes the result's header (its count, its time, its page info) and the ownership rows that leave and
  join, in the refresh's own transaction. Nothing is held in memory, marked, flushed or repaired.
- Every reader builds the result from the header and the ownership rows joined to the facts, each fact with the stamp
  the store holds for it (`InstantStoredLiveQueryResultRows`, on the writer and on the read connection): the retraction
  diff, the prune, the unload, the reload, the declared-relation and application-migration passes. The retraction diff
  compares the stored rows with the new result by fingerprint, as the save's ownership diff does, and decodes only the
  rows that leave. A fact a result owns that the store no longer holds with that value (another result's refresh or a
  local write replaced it) reads the value the server last stated for this result, at time 0, so any stamp the store
  holds is newer.
- The header's update reads no JSON (#1440): a row of three numbers and the page info, where it read the result's
  whole JSON, overflow pages included, on every refresh.
- The unload's copy for a closed query is built inside SQLite (`json_object` over the ownership join), under the prune
  batch's operation-gate hold, as the copy it replaced was. The #436 bound on what an open-time pass reads counts the
  JSON a result's rows make, as it counted the stored JSON.

Measured on a Mac mini (debug, the StorageIO shim's log frames, the refresh exercises of 1.9.54), before (main at
1.9.55, the red) and after (the green), the bytes the log took per refresh and the bytes read back from it:

| Exercise | Before | After |
| --- | --- | --- |
| A refresh of three 50-row recordings lists, one row changed | 57.7 KB (14.0 frames), 3,246 KB read | 49.4 KB (12.0 frames), none read |
| A refresh of a 1-row recordings list | 33.0 KB (8.0 frames) | 24.7 KB (6.0 frames) |
| A refresh of 50 todos, one changed | 37.1 KB (9.0 frames) | 37.1 KB (9.0 frames) |
| A relaunch's unchanged answers, three 50-row lists | 24.7 KB, 3,428 KB read | 24.7 KB, 1,488 KB read |
| A relaunch's answers with one row changed, three 50-row lists | 65.9 KB, 3,508 KB read | 53.6 KB, 1,516 KB read |

What a refresh still writes is its change: the changed facts, each result's ownership rows for them, one page per
restated result's header, and the metadata page. What a relaunch's answers still read is each restated result's
ownership rows, twice: once for the retraction diff and once for the save's diff (#1480, filed with these numbers),
and the ownership rows hold each value in two b-trees (#1434).

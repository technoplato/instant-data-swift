## Release focus

A store whose cache holds one large live-query result opens again (#436, P0). Michael's iPad could not open Scribe:
"Could Not Open Scribe. Local Instant cache failed. While: read declared relation live-query result. Live-query result
'{"transcriptionSegments":{"$":{"order":{"segmentIndex":"asc"},"where":{"recordingID":"a96823cb-…"}}}}' exceeds the
bounded reconciliation row limit." The cached transcript of Recording 039, a 5.7-hour recording, is 8,817,787 bytes.
1.9.1 and 1.9.2 have the same defect.

## What changed

1. **An open-time pass drops a cached live-query result over its row bound instead of failing the open (#436).** When
   an app's declared relations change, the store's open reconciles them with the server's physical relations and reads
   every cached live-query result to do it. A result whose JSON was over 8 MiB (the outbox body limit, reused as a row
   bound) made that pass throw, so one large cached result failed every launch until the app's data was reset. Now the
   pass drops that result and its ownership rows and logs a warning, `live-query-result.oversized-dropped`, with the
   query key, the result's size, and the pass. The facts stay in the store, and the query's next refresh stores the
   result again.
2. **Application persistence migrations do the same (#436).** The other open-time pass that reads cached results drops
   one over the bound, or one the migration grows past it, instead of failing. A dropped cache row changes nothing a
   pending write's rollback depends on, so it does not count against the migration's receipt check.

The other open-time readers keep failing closed, as before: the relation pass's triples are links of a few hundred
bytes, and an application migration's outbox and triple rows are durable data, not a cache.

## For users of the library

- **API:** no public change.
- **Behavior:** at an open that reconciles relations or applies a migration, a cached live-query result over 8 MiB is
  dropped, with the warning above, and refetched when its query next subscribes. Until then that query has no cached
  result: its facts stay on disk but are not loaded at launch, so offline it shows less until it refreshes.
- **Storage:** no schema or data migration.
- **Dependencies:** unchanged from 1.9.2.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic
validation/run-performance-gate.sh live
```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

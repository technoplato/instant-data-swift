## Before you upgrade

One public addition, no storage schema change (one more metadata row, `connection.failure:<appID>`), no removal:

- `InstantConnectionStatus.interruption: InstantSyncInterruption?`: why this device's changes are not reaching the
  server, or nil while they are. `InstantSyncInterruption` has a `cause` (`noNetwork`, `weakNetwork`,
  `serverUnreachable`, `rateLimited`, `authentication`, `localRepairNeeded`, `other`), `since`, `retryAt` (a rate
  limit's, when the server gave one), `networkPath` (`none`, `cellular expensive`, `wifi`, ...) and `detail` (the
  library's words). `keepsQueuedChanges` is true for every cause; `endsOnItsOwn` is false only for `authentication`
  and `localRepairNeeded`.

Behaviour that changes:

- A reconnect's failed attempt publishes the connection status at once, with its interruption. Before, an attempt the
  reconnect loop made saved `.errored` and published nothing. A dropped socket itself still publishes nothing: upstream
  `Reactor.js` sets CLOSED for a drop and ERRORED only for a failed `init`, so an observer sees a drop as closed while the
  reconnect runs (`upstreamPythonSubscriptionPostInitFailureSilentlyRetriesAndResubscribes`); its cause is stored and the
  next status carries it.
- A server answer of type `rate-limited` (status 400 over the socket, 429 over HTTP) is transient: a write stays
  queued and is offered again no sooner than the hint's `retry-at` (else `retry-after` seconds from the answer); a live
  query stays registered and is sent again after that time. Before, the 400 read as a refusal: the write failed for
  good and the query was retired until relaunch. `InstantWriteFailureKind.serverFailureKind` says `.transient` for it.
  While the server rate-limits the open socket, the status's interruption says so, until it answers an operation again
  (`connection.rate-limited`, `connection.rate-limit-ended`).
- An `error` frame answering `init` keeps its status, type, hint and trace ids on the thrown `InstantError`.
- `connection.open-failed` and the reconnect events (`connection.receive-loop-failed` and the others
  `scheduleReconnect` logs) carry `failureKind` and `path` (and `retryAtMilliseconds` for a rate limit).

## Release focus

**The connection status says why changes are not reaching the server** (#2037; plan `643e160c`, red `ba50e4ae`, green
`02388736`, fix `91186166`, tests `74acc5ed` and `d71fd071`).

- Before: a consuming app's device on a cellular network that dropped every few minutes (one build, 2026-11-07,
  16:49-19:33) could only say that it was not syncing: the status read `.errored` with `lastErrorMessage =
  String(describing: error)`. Its own log, read for every span (scripts and tables kept by the app's audit): 28 drops,
  all with the network path up on cellular (the path was cellular in 177 of 177 minutes, never offline); 14 began with
  a write acknowledgement timeout, 13 with the socket dying (POSIX 57 "Socket is not connected"), 1 with a failed open;
  46 opens met the 5 s deadline ("Timed out after 5000ms waiting for Instant live transport."). No rate limit, no
  refused sign-in. The socket waits for connectivity (`waitsForConnectivity = true`), so a device with no network meets
  the same deadline; only the path tells them apart.
- Now the errored funnel (`saveErroredConnectionMetadataWithGateHeld(error:)`) classifies the error, the server's answer
  first (its status and type), then the error's kind (`InstantConnectionFailure`): a transport that did not open or
  keep up, the system's word that there is no route, a server that refused, failed TLS or answered a 5xx, a rate limit,
  a refused sign-in, a local repair, other. It stores the failure beside the last error, keeping the start of the
  failures since the connection was last open. The status reads it on the network path as it is when the status is made
  (a lock read of `InstantNetworkPathMonitor`, no hop): a transport failure is a weak network while the path is there
  and no network while it is not; a path that goes away after the failure turns the cause into no network, except for a
  refused sign-in and a local repair, which wait on someone.
- Upstream's server (vendored at `1bbf7386`): a rate-limited socket operation is answered with an `error` frame, status
  400, type `rate-limited`, and the socket stays open (`session.clj`, the per-op check exempts `init`); over HTTP it is a
  429 (`http.clj`); the retry time is only in the hint (`exception.clj`: `retry-at` an ISO 8601 instant, `retry-after`
  whole seconds); no `Retry-After` header is set. Upstream `Reactor.js` drops `type` and `status` from error frames and
  treats no error specially; Swift keeps its durable outbox, so it waits the server's time instead of dropping the write.

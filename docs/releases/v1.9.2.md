## Release focus

A device that once wrote a single-value attribute now sees other devices' later values of it, and their clears
(#431, P0). In 1.9.1, once the server accepted this device's write of a slot, the store kept this device's value over
every later value of that slot from any other device. On 2026-10-02 Scribe's iPad stamped Recording 039 as its
playback while the iPhone was capturing it: from then on the iPad showed the iPhone's newer `durationSeconds` but
never its newer `updatedAtMs`, and two minutes later Scribe's playback read the row as 131 s old and dropped the live
mark (Scribe #408, found by the live-stamp agent from the iPad's log and store).

## What changed

1. **The server's value of a single-value attribute replaces this device's accepted write (#431).** Instant updates a
   single-value triple in place and keeps its `created_at`, which a refresh delivers as the fact's time. The store
   resolved single-value facts by time, last write wins, so a write this device made after the slot was created,
   timed by this device's clock, beat every later server value of the slot. Now a server fact replaces the slot
   whatever the times, and only writes that are still pending stay on top of it. That is what the TypeScript core
   does: `Reactor.js` builds each query result's store from the server's triples alone and reapplies only the
   mutations that `processed-tx-id` does not cover (`_applyOptimisticUpdates`), and `store.js` `addTriple` sets a
   single-value slot unconditionally. Local writes still resolve by time among themselves.
   - The whole-component rebase applies server facts with `.preserveExactResident`, which now replaces a
     single-value slot whatever the stamps (`TripleIndexes.applyInsert` and the generic insert).
   - The reduced server apply (#296) no longer skips a server fact because the resident fact is stamped later
     (`residentFactWins` is gone). A server fact that changes a slot under no surviving write goes to the rebase once,
     and the next frame's restatement holds. Beneath a pending write, the server's fact patches the write's receipt
     whatever the stamps.
2. **A slot the server cleared loses the store's value (#431).** On a refresh, a single-value slot of an entity still
   in a result now loses every value the store shows there when the result, as the server sent it, holds none: a slot
   the result held before, and a slot its query selects (its `fields`, or every attribute without them) that it never
   held. The second is how a value no result ever held goes, which is the shape 1.9.1 left behind once it had stored
   a cleared result; it is checked on a query's first refresh after launch, and on each later one until the check
   finds nothing. When the query's key vouches for its selection, the newest result decides, even when a result stored
   earlier and not refreshed now still lists the old value. A key vouches when it is an InstaQL query whose namespaces
   and links this store knows and whose `where` stays on each level's own attributes; a `where` through a link brings
   the matched linked entities into the result without their attributes. For any other key, a value another stored
   result lists stays, as before. A query that does not select a slot says nothing about it. Before, only the result's
   own old value was retracted, so this device's value stayed after another device cleared the slot. Scribe's Stop
   clears `activityKind` and `activityClientID`.
3. **Only a pending write of the same slot protects a cleared slot's value (#431).** A retraction in a slot the server
   cleared is now protected only by a pending write of that slot, and not by the write the same server message
   confirms (the one it prunes at the watermark). Before, any pending write of the entity protected it, including that
   confirmed write, and a protected retraction is dropped for good, because the result is stored without the fact.
   Every other retraction keeps the protection it had: a pending write of the entity, so an entity that left a result
   is still collected whole or kept whole (#259).

## For users of the library

- **API:** no public change.
- **Behavior:** once the server accepts this device's write of a single-value attribute, the attribute shows the
  server's value, including another device's later value or its clear. While the write is pending, it still shows
  over the server's value, as before.
- **Storage:** no schema or data migration. A store that 1.9.1 left with this device's value in a slot heals without
  a reinstall: the next refresh that restates the slot replaces the value, and the first refresh after launch of a
  query that selects a cleared slot removes it.
- **Dependencies:** unchanged from 1.9.1.

## Red on 1.9.1, green here

Each round ran the new tests on v1.9.1's code first (library-79's worktree at `b182a3a9`, whose Swift is tag v1.9.1's),
then on this release's code, in one `heavy.sh` job (`library-79-red-431-2`, `-3b`, and `-4`, 2026-10-03; round 4 is
the final code). This is deterministic local evidence and evidence from a pulled device store, not a live check across
two devices.

- `InstantLocalStampShadowsServerTests`, ten cases, each on both server-apply paths, on the fast-drain fixture (a
  server model that stamps every later value of a slot with the slot's creation time, as Instant does). v1.9.1 fails 7,
  each showing this device's value (`updatedAtMs` 1790988543909, `activityKind` "playback", or the old `active`) where
  the other device's value or its clear belongs:
  - another device's later value, and its clear, landing between this device's acceptance and the refresh;
  - a clear while this device has another write of the entity pending;
  - a store left shadowed, healed on the first refresh after a relaunch, also when only one of the two results that
    hold the recording refreshes;
  - a value no result ever held, removed by a query that selects its slot;
  - a clear that wins over results stored before it.

  The three controls pass on both versions: a pending write still overlays the server's value, a query that does not
  select a slot leaves its value, and a key that does not vouch for its selection keeps a value another result holds.
  All ten pass here.
- `InstantFastDrainTests.aRestatedFactReplacesALaterStampedResidentFactOnce`, the expectation 1.9.1 pinned, flipped:
  fails on v1.9.1, passes here, and the next frame plans no bodies (no rebase loop, unlike build 73).
- `InstantLiveQuerySelectedAttributesTests`, six cases: how a query key's `fields` are read, and that a `where`
  through a link does not vouch (new here).
- `InstantLocalStampShadowsDeviceStoreTests` on the iPad's store pulled on 2026-10-03 at 00:52, on a credential-free
  scratch copy and a runtime shaped like Scribe's (skipped unless `INSTANT_431_DEVICE_STORE` names a store):
  - The store as pulled heals on both versions: its four results had restated the iPad's own values, so the Stop's
    refresh retracts them as those results' values.
  - The stuck shape on that store (the iPad stamps again, the server accepts, the iPhone's Stop lands before the
    refresh) stays stuck on v1.9.1: `updatedAtMs` keeps the iPad's 1791000100000, `activityKind` keeps "playback",
    and `activityClientID` keeps the iPad's new id. Here it takes the server's values.
  - The store v1.9.1 left stuck that way, reopened by this code, heals on the next refresh without a reinstall.
- Round 2 also found four other tests failing once (two 250 ms timing tests, a CLI contract decode, and a known-issue
  race in `fiftyEncodingFailuresUseBoundedRowAddressedQuarantineAndDoNotStarveTail`). On v1.9.1 the last failed 1 of 3
  runs; with the fix all four passed 3 of 3.

## Known open items

- Not verified live across two devices. The evidence is deterministic local tests, the iPad's pulled store, and a
  single-device soak against the throwaway app; Scribe build 82 on the devices is the installed-app check (#431's last
  criterion).
- A value no result ever held, left in this session by a pruned write whose slot another device cleared before any
  refresh restated it, goes on the first refresh of a selecting query after the next launch: the scan for such slots
  runs once per query key per launch, until it finds nothing.
- A query key that does not vouch for its selection (a `where` through a link, or a key this store cannot read) keeps
  1.9.1's rule: a cleared slot keeps a value another stored result lists.
- From the review: a cleared slot on an entity with another pending write sends that server apply to the
  whole-component rebase once (the reduced apply declines `retractsShadowedFact`), which can take seconds during a
  large backlog. And a refused write's rollback, or a protected value under a pending write that is later refused, can
  restore a value the server cleared, until the next launch's first refresh of a selecting query.
- The receive path's cost was not measured cleanly. A replay ABBA on Scribe's captured dictation (v1.9.1 against
  `1976f8aa`) ran beside other heavy jobs, and the follow-up removed the per-refresh scan it measured; a clean ABBA on
  this code comes with the next speed work.

  cross-SDK latency comparisons still fail: Swift took 4.6 to 6.5 times the TypeScript core's time at v1.9.1, not

- Carried from 1.9.1 and 1.9.0: #402 (a public resident-store statistic, refresh-ok's whole-result memory, a 16 MiB

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

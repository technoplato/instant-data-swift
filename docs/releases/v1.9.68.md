# Instant Swift Data 1.9.68

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (`0df9d697` plus its ledger and this release record):
every source change on `main` since `v1.9.67` is now marked ready for a build. It carries 1.9.67.

## Before you upgrade

No public API change, no storage change.

## Release focus

**A publication splices the rows a final line reaches** (#1513; red `a0dee714`, greens `f8b7c453` and `428411d9`,
tests `fe0b7951` and `b3435d8d`; merge `0df9d697`).

- On a recording phone each final line becomes its recording's preview in the recordings list and the newest line of
  the transcript's windows. The store's splice declined both, because the new line was shown by no row yet, so the
  list was materialized again from every recording and each window from every line of the recording. On the phone
  (the consuming app's build 248, 88 minutes of recording) observer refreshes were 41.8 CPU-s, the largest receive-side
  cost, and in a 90 s trace of speech (build 251) `InstantStore.refreshObservers` took 725 ms, 486 of them
  materializing pages.
- A verified observer now makes again only the roots a change reaches: a changed entity that keeps its place in the
  root set changes only the roots whose trees show it, or show an entity it links to before or after the change. An
  entity that enters a head window (a limit, no offset or cursor) is placed by the window's own bounded selection over
  its rows and the entering ones, which is exact: a full window gains a row, and a window that is not full shows its
  whole set, so it also splices a shown row that leaves or moves (a live line's final deletes it). New server page
  info for such a window only replaces the page info it reports. Anything else is materialized as before.

**A server apply compares each restated result with its stored rows once** (#1480, #1116 in part; red `322c3993`,
green `ca9dd8d2`, test `eecdc2d7`).

- The retractions and the save each compared a restated result with its stored ownership rows, each pass encoding
  every restated value and reading every row (`serverApplyRetractions` 15.0 and `serverApplyPlan` 15.3 CPU-s in the
  same 88 minutes). The save now takes the retractions' comparison, made in the same read, when the facts it saves are
  the facts compared; a nested limit that drops a fact, a different count, or a key restated twice in one frame
  compares again as before.

**A refresh whose nested limit keeps every fact removes nothing** (#1109; `4fff7e5c`): the translator no longer builds
a set of every restated fact's identity, its value's text included, to remove none.

**F21's guard** (#1116; `0459f173`): `aLargerPageWithOneLineChangedCostsAboutWhatASmallerOneDoes` holds a 256-line
page's refresh to twice a 64-line page's rows read and values encoded. It is about 4x today, recorded as a known issue
until each result's rows are kept in memory.

## Checks

Mac mini, one build.sh job (`1797-recv-splice-ab2`, 2026-11-04 21:19-21:59 EST), release builds of the red sources and
of `0459f173` side by side, then the whole bundle in debug. `0df9d697`'s sources and tests are byte-identical to
`0459f173`'s (`main` gained only documents since).

- Red: `aFinalLineSplicesTheListRowAndPlacesTheLineInEachWindow` and
  `theServersEchoWithNewPageInfoStillSplicesAHeadWindow` fail (the list and the windows re-materialize);
  `aRefreshComparesARestatedResultWithItsStoredRowsOnce` fails (192 rows read and 192 values encoded where 96 are
  expected). Green: all pass, and the differential `everyObserverHoldsAFreshResultThroughRandomRecordingWrites` passes
  at both.
- Green, release: 131 tests in 13 server-apply, live-refresh and stored-result suites, and 521 in 15 publication,
  store, infinite-query and observation suites, pass but for the known release-only `withKnownIssue` artifacts (four
  tests whose library issue only a debug build records) and the CLI tests, which need a CLI binary the release job
  does not build (they pass in the bundle below).
- `PublishFanOutExercises` (48 observers: three 50-row recordings lists with five includes, eight 64-line transcript
  pages, the live line, 36 small queries; 2,000 publications, red and green alternating, two rounds):
  - a final's publication p50 17.6 and 18.2 ms -> 15.6 and 16.0 ms, p90 19.3 and 20.1 -> 17.7 and 17.6 ms;
  - observers re-materialized 3,500 -> 2,800, materialized snapshots 320,850 -> 181,550 (-43%);
  - with each interim written into the open line, linked to the recording: an interim's p50 2.90 -> 0.48 ms, a final's
    16.3 -> 14.3 ms, materialized snapshots 264,255 -> 54,885 (-79%).
  - What still re-materializes on a final is the fixture's seven offset transcript pages (a new line shifts each by one
    row) and its live-line query, an indexed read of one or two rows. The consuming app observes no offset page live:
    its offset read of a recording's lines is a one-shot answer.
- E03 (one page refresh applied on the phone-sized store, eight runs): 64 lines 6,522 -> 6,485 allocations and 5,757
  -> 5,493 KB; 256 lines 19,476 -> 19,442 and 19,317 -> 18,263 KB. One live write's echo (`eachStepOfALiveWrite`):
  4.53 -> 4.08 ms CPU.
- The whole InstantSwiftDataCoreTests bundle at green, debug (1,669 tests, 379 s, plus 14 measurement tests alone,
  197 s, load 1.3-6.6) against `Tests/known-failing.txt`: 4 failing, one of them listed; the other three fail on
  `main` since 1.9.64-1.9.67 (`InstantAcknowledgementDigestTests` `aBodyStoredInAnotherEncodingReusesTheKeptFingerprint`
  and `aBodyWhoseContentChangedIsFingerprintedAgainAndRefused`, and the timing ratio of
  `InstantLiveFrameDecodeTests/aServerResultDecodesAtAFractionOfJSONDecodersCost`, 0.344 against 0.33), none in what
  this release touches.

## Not run

The release gate, `validation/run-performance-gate.sh live`, did not run (the maintainer's authorization quoted above):
its wire lanes, memory and throughput were not measured. This release changes how the store publishes to observers and
how a server apply plans its result saves, not the wire or the stored format. Its effect on a phone is measured after
the consuming app's build carries it (`refresh-cost.py`, an hour of recording), and recorded on #1797.

# Instant Swift Data 1.9.80

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (the landing of `agent/claude/ack-session-1942` and this
record): the only source change on `main` since `v1.9.79` is this release's. It carries 1.9.79.

## Before you upgrade

No public API change, no storage change, no schema change. Delivery behaves differently in one case: a write whose
answer is late, on a session that still delivers frames, keeps its claim and its session instead of replacing the
session. Two new diagnostics lines: `outbox.mutation.ack-late-kept` (notice) and `outbox.mutation.ack-late-wait-exhausted`
(warning). `outbox.mutation.ack-timeout-batch` and `connection.mutation-delivery-failed` now mean the session went
quiet or a write stayed unanswered for the deferral limit.

## Release focus

**One late answer no longer tears down a session that still delivers frames** (#1942; plan `80588602`, red `7a8f53c5`,
green `d10f9b13`).

- Before: a durable write that missed its acknowledgement deadline (6 s times its place in flight) expired its claim,
  and the live session was replaced (`releaseMutationReservations(_:timedOut:)`: a new generation and `abort()`) before
  the write went out again. Every one-shot read in flight failed with it and every registered query was sent again.
  Measured on a consuming app's Mac on 2026-11-06 12:27-12:41 (1.9.78, the laptop's load 105-300, two long recordings
  opened, their detail registering about 35 live queries at once): 16 `outbox.mutation.ack-timeout-batch` lines, each
  expiring exactly one write, each followed by `connection.mutation-delivery-failed`; 71 failed one-shot reads that
  hour against 0-3 in each other hour of the day. One write missed its deadline at 6.3 s and was accepted 1.6 s later
  on the next session: the old session was slow, not dead. One-shot reads that failed at a replacement had kept waiting
  through four 5 s stall windows, each of which needs a frame received, taken or being applied, so the session was
  still delivering up to the deadline (an inference from their timing and the stall rule, not a frame count).
- Upstream `Reactor.js` (`_sendMutation`) fails only the transaction when its timer fires and never closes the socket
  for it. Swift keeps the write in a durable outbox, so it now keeps the claim: a delivery pass reads, in one hop, the
  frame the applier is applying and how many frames it has taken. While the applier took a frame within one interval
  (6 s), the claim admission keeps this runtime's claims that passed their deadline, moved one interval later with their
  tokens, inside the SQLite transaction that would have reclaimed them, so a wait for the operation gate between the
  look and the claim cannot let them expire. The answer, when it comes, settles the write on the connection it was sent
  on.
- Kept from #296, #1383 and #1270: a frame being applied still defers the deadlines by its own bound (a stuck frame is
  still stuck after 120 s without progress, and the taken-frame count does not move while one frame is stuck). A session
  whose applier took no frame for a whole interval may be half-open, so its late claims still expire and it is still
  replaced, one or two intervals after its last frame (the count is read at each pass). A write kept past its deadline
  for the deferral limit (120 s) on a delivering session is given up as before, behind the acknowledgement-unknown
  barrier, so a lost answer cannot hold the queue or leave older writes unconfirmed under newer ones for longer than it
  did. Offline writes replay as before: nothing in the claim order, the barrier or the replay changed.

## On the consuming app's Mac, before this release

Measured from the app's own diagnostics (library 1.9.78-1.9.79, builds 286-293; the laptop's 5-minute load per hour from
its build queue's journal):

- At rest, 12:52-20:06: 481 writes, acknowledgement time (save to server-accepted) median 90 ms, p90 317 ms, p99
  682 ms, max 1,301 ms; no `ack-timeout-batch` and no `mutation-delivery-failed`. 13:00-14:59 ran at load 107-312
  (median 144-148) with none either, so load alone did not trigger the replacements: the 12:27 window also had two long
  recordings' detail queries registering at once and the server answering some of them `500 operation-timed-out`.
- Opening the 7-hour recording at 20:32 (build 293, 1-minute load 21-37): its compressed copy was found 0.33 s and
  loaded 5.96 s after the screen appeared, on the first try; no batch and no replacement. Three live queries were
  answered `500 operation-timed-out` (20:32:31), and six one-shot reads begun about 20:32:55, after the timed window,
  failed at 20:33:27 on the 30 s limit while the connection kept receiving and applying frames (#1796's rule), not on a
  replacement.

## Not run

The release gate `validation/run-performance-gate.sh live`, nor its Swift→TypeScript and TypeScript→Swift boundary
checks (the maintainer's authorization quoted above): this release changes when a claim expires, not what a write
sends, stores or delivers, and adds one indexed read of at most the in-flight window per claim; no memory or throughput
number was measured for it. The consuming app's after-measurement (ack-timeout batches and session replacements per
hour, failed one-shot reads, acknowledgement times, the 7-hour recording's first try, each with the laptop's load)
waits for the first build that pins this release.

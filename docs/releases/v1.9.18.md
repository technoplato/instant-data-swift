## Release focus

A server apply costs what its frame changes rather than what the outbox holds, and its event says what it cost (#932).

On the phone (build 114) a server apply held the operation gate 4.3-7.4 s about every 30 s with ~2,560 pending writes,
and 1-4 s with none; every transact, query, observe, delivery claim and acknowledgement waits on that gate. With a
backlog, each refresh peeled and replayed every pending write of the recording (~888 changed entities a frame), and the
event recorded only "commit 3,914 ms".

1. **The gate-held event names its cause** (green `7b468b16`). `server-apply.operation-gate-held` now carries the path
   (`reduced`, or `full rebase: <reason>`, the #296 reduction's decline that was logged at debug only), the attempt,
   whether the gate was held from the seed, the planned and peeled body counts, and the commit's parts measured inside
   the persistence actor: validation, facts, outbox, results, bookkeeping and the SQLite `COMMIT` (a checkpoint inside
   `COMMIT` lands there), with the result JSON bytes written and the outbox rows deleted. The commit phase minus
   `commitInsideMilliseconds` is the wait for the persistence actor.
2. **The resident-outbox patch reads only the rows the in-memory outbox holds** (green `0e493cba`). Under the gate it
   read and decoded every staged row and hopped to the outbox once per row (0.8-1.3 s of the phone's gate holds). The
   in-memory outbox holds only the claimed delivery window, and rows it does not hold were no-ops.
3. **A body page checks only its own rows against the outbox** (green `89c462cd`). Each 51-row page re-validated the
   whole plan: about 2R^2/50 row checks per full apply (~262,000 at 2,560 pending), each walking a body's overflow
   pages. Extending the plan and the commit still validate every row, in the transactions that write.
4. **A frame restating a live line its final deletes is reduced** (green `17bc06b8`). Scribe's line in progress is a
   `liveLines` row that the line's final deletes (ADR 0069). During a backlog the server's live-lines result still shows
   rows whose final is pending, and a delete leaves no write key, so the reduction declined and the apply peeled and
   replayed every pending write. The reduction now names, for each shadowed entity the store does not show, the
   surviving write that deletes it last, and places a scalar fact on it where the full rebase would: in the receipt that
   holds the slot's base, or nowhere when that receipt already holds it. Links, many-valued slots and receipts that
   cannot name the base still take the full rebase (`deletedEntityFact`).

5. **The package compiles for the Watch again** (#1019; red `32f92123`, green `d165589d`, from release-116).
   `InstantFileBlocks` (1.9.14, #959) passed `UInt32(FSOPT_ATTR_CMN_EXTENDED | FSOPT_NOFOLLOW)` to `getattrlist`, whose
   options are `UInt32` on 64-bit platforms but `UInt` on the Watch's arm64_32, so 1.9.14-1.9.17 did not compile for the
   Watch. It now passes `numericCast(...)`, the same value on 64-bit platforms. `scripts/check-watchos-arm64_32.sh`
   type-checks the helper for arm64_32 and arm64 watchOS, arm64 iOS and arm64 macOS.

## What stays the same

No public API, schema or migration change. What every observer is shown is what the full rebase shows: the
reduced-versus-full differential checks it after every step, now also with live lines. Delivery, acknowledgements and
the outbox's order are unchanged, and the commit still validates every planned row and the component's closure in the
transaction that writes, so a write reaches the server, and a server change reaches its observers, no later than before.

## Not changed here

- A refresh's restated query results are still diffed against their stored ownership rows under the gate: on a copy of
  a real store (0 pending, 7,287 restated facts a frame) the commit is all `results`, 87-140 ms a frame on a Mac mini;
  that is the phone's 1-4 s commit with nothing pending. The next release prepares those saves before the gate.
- The commit's outbox update (fifteen correlated lookups per row), the staging table's column order (bodies before the
  small columns) and the commit's closure re-plan, which reads every body's length.
- When local writes land between every attempt's seed and plan, the apply still runs once holding the gate from seed to
  commit (`server-apply.exclusive-fallback`).
- The steady-state sync tasks still run at their caller's priority (#590).
- A frame the reduction declines for another reason still peels, re-stamps and rewrites every pending body (~95 MB a
  frame at 2,580 pending in the fixture).

# Instant Swift Data 1.9.10

Status: published by direct maintainer authorization, typed on 2026-10-14: "Land all this performance work and then
install that in the next build as a developer build and as a production build. So build both. I want to just compare."
(16:03 EDT) and "Do 694 release it test it and get it into scribe" (20:30 EDT). This release is what lets a device whose
store an earlier version wrote synchronize again (#696). The checks that ran are below: on `7c30fda4`, the last code
commit, and on `fe8976a7`, which changes one test.

## Release focus

A retained mutation with no preparation receipt no longer stops every other write (#696).

Since migration 0020, every outbox row carries a SQLite-owned preparation receipt: the record, written by the runtime
in the same transaction as the write's local effect, of how to undo or replay what the write did to the local cache.
A row without one has an unknown local effect, so it can never be sent safely. Up to 1.9.9 the first such row refused
every live connection: `connect()` threw `persistenceFailed` ("Mutation '…' has no matching SQLite-owned Runtime
preparation receipt, so its local cache effect is unknown. Synchronization is blocked by N retained mutations."),
automatic reconnect paused, and every later write, however valid, waited unsent behind it. The only way out was a
destructive local reset, which set aside every unsent write with the few unknown ones. A store written by an earlier
version held five such rows among its older writes; on that device thousands of valid writes made afterward never left
it.

Now runtime bootstrap moves each such row, whole, out of the outbox into a quarantine, and the runtime opens and drains
every other write in its order, exactly as before. Nothing is deleted: the quarantine keeps each row as it was, the
library never sends or removes one on its own, and an application lists, exports and sends one again when the person
asks.

## What changed

1. **The quarantine (`instant_outbox_quarantined`).** Created the first time a store needs it, not by a migration, so a
   store that never holds such a row never gains the table and is not written to: the check is the indexed read the
   synchronization blocker already made. One row per quarantined mutation:
   - `mutation_id`, `created_at_ms` and `status` as the outbox had them;
   - `json`: the outbox body, byte for byte;
   - `outbox_row_json`: every column of the outbox row as one JSON object (`json_object` over the columns the store's
     `instant_outbox` has, read from its schema, so a row keeps the columns of whichever version wrote it);
   - `reason` (`no-preparation-receipt`) and `quarantined_at_ms`;
   - `resolution` and `resolved_at_ms`: NULL while the row is held; `sent-again` after Send Again. The row stays.
   - `quarantine_id` keeps a mutation quarantined twice as two rows; nothing in the table is ever replaced.
2. **When it runs.** In `InstantRuntime.bootstrap`, after the store's migrations (and the application's own) and before
   the runtime derives the synchronization blocker, in one SQLite transaction: copy each row whose optimistic effect is
   active and has no receipt (exactly the rows the blocker reports), then remove it and its derived write-key and
   effect-entity index rows from the outbox, then bump the outbox revision. A failure rolls the transaction back, is
   recorded (`outbox.mutation.quarantine-failed`), and leaves the rows where they were, so the runtime behaves as 1.9.9
   did; a launch never fails because of this step. A move is recorded as an error-level diagnostic
   (`outbox.mutation.quarantined-no-preparation-receipt`, with the count and the first IDs).
3. **What stays the same.** Every other write keeps its row, its receipt and its place: the outbox drains in creation
   order as before. Local triples are not touched: what a quarantined mutation materialized stays until a server result
   replaces it, which it now can, because no unproven row protects every server retraction any more. A receipt the
   runtime revokes while a session runs (a body that no longer matches its receipt) still stops that session as before;
   the next launch quarantines that row.
4. **The ledger.** `InstantQuarantinedMutation` (its ID, `reason: .noPreparationReceipt`, when it was quarantined and
   created, the status it had, its body, its outbox row as JSON, and the body decoded when it still decodes), read
   through `quarantinedMutations(limit:)` and `quarantinedMutationCount()` on `InstantRuntime` and
   `InstantSwiftDataClient`, outside the operation gate. Only rows still held are listed.
5. **Send Again.** `retryQuarantinedMutation(id:)` makes the held mutation's transaction a new local write with the
   same ID, prepared against the store as it is now, so it gets its own receipt, and the outbox sends it in its order.
   The quarantine row stays, marked `sent-again`. It throws, and the mutation stays held, when no held mutation has the
   ID, its body no longer decodes, or the write fails as any write can.
6. **A held mutation's lifecycle.** Its outbox row is gone, so `observeMutationLifecycle(id:)` used to answer
   `.waiting`, forever. It now answers `.failed`, with the effect unknown (no overlay, no rollback) and a message naming
   the quarantine; never `.serverAccepted`, whatever the held body says. After Send Again the new row answers as any
   write.
7. **The old wall, on request.** `InstantRuntimeConfiguration.retainedMutationsWithoutPreparationReceipt`:
   `.quarantine` (the default) or `.blockSynchronization`, which keeps 1.9.9's behavior. Thirteen existing tests that
   seed receipt-less rows before launch, to test that behavior or to measure stores that keep 500 or 10,000 such rows,
   ask for it (`a6fbc77b`, `fe8976a7`).

The API change is additive.

## Checks

All through the laptop's load guard (`safe-heavy`); the machine was shared with other builds (5-minute load 50-140).

- **Red, then green.** `InstantRetainedMutationQuarantineTests`, on a clean build at the red commit (`ca789c91`):
  `connect()` threw `persistenceFailed` ("Synchronization is blocked by 3 retained mutations"), both guards passed; at
  `da8ce80e` all three pass. Send Again and the held lifecycle: red at `03468750` (the two expected failures), green
  at `7c30fda4`: 34 of 34 in the focused set, one test at a time (the suite's 4 tests, the twelve tests that pin the
  1.9.9 wall, the lifecycle test, 17 upstream fixture checks).
- **The tests that pinned the 1.9.9 wall.** The whole suite at `da8ce80e`, then every failure one test at a time:
  twelve tests that seed receipt-less rows before launch, to test blocking synchronization or to measure stores of 500
  and 10,000 such rows, now ask for `.blockSynchronization` (`a6fbc77b`); a thirteenth (a failed public body's
  lifecycle) passes with the held lifecycle. The clean whole-suite run below found one more, a caller-shaped accepted
  body whose lifecycle must stay `.waiting` in the outbox: it asks for the wall too (`fe8976a7`); by default it is held
  and reports `.failed`, never accepted.
- **A store an earlier version wrote.** A local probe, not committed, ran copies of two real stores written by an earlier
  version through bootstrap: one with 1,729 pending and 410 failed rows, one with 99 failed rows. With
  `.blockSynchronization` each reproduces the field failure exactly (5 retained mutations, and 1). With the default,
  bootstrap quarantines exactly those rows (all of them failed rows), the blocker is gone, every other row keeps its
  status and place, and the SHA-256 of each held body equals that of the body the copy held before bootstrap.
- **The whole suite on a clean build of `fe8976a7`** (built from an emptied `.build` 2026-10-15 01:30-01:35, run
  02:16-02:27 with the one pre-existing hang skipped, as for 1.9.9): 2,094 tests in 208 suites, 37 failed in parallel
  under load. Those 37 again one test at a time (`--no-parallel`): every one passes except the same 7 that fail on
  1.9.9 (#304's `typedLookupUpdateCanResolveEntityCreatedEarlierInSameTransaction` and six environment checks: the
  vendored SQLiteData record, three TypeScript contract verifiers, the upstream checkout's pin and inventory).

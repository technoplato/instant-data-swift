## Before you upgrade

No migration, no public API change. A waiting result's marker in `instant_sync_metadata` now holds its page info as JSON
(`{"pageInfo":...}`) where it held `1`; a marker an older version wrote is read as before, and an older version reads
the new one by its key alone. The internal `InstantRuntimeConfiguration.liveQueryResultJSONWriteIntervalMilliseconds` is
now optional and nil by default.

## Release focus

**A server refresh writes what changed, not the whole result** (#1426). The consuming app's phone wrote 334 MB an hour
of server-apply commits while recording, 131 KB each, 2,553 an hour (its energy ledger, 2026-10-30 12:00-17:14, launch
minutes left out). Instant's server restates a live query's whole result after every transaction that changes it, so
the question was whether the store's writes follow the frame. Mostly they do not: the reduced server apply leaves a
resident fact with the same value alone, so a refresh of 50 rows with one changed writes what a refresh of one row
does (todo rows 9.0 log frames against 10.0; rows shaped like the phone's recordings, held by three results, 12.0
against 8.0), and on a copy of the phone's store the facts keep the stamps of the writes that made them. Two writes did
follow the result:

- **Each changed result's whole JSON, every five minutes** (#1123's interval). Over five minutes of a recording's list
  refreshes 6 s apart, three 50-row lists wrote 93.4 KB a refresh against 33.7 KB for one row. The JSON now waits for
  the app's flush on background and termination, an unsubscribe or the close. Nothing is lost by waiting: the
  ownership rows hold each result exactly after every save, and a kill is repaired from them at the next launch
  (#566). A window over a growing list moves its cursors with every new row, so a waiting result's marker now holds
  its page info, written again only when it changes, and the repair uses it.
- **A relaunch's answers rewrote unchanged results' JSON.** A new process did not know the page info a stored JSON
  holds, so the first answer restating a stored result wrote it whole even when nothing in it had changed. The first
  save of an unchanged stored result now reads its page info inside SQLite and leaves the JSON alone.

Measured on the laptop (debug, the StorageIO shim's log frames), before and after:

| Exercise | Before | After |
| --- | --- | --- |
| Five minutes of refreshes, three 50-row lists | 93.4 KB a refresh, 3 JSON writes | 57.7 KB, none |
| A relaunch's unchanged answers, three 50-row lists | 1,248 KB | 24.7 KB |
| A relaunch's unchanged answer, 50 todos | 98.9 KB | 8.2 KB |
| A relaunch's answers with one row changed, three 50-row lists | 1,277 KB | 65.9 KB |

What a refresh still writes is what its change costs: the changed facts, each result's ownership rows for them, one page
per restated result's row, and the metadata page. The larger costs found on the way are their own issues: the outbox's
claim and acknowledgement rewrite the whole row, body included (#1435, about 262 MB/h on the phone), about ten
outbox-side b-trees at each save and again at the echo (#1436), and the ownership rows hold each value in two b-trees
per result (#1434).

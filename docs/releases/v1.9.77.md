## Before you upgrade

One public API addition, source compatible: `InstantProgressiveMediaReader.Source` gains `segmentsAt` (a stream's stored
segment rows at given indexes, in any order) and a four-argument init. The three-argument init still compiles; its
`segmentsAt` reads each run of consecutive indexes as one `segments` page. `Source.live(_:)` reads them by the rows'
derived ids. In a long stream's `Snapshot.segments`, a segment placed by the stream's grid without reading its row has a
`byteCount` of 0. No storage change, no row change, no schema change.

## Release focus

**A long progressive media stream lists from its last rows, read by id, whatever its length** (#1916; red `b04dd179`,
green `5645a2ec`, ADR 0021 amendment `215a0f87`).

- Before: `refresh()` read every segment row, 500 a page, one page after another, before the resource loader could
  answer the playlist, so a player's first sound waited for 2 reads at 81 minutes (811 segments) and 16 at 12 h 49 min
  (7,695). Measured 2026-11-06 against a live app: a cold first page took the server 1.1 s for 164 rows, 2.2 s for 811
  and 5.2 s for 4,203 (warm pages 0.15-0.9 s), and a consuming app with a large transcript loading never finished the
  walk: AVFoundation gave up on the playlist request after 20 s, on every retry.
- Now: a stream longer than 64 segments is listed from its last 64 rows. The writer starts each segment where the one
  before it ends, names each file after its index and writes the stream's `segmentCount` with each segment row, after
  its file; AVAssetWriter cuts a take every `segmentSeconds` from where the take starts. So a stretch whose ends sit `n`
  segments and `n * segmentSeconds` apart (within 0.25 s) is placed by arithmetic, one that is off is split 16 ways at
  rows read together, and a stretch of 64 or fewer is read whole. A gap or a foreign path among the rows read falls back
  to the walk.
- Read by id: on streams not read for a while, any read that selects by `streamID` cost the server 3.7-6.6 s (it reads
  the stream's rows; the last 64 by `streamID` and `index`: 1.0 s at 811 segments, 2.5 s at 1,768, 4.5 s at 4,203, 6.6 s
  at 7,695), while rows read by their derived ids took 39-68 ms for one and 171-315 ms for 64. `$in` on `index` was
  slower still (7.6 s for 17 rows), and `$gte` with `$lte` in one clause kept only the lower bound.
- A census of the live app's 221 streams (every row read): 218 whole and contiguous, 212 with every start within 0.25 s
  of the grid, 8 shifted 1.4-5.4 s, each breaking only in its last two segments, which the last rows hold.

```swift
let reader = InstantProgressiveMediaReader(streamID: stream.id, source: .live(client))
let snapshot = try await reader.refresh()  // a 12-hour stream: one read of its last 64 rows
```

# Instant Swift Data 1.9.42

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `239ba916`; its last code commit is `53979805`. It carries 1.9.41.

## Before you upgrade

Nothing new: 1.9.42 adds no migration and changes no stored format. 1.9.41's warning stands: a store 1.9.40 or later
opened cannot be used by an older build, so an app that keeps its store across installs must delete its data before an
older build is installed over it.

## Release focus

Delivery, one-shot reads and compaction stop taking the operation gate for work they do not need. Each fix is a red
commit, then a green one:

1. **A write's delivery claims it once, and takes no retry turn while nothing failed** (#1130; red `9ec20c0c`, green
   `b8a2c11e`). Each pump pass opened with the retry window's turn under the gate, and every `transact-ok` asked for a
   second pass that found nothing to claim. A pass now reads, without the gate, whether a failed write waits to be
   retried; a `transact-ok` asks for a pass only when a write waits to be claimed or retried. Upstream `Reactor.js`
   settles a mutation on `transact-ok` and flushes nothing.
2. **A one-shot read answers without the operation gate** (#1134; reds `24b7177a`, `70257dfe`, greens `7e8460c5`,
   `8aa690b0`). While SQLite holds what the store has installed, `queryOnce` answers as the local read does, from a
   local observation's first answer, and writes its query-cache row after it, revision-checked; a read that finds a
   write of this process mid-commit waits for it to leave the gate (`AsyncSerialGate.waitForRelease()`) without taking
   it. Only another connection's write, which must be adopted, and a closed connection's error read under the gate.
3. **Compaction asks the app's hold once, before the operation gate** (#1136; red `d0280c43`, green `53979805`). Under
   the gate it asked the hold closure again, so the gate was held while the closure ran (the consuming app's hop to
   the main actor). Under the gate it now re-checks only what reads at once: cancellation, the device's heat and power,
   the volume's room.

## Measured

On #1072's real-size fixture (version 3), Mac mini M4, release, two runs each:

- **#1130** (`recording`; main with #1133 before; 90 writes, all accepted): delivery claims 180 -> 90 a minute, retry
  turns 180 -> 0; delivery's gate time about 0.6-0.7 s a recorded minute; acknowledgements unchanged (p99 108-122 ->
  109-114 ms).
- **#1134** (`recording`): one-shot read holds 60 -> 0 a minute (863-884 ms of gate -> 0); a write's wait for the gate
  p99 12.70-19.83 -> 4.49-12.24 ms; the read's latency unchanged (p50 about 110-114 ms, the server's round trip). The
  relaunch's 14 actor calls are now gate 4, persistence 6, store 4.
- **#1136** (`compaction-main-hop`, new: a hold closure that asks a main actor kept busy in 30 ms slices): the gate's
  hold 189.09/169.88 ms against a VACUUM of 159.08/139.86 ms -> 159.55/156.00 ms against 154.19/150.67 ms.

## What stays the same

No public API change. `compactLocalCache(holdingWhile:)` asks `hold` once, before the gate (its documentation says so):
an app that must stop a compaction that already passed its hold cancels the compaction's task. A one-shot read returns
the same rows: the query-cache, cross-runtime, parity and local-read suites pass unchanged.

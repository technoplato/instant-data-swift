## Release focus

A local write no longer holds the runtime's operation gate while it writes the log, and listing the outbox never waits
for the gate (#473, P0). On Michael's iPhone (Scribe build 82, library 1.9.2) a local write held the gate for 12 s at
13:17:46 on 2026-10-03 ("hydrate deferred query emission waited 12133 ms"); the app went silent and relaunched, and
Recording 185 died. At 14:03 Recording 186's transcription stalled behind a write backlog, with persistence failures, a
missed 5 s durability deadline, and pending writes climbing from 23 to 51 while the phone was hot. Recording 040's
report measured local writes holding the gate for about 300 ms each, at 1.6 writes a second.

## What changed

1. **The diagnostics log file is written off the caller's thread (#473).** A write logs while it holds the gate, and
   every line created the log directory, opened, locked, wrote and fsynced the file before the call returned. Now
   `InstantDiagnostics` hands each line to its own serial queue, which writes them in order, so `record(...)` returns at
   once. `flush()` waits for every line recorded so far; `configure(_:)` and process exit flush. If the file falls
   8 MiB behind (a disk that stopped answering), new lines are dropped and `lastWriteError` says how many. Handlers
   still run synchronously.
2. **The gate's wait and stall reports run off its actor (#473).** A caller that waited is resumed at once, and a slow
   report (a diagnostics line and the app's handlers) never holds the gate. On the iPhone, writing the stall line held
   the gate for about 4 s of the 12 s hold.
3. **A local write names its phases (#473).** read state, adopt store, load deferred values, prepare, save, publish
   store, publish status, so a stall or a slow handoff says which phase held the gate. Phases are named with a lock
   (`markHolderPhase`), not an actor hop, and server apply now names its phases the same way, without its five hops.
4. **Bounded outbox listings off the gate (#473, #445).** `pendingMutations(limit:)` and `failedMutations(limit:)`, on
   the runtime and `InstantSwiftDataClient`, read the oldest rows from SQLite without the operation gate and without
   decoding the rest. `pendingMutations()` and `failedMutations()` still decode every row under the gate: after a
   relaunch on Michael's iPhone such an unbounded listing held it for 4.1 s, and that store held 309 failed rows.

## For users of the library

- **API:** additive. New: `InstantDiagnostics.flush()`, `pendingMutations(limit:)` and `failedMutations(limit:)`.
- **Behavior:**
  - Log lines reach the file asynchronously; read the file or `status.lastWriteError` after `flush()`.
  - A process that exits flushes; one killed at once can lose the lines it recorded in its last moments.
  - Stall and wait reports for local writes now carry a phase.
- **Storage:** no schema or data migration.
- **Dependencies:** unchanged from 1.9.4.

The new tests that need no 1.9.5 API ran on v1.9.4's code first: library-79's second worktree at `4da6f182`, with
`InstantOperationGateHoldTests` minus its tail that needs 1.9.5's API (`library-79-gate-195`, 2026-10-03 14:59–15:10

- `recordingAnEntryDoesNotWaitForTheLogFile`: the log file is a FIFO with no reader, so opening it blocks.
  - On v1.9.4, `record(...)` waits on that open: "record waited for a log file it could not open".
  - Here it returns at once; the write waits on the writer queue.
- `theNextHolderRunsBeforeItsWaitIsReported`: the gate's wait report blocks.
  - On v1.9.4 the next holder waits for it: "the next holder waited for the wait report".
  - Here the next holder runs first.
- `aLocalWriteNamesThePhaseThatHeldTheGate`: one local write pauses after its save while a second waits.
  - On v1.9.4 the run crashed (SIGBUS) at this test. The second worktree's incremental build from v1.9.3 to v1.9.4
    had kept test objects compiled against `InstantRuntimeConfiguration`'s old layout, the hazard 1.9.4's release
    document describes, so this test has no red result. On v1.9.4 a local write names no phase at all.
  - Here the handoff names the phase the held write was in when it left.
- The rest are new API (`aPhaseNamedWithoutAHopReachesTheStallReport`, `aBoundedOutboxListingDoesNotWaitForTheOperationGate`,
  `InstantPendingMutationsPageTests`), so they have no red run.

The red run also showed a test bug: once the FIFO has a reader, the write fails at `flock`, which refuses a FIFO, so no
line arrives. `bb598182` makes the test wait for the write error instead; its assertion that `record(...)` returns at
once is unchanged.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract


Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

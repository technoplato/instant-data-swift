# Instant Swift Data 1.9.47

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `6fb8b654` (red `464d057f`, green `6fb8b654`; plan amendment `962e8a10`). It carries 1.9.46.

## Before you upgrade

Nothing new: 1.9.47 adds no migration and changes no stored format. 1.9.41's warning stands: a store 1.9.40 or later
opened cannot be used by an older build, so an app that keeps its store across installs must delete its data before an
older build is installed over it.

`InstantProgressiveMediaRow` gains a case, `.streamProgress`. A `switch` over it that lists every case needs the new
one; `mutation` and `Storage.live` handle it.

## Release focus

**A progressive media stream's later writes carry only what changes** (#1253). A stream's row restated its 13 fields
every segment where four change: on one device that was 59% of the fact records its store's write-ahead log held in a
quiet 72 s of recording, each field a retract and an insert in the outbox body, a write-key row in two b-trees and a
fact in the echo. Now the stream's first write creates the whole row (`upsertMutation`) and each later one, a
segment's or the finished one, is `InstantProgressiveMediaRow.streamProgress`, whose `progressMutation` sets its state,
segment count, duration and update time. A stream has one writer and the other eight fields never change after the
first write; a replayed write sets the same values, so it stays harmless.

Measured on the same store (laptop, debug; each write after another row, so neither replaces the stream's unsent
write): a stream write's local save 29 -> 17 pages (-41%), its outbox body 8,627 -> 3,515 bytes (-59%).

## What stays the same

The row the server and every reader see after each write is the same (`aStreamsLaterWriteCarriesOnlyWhatChanges`
reads it back). Files are still stored before their rows; rows are still written in order. A partial write is never an
immediate-tail supersession, so the stream's creation row always stays in the outbox until it is sent.

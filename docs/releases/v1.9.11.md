# Instant Swift Data 1.9.11

Status: published by direct maintainer authorization, typed on 2026-10-15: "Do 704" (08:38 EDT), under the standing
rule for performance work, typed 2026-10-14: "We want to make sure that we're not changing any functionality, but
improving performance". The checks that ran are below, on `a6fa6662`, the last code commit.

## Release focus

The live-query cache's ownership table stops repeating each query's whole key on every row (#704).

Since migration 0011, `instant_live_query_triples` recorded which stored live-query result owns which fact, one row per
(result, entity, attribute, value), and every row carried `query_key`: the whole InstaQL JSON of its query. A list
query with its fields, includes and page cursor is 1.7 KB on average and up to 4.3 KB. The table was a rowid table, so
its primary key was a second b-tree holding every column again, and the identity index held the key a third time; an
index cell keeps about 1 KB on a 4 KB page, so most index entries spilled to an overflow page of their own. On a store
copied from a device, 32,555 such rows holding 3.7 MB of values took 328.9 MB.

Now each stored result has an integer id, and an ownership row names its result by that id. Every read answers what it
answered before; only the bytes change. The design is ADR 0020 (`docs/adr/0020-compact-live-query-ownership.md`).

## What changed

1. **The layout.** `instant_live_query_results` gains `query_id INTEGER PRIMARY KEY` (its rowid); `query_key` stays,
   `UNIQUE`. Results are written by upsert (`ON CONFLICT(query_key) DO UPDATE`), so a result keeps its id for as long as
   it is stored. `instant_live_query_triples` is `WITHOUT ROWID` with `PRIMARY KEY (query_id, entity_id, attribute_id,
   value_json)` and a foreign key to the result's id, `ON DELETE CASCADE`; the identity index is `(entity_id,
   attribute_id, value_json, query_id)`. The duplicate primary-key b-tree is gone.
2. **The statements.** Every statement that reads or writes ownership names `query_id`: storing, refreshing,
   reconciling and dropping a result; #441's newest server stamp and #445's newest server values; whether another
   result owns a fact (the excluded keys map to their stored ids; a key with no stored result owns no rows); the
   application-migration scan; and the entity repair. Each returns the same rows as the statement it replaces.
3. **The conversion.** A new store's 0011 creates these tables. A store that ran 0011 before converts once, at
   bootstrap, decided by the ownership table's columns (not the ledger, since fixtures and restores can recreate the old
   tables), in one `BEGIN IMMEDIATE` transaction: results copied in key order; ownership rows staged with their result's
   id in a temporary table; the old ownership table dropped, then the old results table; the new tables created under
   their own names; the identity index; ledger row `0026_live_query_compact_ownership`; a startup-trace phase
   (`sqlite.live-query-ownership-compaction`) and a notice (`sqlite.live-query-ownership.compacted`: rows, results,
   rows without a result, milliseconds). A process that dies during it leaves the old tables as they were, and the next
   open converts from the start. A row whose result is missing (which the foreign key forbids) is counted, not copied.
4. **What stays the same.** The outbox, the triples, the metadata and the query cache are not touched, and no revision
   is bumped. The freed pages go to SQLite's freelist and are reused by later writes; the file does not shrink (a
   `VACUUM` is not part of this release).

No public API changes.

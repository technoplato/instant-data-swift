## 1.1.2 — A stalled outbox no longer hides itself

Scribe is a live transcription app built on this library. It records continuously
on an iPhone, an iPad and a Mac, all writing into one shared Instant app, and it
expects a recording started on one device to show up on the others.

On August 1st it wasn't. The Mac sat on "Loading recordings…" with an empty
sidebar. The iPhone reported "no audio file" for most recordings. Nothing looked
broken from the inside: recording worked, transcripts scrolled, and every write
reported success, because every write *was* succeeding — locally.

The first theory was that the server was rejecting the writes. That turned out to
be wrong, and wrong in an instructive way: a test that replayed the writes through
the **admin SDK** was accepted every time, which seemed to exonerate the server.
It didn't. The admin SDK creates unknown attributes on demand, so it could never
reproduce what the *client* does, which is resolve attribute names against the
schema the server sends at handshake and refuse to send anything it can't resolve.
The canary had quietly repaired the very condition it was meant to detect.

What actually cracked it was opening the devices' own databases. The iPad's outbox
held 691 pending mutations and one failed one, and that failed row had stored its
own explanation: `Could not resolve 'recordingAttachments/analysisCaptureContextJSON'
from the attrs returned by init-ok`. An attribute existed in the app's schema file
but had never been pushed to the server. The iPhone was worse — 2,775 pending and
463 permanently failed, going back nine days, across four distinct causes. And the
iPad's stored connection state read `errored`, with
`run Instant live query: Timed out after 10000ms waiting for Instant live transport`.

### What was wrong

Three separate defects compounded into one silent outage.

A backlog was flushed in a single burst. Every time a session opened, all 691
queued mutations were written to the transport at once, which starved that same
session's own queries until they hit their ten-second timeout. The connection then
errored and closed, and on reconnect the same burst happened again. The queue could
never drain, and it grew with every recording.

A mutation the server couldn't accept was quarantined permanently. Only timeouts
and service-unavailable errors were ever retried. A write rejected because the
server was missing an attribute or a permission rule was marked failed forever —
so even after the schema was deployed, those 464 mutations, including audio
attachment metadata, would never have been delivered.

None of it was visible. Recording the quarantine could itself fail and, when it
did, it tore down a perfectly healthy connection. Mutations sent but never
acknowledged stayed marked in-flight for the life of the session and were skipped
on every subsequent flush. Nothing was logged, nothing was reported, and the only
record of the failure was a string inside a SQLite file on a phone.

### What changed

Each flush is bounded to 50 mutations, and a delivery pass drains in bounded
batches with a pause between them so acknowledgements can land. A backlog now
converges instead of choking the connection it depends on.

Mutations the server never acknowledges are reclaimed after 10 seconds and retried,
rather than being blocked for the lifetime of the session.

Failures a deployment can fix — an unresolvable attribute, a permission denial —
are retried on a fresh session, which re-reads the server's attributes and rules.
Work queued while the server was behind now lands once the deployment does.

Quarantined mutations, unacknowledged writes and deep backlogs are reported through
Point-Free's IssueReporting, so they are loud in development builds and silent in
production. Recording a quarantine can no longer close a healthy connection.

Deliberately not changed: the retry is not unbounded, and a genuinely undeliverable
mutation is still quarantined rather than retried forever. The 10-second budget is
short on purpose — when a device is online, a write that hasn't been acknowledged in
ten seconds is a problem to surface, not a slow network to wait out.

### How this was verified

Three regression tests in `InstantOutboxDeliveryStallTests.swift` reconstruct the
failure: an undeliverable mutation must not block the writes queued behind it, a
deep backlog must flush in bounded batches, and a mutation quarantined for a missing
attribute must deliver once that attribute is deployed. The batching test was run
with the fix reverted and confirmed to fail, then restored and confirmed to pass —
compilation and a green suite are prerequisites, not evidence.

47 tests across the reactor-parity, mutation-lifecycle, simple-E2E and
infinite-query suites pass unchanged, which is the blast radius for the delivery
path.

Still unproven: the field devices have not yet drained. That needs a build of the
consuming app on the affected hardware, and it is the next thing to check rather
than something this release can claim.

### Upgrading

No API changes; no migration. Pin to `1.1.2` and rebuild — a consumer still pinned
to `1.1.1` has none of this, which is worth checking before concluding a backlog
hasn't recovered.

If you have devices with a stalled queue, deploy your schema and permissions first.
The recovery path only helps once the server can actually accept the writes that
were rejected.

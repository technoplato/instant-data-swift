# Instant Swift Data 1.9.81

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (the landing of `agent/claude/replay-2028` and this
record): the only source change on `main` since `v1.9.80` is this release's. It carries 1.9.80.

## Before you upgrade

No public API change, no storage change, no schema change. Three behaviours change:

- The server apply's watermark keeps an accepted write in the outbox while an older write that sets one of its slots is
  still open (neither failed nor proven), and prunes it at the first watermark after that write resolves. While it is
  kept, its optimistic overlay stays above the older write's, so the device shows the newer value.
- A replay's refusal waits (parked, `outbox.mutation.refusal-parked`) behind a later write that covers it whether that
  write is in flight or still waiting its turn; before, only a write in flight counted.
- A refusal resolved by coverage records the server's verdict, so the one-write-at-a-time delivery that follows a
  transient server error ends there, as it does on an acceptance (`InstantMutationServerErrorBackoff.recordAcceptance`
  becomes `recordVerdict`).

A write refused only because a newer write of this device holds every slot it sets is now resolved as accepted
(`outbox.mutation.refusal-superseded`) or never offered again, instead of failing as
`outbox.mutation.server-error-terminal` and `outbox.mutation.refused-write`.

## Release focus

**A replayed write the server refuses because a newer write of this device already landed is not a refusal** (#2028;
plan `51285997` and amendment `74496606`, red `586649b4` and `4073aa6f`, green `362fdbbf` and `2881ae5b`, measure
`555dfff6`).

- Before: a consuming app's device on a cellular network that dropped every few minutes (one build, 2026-11-07
  17:47-19:24) recorded 16 writes as refused for good, each a replay of an unanswered write (`Permission denied: not
  perms-pass?`): 9 of a media-stream row, 6 of route chunks, 1 of a sound. The app reported data as refused. An admin
  read of the server's rows found every one of those rows at a newer `updatedAtMs` than the refused write: a route chunk refused at 52, 62 and 72 samples is held at 128
  samples, sealed; a media-stream row refused at 725-733 segments is held at 1,336. The app's rules refuse a write that
  moves `updatedAtMs` back, so the replay of an older write that arrives after a newer one is refused, as it should be:
  nothing was lost.
- Item 3 (library-78) already resolves such a refusal as accepted when later accepted writes of this device cover every
  slot it sets, and does not offer such a write again (`laterWriteCoverageWithoutTransaction`). It reads those writes
  from the outbox. The server apply's watermark prune had deleted them: a write is offered again after its first offer
  may have been applied (a lost answer, a transient error, an expired claim), and by then the newer write's answer and
  the server's next result, whose watermark passes it, had arrived. In the same minute on the same device
  (19:24:49-52), four replay refusals resolved as superseded because their covering writes were still in the outbox.
- Now the watermark keeps an accepted write while an older write that sets one of its slots is open: one guard
  (`keepsEvidenceForAnOlderOpenWrite`) in both prune predicates, the server-apply reduction's and the plan's, so they
  agree on what is pruned. In order, an older write is answered before a newer one, so a write is kept only after an
  answer was lost or came out of order. A refusal that later writes cover only in part still fails, as do a first
  offer's refusal of a write no accepted write covers and every other refusal.
- The flapping-network simulation found a second path on both trees: the server timed the older write out and applied
  the newer one, the socket dropped before the newer write's answer, and after the transient error the outbox offers
  one write at a time, so on the next connection the older write went out alone and its refusal arrived while the newer
  write waited its turn. Item 3 counted a later write not yet answered only while in flight, so the refusal stood. Now
  such a write counts too, and the refusal it parks records the server's verdict: the parked refusal holds its claim,
  and one write at a time would never send the covering write. On the unfixed tree the same test showed the liveness
  side of it: a refusal parked to wait for a server result held the only slot, and nothing else was sent until the wait
  ended.
- A suspected stall was tested and ruled out: a covering write that meets a transient error while a refusal is parked
  behind it is sent again by one write at a time, and the refusal resolves (`b919b8b6`'s test passes without a change).
- Upstream `Reactor.js` re-sends every unanswered mutation after a reconnect (`_flushPendingMessages`) and drops a
  refused one as an error (`_handleMutationError`); Instant's server applies every transact it receives, without
  deduplicating a client-event-id (`session.clj`). Upstream has no supersession, so this release keeps Swift's.

## Not run

The release gate `validation/run-performance-gate.sh live`, nor its Swift→TypeScript and TypeScript→Swift boundary
checks (the maintainer's authorization quoted above): this release changes which accepted writes the watermark prunes,
not what a write sends, stores or delivers. The guard is one correlated `EXISTS` per prunable row over the write-key
index; no memory or throughput number was measured for it. The consuming app's after-measurement (refused writes per
dropped connection on the device, with the network's state) waits for the first build that pins this release.

# Instant Swift Data 1.9.46

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `b4ee694b` (red `3332dc8a`, green `b4ee694b`; plan `6d903e63`). It carries 1.9.45.

## Before you upgrade

Nothing new: 1.9.46 adds no migration and changes no stored format. 1.9.41's warning stands: a store 1.9.40 or later
opened cannot be used by an older build, so an app that keeps its store across installs must delete its data before an
older build is installed over it.

## Release focus

**SQLite's own counters, per store call and per kind of file** (#1245). On one device a recording hour wrote 3.31 GB,
and 0.80 GB of it no meter named: `InstantStorageWriteMeter` (#1007) counts the pages each store call writes to the
write-ahead log, not what a checkpoint copies into the database file, the temporary database or its journal, and it
said nothing of how a call's statements did their work.

- **`InstantSQLiteFileMeter`**: a pass-through VFS (`instant-metered`) in front of the system's `unix` VFS. The store's
  writer and its read connections open through it, so SQLite's own files for them count: per kind of file (database,
  write-ahead log, rollback journal, statement journal, temporary database and its journal, transient sort files) the
  bytes and calls written and read, the syncs and full syncs with their time, and the truncates. Each call goes to the
  system's file unchanged; the meter adds to its kind's counts under one lock and allocates nothing.
  `InstantSQLiteFileMeter.snapshot()` returns them; `InstantSQLiteFileSnapshot.subtracting(_:)` gives an interval. In
  WAL mode only a checkpoint writes the database file, so its kind's bytes are the checkpoints' copies.
- **`InstantStorageWriteSnapshot.Measure.sqlite`** (`InstantSQLiteCounters`): for each store call, its statements'
  virtual-machine steps, full-scan steps, sorts, rows put into automatic indexes and re-prepares
  (`sqlite3_stmt_status`), and its page cache's hits, misses and spills (`sqlite3_db_status`). The statement cache reads
  a statement's counters with reset when it takes the statement back, so a reused statement counts each use once (two
  test metrics that summed a reused statement's cumulative sorts and full-scan steps now sum each use's).

## What stays the same

Every connection's files, locks and shared memory are the system VFS's: the meter only forwards. A test that sets
`connectionVFSForTesting` still opens the writer through its own VFS. The write meter's pages and transactions, the
`persistence.write-summary` line and every public type keep their meaning; `Measure`'s initializer gains a defaulted
`sqlite` parameter.

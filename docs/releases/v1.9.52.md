# Instant Swift Data 1.9.52

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Cut at `00b245bc` (#1383: red `17149a7e`, the stuck-frame guard `cda06974`, green `00b245bc`). It carries 1.9.51.

## Before you upgrade

No migration, no stored format change, no public API change. `outbox.mutation.ack-deadline-deferral-exhausted` now
fires when a frame has made no server-apply progress for the limit, and carries `serverApplyProgress`.

## Release focus

**A slow server frame that keeps working keeps its acknowledgement claims** (#1383). The live receive loop applies
frames in order, so a transaction's acknowledgement waits behind the frame before it; the runtime defers the claims'
deadlines while a frame is applied, the way upstream `Reactor.js` never fires a mutation timer mid-frame (#296). The
deferral had a bound, 120 s from the frame's first sighting, meant to treat a stuck frame as stuck. One device relaunched
with 4,344 pending writes, and every frame its query registrations brought back (`add-query-ok`) peeled and replayed the
queue: 30 passed the bound within ten minutes, each expiry reclaimed the claims and replaced the live session, the
replacement dropped the frame being applied and what was queued behind it, so the rebase never finished, nothing was
pruned, and the next session started the same rebase again. Nothing was accepted in those ten minutes.

Now the server apply reports progress (each attempt, each staged body page, the commit), and the deferral times a frame
from its last progress: a frame that keeps working keeps its claims and its session, however long it takes, and a frame
that reports nothing for 120 s is treated as stuck, as before.

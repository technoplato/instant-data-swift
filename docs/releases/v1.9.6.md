## Release focus

A stored file downloads to a destination file, streaming, instead of into memory (#454, P0), and the diagnostics file
is written in batches with an fsync at most once a second (#473). On an iPad on Scribe 0.1 (83), playing back
Recording 039 downloaded its 1,964,275,244-byte WAV into memory, cached a copy and wrote it again: a 4,384 MB footprint
and 3.9 GB more on disk. The freeze report on Recording 185 found that 1.9.5 still fsynced every Instant log line, on
the writer queue, behind one process-wide file lock.

## What changed

1. **`downloadStoredFile(id:name:to:)` streams a stored file to a destination (#454, phone-perf).** On
   `InstantRuntime` and `InstantSwiftDataClient`. It streams to a temporary file with a `URLSession` download task and
   moves it into place, replacing a file there. The library keeps no copy, so the destination holds the only one; a
   file the library already holds is copied file to file (an APFS clone); a failed download leaves the destination as
   it was and no temporary file. `InstantStorageHTTPClient.downloadToFile` and the transport's file downloads are new;
   a client built from `send` writes what `send` returned, so custom clients keep working. `storedFileContents(id:name:)`
   is unchanged, for small files.
2. **The diagnostics file is written in batches (#473).** Each run of waiting lines for one file is written under one
   open and one `flock`, rotating before a line that would take the file past its bound (the retired file is fsynced
   first), and a written file is fsynced at most once a second, or at `flush()`. A line survives an app crash once it is
   in the kernel's cache; only a power loss inside that second can lose it.

## For users of the library

- **API:** additive. New: `downloadStoredFile(id:name:to:)` on the runtime and the client;
  `InstantStorageHTTPClient.downloadToFile`; transport initializers that take file downloads.
- **Behavior:**
  - Use `downloadStoredFile(id:name:to:)` for large files; `storedFileContents(id:name:)` still returns `Data`.
  - Log lines reach the disk at most a second after the kernel has them; `flush()` syncs at once.
- **Storage:** no schema or data migration.
- **Dependencies:** unchanged from 1.9.5.

## Red and green

Both changes add API the old code lacks (`downloadStoredFile`, the diagnostics write counts), so their tests have no
red run on 1.9.5. `InstantStoredFileDownloadTests` also pins the defect on the old path: `storedFileContents` holds
every byte and keeps a cached copy. `InstantDiagnosticsTests.burstsAreBatched`: 200 lines cost at most 3 fsyncs, and
every line arrives in order.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic

```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

# Instant Swift Data 1.9.43

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `13dbc935` (its only code commit since 1.9.42). It carries 1.9.42.

## Before you upgrade

Nothing new: 1.9.43 adds no migration and changes no stored format. 1.9.41's warning stands: a store 1.9.40 or later
opened cannot be used by an older build, so an app that keeps its store across installs must delete its data before an
older build is installed over it.

## Release focus

**A stored file's copy is found in the store's own files folder, wherever the folder moved** (#1227; red `c34bb499`,
green `13dbc935`). A record of a copy keeps the absolute path the copy had when it was made, and iOS moves an app's data
container, with the store's folder, when it installs an update. On one device 3,844 records (25.44 GB of copies) named
14 earlier containers while every copy sat at the same place in the current one, the same size. So
`evictStoredFiles(ids:)` answered `.kept(.notHeld)` for every copy, `readStoredFileContents` failed, and
`deleteStoredFile` removed the record and left the copy on disk; a consuming app's cleanup of the copies 1.9.13 and
earlier kept (#959) removed nothing. `loadStoredFiles(appID:)` and `loadStoredFile(appID:fileID:)`, which every read,
eviction, download and delete goes through, now place a held copy whose path is not already in the store's files folder
by its path's last three components (`<app>/<file>/<name>`, the only layout the store writes). A path already in the
folder costs a prefix check.

## What stays the same

No public API change; the stored JSON keeps the path it had; a record without a copy stays without one. A copy that is
truly gone still reads as before: a read reports the missing copy loudly, and eviction keeps the record.

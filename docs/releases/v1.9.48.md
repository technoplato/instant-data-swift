# Instant Swift Data 1.9.48

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `68fa970c` (red `fdd08d36`, green `792c5411`, the gate-held line's attribute `68fa970c`; plan
`8e2e0cef`). It carries 1.9.47.

## Before you upgrade

Nothing new: 1.9.48 adds no migration and changes no stored format or public API. 1.9.41's warning stands: a store
1.9.40 or later opened cannot be used by an older build, so an app that keeps its store across installs must delete its
data before an older build is installed over it. 1.9.47's note stands too: `InstantProgressiveMediaRow` has the
`.streamProgress` case.

## Release focus

**A server frame no longer replays the whole outbox when a pending write named a link the server issued an id for**
(#1270). One device's outbox grew from 0-1 to 2,316 pending writes in two hours of recording: 49 of its 51 slow server
applies said `full rebase: changesShadowedFact`, each peeling and replaying 1,073-2,093 pending writes for one frame
and holding the operation gate 0.7-5.3 s, so writes were accepted 2-14 a minute while recording made 45-85.

Its screenshots set the recording's `previewImage` link under the link's name, `recordings/previewImage`; the store and
every server frame hold the link under the attribute's id, which the server issued. The outbox keeps a write's keys
under the names the write used. The server apply's reduction (#296) looked the slot's pending writers up by the id,
found none, saw the store not showing the server's value (it showed the newest pending screenshot), and declined into
the whole-component rebase; the replay put the pending value back, so every later frame restating the recording
declined the same way, and its cost grew with the queue.

Now the reduction looks a slot's writers up, and reads their values, under every name a write can give the slot
(`AttributeStore.forwardWriteNames(of:)`: the attribute's id and its forward identity). The same blind spot in the
refused-write splice is gone, so removing a refused screenshot write no longer forces the whole-component rebase.

Measured on the laptop (debug, Xcode 27 beta, arm64, machine load 40-100), red `fdd08d36`, green `792c5411`:

| | Before (1.9.47) | After (1.9.48) |
| --- | --- | --- |
| One frame restating the recording, fast-drain fixture in the device's write shape, 105 / 1,001 / 2,002 pending | 0.25 / 2.8 / 7.0 s, every pending write replayed | 4-7 / 5-8 / 7-9 ms, none replayed |
| Draining 2,002 pending writes with no new writes | 60 accepted writes took 410 s, 118,350 writes replayed | the whole queue in 24.7 s applying, 0 replayed |
| A recording minute (70 writes) on 2,002 pending, the server accepting as fast as frames apply | the whole-component rebase the device ran: 9 accepted, 2,002 -> 2,063 | 2,072 accepted, 2,002 -> 7 |
| The device's own store (1,241 pending) through the phone-replay gate | 42-44 s per frame, 1,067-1,117 writes replayed, every frame declined on the link's id | 1,241 -> 0 in 9.9 s, 78 frames, none rebased; all 473 touched entities match the model server |

The gate-held line now also names the attribute that declined a frame (`declinedAttributeID`); before, only a
debug-level line did, and finding this took a copy of the device's store.

## What stays the same

Every write is still sent, in order, with the same operations; nothing is merged or dropped. The reduced apply leaves
what the whole-component rebase leaves: the differential test runs the attachment shape through randomized
interleavings of acceptances, frames, refusals, lost acknowledgements, replays and another device's writes, and
compares both devices' stores and outboxes after every step (seeds 31-36 in every run; over 40 more seeds, 38 match and
the two that do not are #1275, under "Known"). A slot written under one name only (every scalar, every
link whose id is its name) is looked up exactly as before.

## Known

- **#1275**: a local write can lose last-write-wins to a pending value whose stamp is later than the device clock. Both
  paths have it; the whole-component rebase replays every pending write on the next frame and so shows the newest local
  write again at once, while the reduced apply does so when a frame next restates that slot (or the write's own echo
  arrives). With this release more frames take the reduced apply, so a hidden write can stay hidden a little longer.
  It needs a resident stamp after the device clock: the test fixture's server manufactures one (its clock jumps a
  million milliseconds per foreign write and it keeps no first-set time), Instant's server keeps a slot's first-set time,
  so on a device it needs server stamps ahead of the device's clock (inference: rare). Upstream's store always replaces a
  single-valued slot with an optimistic write.

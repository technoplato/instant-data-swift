## Release focus

A page of a list with includes skips a change it cannot show, and judging that costs less than refreshing (#1007).

A paged list keeps one observer per page (an infinite query's chunks). Each page of a recordings list shows its
recordings and, for each, a bounded include of its newest lines and attachments. Before this release a plan with
includes refreshed on every change to any namespace it reads, so a new line, a duration heartbeat or an attachment of
the one recording being written re-materialized every page of the list, though only the page that shows the recording
could change.

1. **A page with includes skips a change it cannot show** (red `3c2c2023`, green `b7e619bf`). For a verified plan whose
   includes all have sub-queries and whose field paths are all its own namespaces', the page is its root namespace's
   ordered set, windowed, and for each shown root the included entities its links reach. When no changed entity is
   shown at any depth, none is linked to a shown entity before or after the change, and none moves in or out of the root
   set or along its order, the observer skips. A link's change marks both of its ends changed, and a delete marks every
   entity linked to the deleted one, so a link added to, removed from or held by a shown entity always refreshes.
   `TripleIndexes.hasLink` answers the link question from each link's smaller side.
2. **Placing an entity in a result set reads only the fields the plan names** (red `ffbd23d9`, green `023ff4af`). The
   check behind every skip (#654 and item 1) read the entity's whole snapshot, and a recording's whole snapshot
   materializes every link set it holds: thousands of refs, sorted, on every read, twice per page per publication. Item
   1 alone therefore cost more than the refreshes it saved. `resultSetMembership` now reads the values of the plan's
   filter and order fields from the entity's facts, as the whole snapshot reads them, and is nil exactly when the whole
   snapshot is; a plan with a dotted field keeps reading the whole snapshot.

## What stays the same

No public API, schema or migration change. Every observer holds and is handed exactly what a fresh materialization of
its plan returns after every change (the random tests below check it after every step); only the observers that cannot
change stop re-running their queries. Delivery, acknowledgements, server applies and the outbox are unchanged, so a
local write reaches the server, and a server change reaches its observers, no later than before.

## Not changed here

- The live-query prune still copies the whole store, and when it removes orphaned facts it rebuilds every index and
  un-verifies every observer, so the next publication re-materializes them all (#654, #1007).
- A plan with a bare include or a dotted field path still refreshes on every change to its namespaces.

# Instant Swift Data 1.9.39

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `ba733bd9`; its last code commit is `3e787d2d`. It carries 1.9.38.

## Release focus

Work that held Instant's operation gate, or the frame applier, for a whole result moves out of it, and three costs of a
page refresh fall. Each fix is a red commit, then a green one:

1. **An observer's registration holds the gate only to record itself** (#1131, #1135; red `5a7edf91`, green
   `0b0650d9`). Registering a live query held the operation gate across its `add-query` socket send (5.0-7.8 s holds on
   builds 121-126, about 11 callers queued) and across the reload of its closed stored result. The live session now
   records a registration under the gate, where the prune reads the open queries, and sends it after the gate, guarded
   by the socket generation it was recorded on; the infinite query's chunk and the one-shot read send the same way. A
   closed result is read and decoded on the read connection before the gate, and its stored JSON moves back inside
   SQLite instead of being encoded again.
2. **A closed result loads back in bounded holds** (#1131; red `d55e72fd`, green `ffd14777`). The reload of a closed
   result commits in chunks of at most 2,048 facts, each its own hold, under a per-key registration lease: the prune
   keeps a reloading result, a second observer of the same query waits for the first one's registration instead of
   answering from a half-loaded result, and a chunk stops once a server answer replaced the row.
3. **An observation that ends before its add-query went out sends it first** (#1131; red `fb3bc407`, green
   `821e592a`). With the send after the gate, an infinite query's frozen chunk evicted at once put `remove-query` alone
   on the wire; the registration now records the generation whose add-query it owes, and the unregistration sends it
   first, so the wire reads add then remove, as upstream `Reactor.js`'s synchronous `ws.send` at subscription makes it.
4. **The cadence prune runs in a task of its own** (#1129, first slice; red `4278f2f8`, green `e1ea434c`). It ran inside
   the frame applier while that held the server-apply gate, so every frame behind waited for the whole prune; it now
   runs after the refresh that asked for it, coalesced, each batch still queueing for the operation gate at background
   priority. A batch still takes a whole result; bounding it is the next slice of #1129.
5. **A line linked to a long recording copies one shard of its link set** (#1152; red `ccdbc47b`, green `33c5c042`):
   a many-cardinality slot keeps its values in a `ShardedDictionary` with a small mode, and an insert writes a derived
   index shape only when it changes.
6. **A page refresh costs less of the page** (#1147, steps 1-3): the nested-limit pass of a page with no nested include
   builds no map of the schema or the page (red `79707ad5`, green `a9751099`); hydrating a page's deferred text looks
   up only the configured attributes (red `63b65c80`, green `553cb332`); a received frame's arrays are sized once,
   escapes reuse one buffer and a frame's repeated ids share one copy (red `40280360`, green `3e787d2d`).

Test and harness commits with them: `496ff990` (the memory exercises' allocation sites), `a42ea364` (one-thread
allocation counts take turns), `bc7cf4a4` (the memory replay's smoke test runs in the measurement pass, alone).

## Measured

On #1072's real-size fixture (version 3: integer transaction ids), Mac mini M4, release:

- **Observer registration** (#1074's `observers` exercise, every socket send delayed 150 ms; main `ed161097` before,
  `e1ea434c` after): the registration's hold p50 154.24 -> 0.11 ms, worst 169.24 -> 1.68 ms; a write's wait for the
  gate there p50 76.86 -> 0.00 ms. #1131's first criterion (under 5 ms) is met.
- **The `$files` list's registration** (`server-apply` exercise, 75,640 facts reloaded): the registration's own hold
  1,616.70 -> 23.74 ms; the reload's 38 holds p50 37.51 ms, worst 78.77 ms; a write's worst wait in that window
  1,524.28 -> 677.16 ms, behind the list's first answer's plan (#1128, 660 ms, next). #1131's second criterion (under
  100 ms) is met.
- **Launch** (`launch` exercise, 62 observers while the socket connects): first emission p50 78.90 -> 72.78 ms, p99
  97.57 -> 88.96 ms.
- **The cadence prune** (`prune-inline` exercise): the refresh queued behind it applied after 1,723.23 ms before and
  1,618.05 ms after: it no longer waits for the whole prune, but the closed `$files` list is still one batch of
  1,705 ms (`prune` exercise), so it waits for that batch. #1129's criterion is not met by this slice.
- **#1152** (E04, fix-memory-1075's measurement, same-day before on main `8cfbbbd6`): a final line on the 2,318-line
  recording 7,255 -> 6,636 KB, +6.9% -> +2.8% over a new recording (criterion: within 5%).
- **#1147** (E03, fix-memory-1075's measurement): a 64-line refresh with one line changed 23,947 -> 16,280 allocations
  and 22,769 -> 12,236 KB; the whole `$files` answer's decode 548,414 -> 160,779 allocations, 58.9 -> 27.8 MB.

## What stays the same

No schema, migration or public API change. A registration still lands in the live session before its observation's
first answer; a reconnect's init still sends every registered query; the wire still reads add-query before
remove-query for every observation. A reopened query still answers from its stored result before the server does, the
prune still unloads the same results and drops the same facts, and the cadence prune still runs every 64th refresh with
results.

## Checks

- **Red, then green** (Mac mini M4, Xcode 27 beta, release): `InstantObserverRegistrationGateTests` (each red fails as
  designed: the gate held across the send and the read, the reload in one hold, the wire's remove-query alone; each
  green passes), `InstantPruneOffTheApplierTests` (red fails 2/2, green passes). With them, 260 tests of the reload,
  registration, prune, live transport, connection survival, Reactor parity, infinite query, nested limit and local read
  suites pass in release, except `explicitFlushReclaimRetiresTheOfferedLiveGeneration`, a `withKnownIssue` that release
  builds cannot record (IssueReporting records Swift Testing issues only under `#if DEBUG`).
- **The real-size budgets** (release, `INSTANT_REAL_SIZE_BUDGETS=1`): `RealSizeBudgetTests` passes twice on
  `e1ea434c` with 13 known issues, as on 1.9.38, and once more on `ba733bd9`, the release's code, with the same 13.
- **The whole `InstantSwiftDataCoreTests` bundle** with `scripts/known-failing-tests.sh run` and `compare` on a copy of
  `ba733bd9` (Mac mini, debug, the open-file limit raised to 4,096): 1,478 tests, 3 failing. One is listed
  (`binaryCodecRemovesBase64AndJSONCPU`, idle 2/3). Two are new and are #1147's cost tests:
  `RefreshCostTests/aPageWithNoNestedIncludePassesThroughTheNestedLimitPass()` (855,703 bytes with 2,283 attributes
  against 506,585 with 16, bound 4,096 more) and `RefreshCostTests/hydratingAnEmissionDoesNotMapTheSchema()` (1,376,859
  against 330,089): their bounds hold in release builds, where they were written and pass, and not in debug builds,
  which allocate more for the same work; they are fix-memory-1075's to gate to optimized builds, as `RealSizeBudgetTests`
  is. The first run of the bundle, at the ssh session's open-file limit of 256, failed 34 tests, 30 of them with "unable
  to open database file": the bundle's parallel stores, each now with its read connection once an observer registers
  (#1131), outran 256 descriptors; at 4,096 they pass.

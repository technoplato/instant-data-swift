Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (merge `d3ed3c50` of the lane's verified head `7773cfa5`

## Before you upgrade

No public API change, no storage change. `transact(_:createdAt:source:)` with `createdAt: nil` (the default) now takes
its outbox time under the operation gate on every path (#1648); a non-nil time is kept exactly, as before.

## Release focus

**A live write is claimed by its own save** (#653; red `096246e4`, green `9691ee4d`, fixes `cdca7eb3`, `45f92924`,
`2a3c78b1`, test `30a344aa`; session red `c208d640`, green `416ac3b1`; attributes red `3e937899`, green `7773cfa5`).

- While the connection is open, the pump runs no pass, no server error pauses delivery and nothing is ready ahead of
  it, a write's save claims it in the same SQLite transaction (its row written once, already claimed, with the
  projected body's exact size and wire fingerprint) and queues it on the pump under the operation gate, so windows go
  out in save order, as `Reactor.js` `pushOps` sends a mutation as it records it. The claim turn it replaces took the
  operation gate, read the write back, decoded and fingerprinted it again: 3.06 ms a claim on the phone (the consuming
  app's builds 248-249), more than the save.
- A window claimed at save goes out only on the live session generation it was claimed for: when that session ends
  first, the disconnect puts older writes back and the next pass sends them first.
- A claim's visible-write filter reads its writes' attributes from a decoded copy kept while they are unchanged; each
  claim read and decoded them one statement per attribute (36 of the claim at save's 136 samples).

**The delivery claim encodes a write less** (#1517; red `db5e4365`, green `d5f4a7d7`): the claimed row's first wire
fingerprint, always replaced before commit, is gone, and an unsubstituted projection is not built and encoded a second
time. Three claimed writes: 6 -> 3 projected-body encodes, 6 -> 3 wire fingerprints.

**A write's receipt is found by its stored bytes** (#1523; red `d6b239f4`, green `1ef4aa2f`, `037012ec`, `bca8111b`):
the save, the claim and the acknowledgement find a write's kept receipt fingerprint by the SHA-256 of its body's stored
bytes instead of hashing its transaction and rollback. Two writes: 6 -> 0 input hashes. Known cost, fixed on the lane
branch (`9b792550`, `6ff60ee9`) and coming in the next release once its job passes: the server apply's body pages and
staging still look the fingerprint up by the write's inputs, which the save no longer keys it by, so a write an echo
replays is fingerprinted again there and, when the echo changed its body, at its acknowledgement too (the
acknowledgement 439.7 -> 628.7 us a call below).

**One sleeping deadline wake** (#1142; red `21c16cfb`, green `0adffc2e`, test `ed0a2f00`): each send started a task
sleeping until its acknowledgement deadline (about 6 s) and each acknowledgement cancelled it; the wake keeps one task
that sleeps on to the deadline that still stands. Six acknowledged writes: 6 tasks -> at most 2.

**Two writes made in the same millisecond go out in the order they were made** (#1648; reds `4b6117a5` `5535f452`,
green `3ae5585b`, fix `74fea3ae`, tests `2cf4e1d8` `ba690a53`, merge `af35bc58`, fix `94a77045`). The typed transact,
`transact(operations:)` and Send Again read the clock before the operation gate and passed it on, so two writes in one
millisecond tied and went out in transaction-id order. A write's step that its own later step overwrote is not
restamped to win (`94a77045`): a write that sets a slot twice, as the todo example's seed sets each todo's
`isCompleted` in its upsert and again in its completion, is prepared once, where it was restamped and prepared a second
time (the seed's actor hops 8 -> 7, pinned in `cd8be798`).

## Measured

Mac mini M4, build.sh job `1797-c-release-candidate` (2026-11-04 22:19-23:05 EST), release builds of v1.9.67
(`49780127`) and of `7773cfa5` in the same job, `ContentionExercises.recording` (150 s on the real-size store, 225
writes; the energy meter's CPU per operation):

| | v1.9.67 | 7773cfa5 |
|---|---|---|
| save + claim, a write | 5,523.4 us | 4,208.3 us (-23.8%) |
| `outboxClaim` | 2,812.5 us x 225 | no claim turns |
| `localSave` (now with its claim) | 2,710.9 us | 4,208.3 us |
| `acknowledgement` | 439.7 us | 628.7 us (+43%, the known cost above) |
| write side: save, claim, acknowledgement, encode | 1,344.5 ms | 1,092.2 ms (-18.8%) |
| every library operation the meter counts | 8,503.5 ms | 8,377.7 ms (-1.5%) |

`serverApplyPlan` 1,040 -> 1,156 us a call and `serverApplyStage` 1,275 -> 1,378 us are the same known cost.

Log frames per save, claim, acknowledgement and echo (`aLiveWritesStepsByBTree`: 14.2, 2.0, 4.0, 18.5) are unchanged:
that exercise claims at the persistence level, not through a live session, so it does not see a claim made by a save.

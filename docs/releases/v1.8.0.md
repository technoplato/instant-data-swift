# Instant Swift Data 1.8.0

Status: release document. `v1.8.0` is published only after the gate below passes on the release commit: through `.github/workflows/release-gate.yml` when the home runner is online, otherwise by direct maintainer authorization with the same gate run locally and its results recorded in the tag message and the GitHub release (the `v1.5.7`, `v1.6.0`, and `v1.7.0` precedent).

## Release focus

A device keeps up with a live recording, catches up a large backlog in minutes, and no longer stalls behind the main thread or behind one refused request.

Scribe builds 62 to 77 (2026-09-27 to 2026-10-01) ran this library on Michael's iPhone through hour-long recordings. Those recordings found what this release fixes:

- Every server message that touched the queued writes replayed the whole queue. With Recording 023's 2,487 queued writes, each message cost 22-25 s, and the queue shrank by about 33 writes every 55 s.
- The connection died during every long apply, and each reconnect started the same apply again.
- A refused write could leave its value behind.
- One server timeout froze a live view until relaunch.
- At startup, one library call held the write lock for 23-101 s while it waited for the busy main thread (fresh simulator).

Build 75's library drained the iPhone's 2,875 queued writes in 3 minutes (2026-09-30 22:12 to 22:15 EDT). This release is build 77's library: `956fce52` on `agent/claude-opus-5.5/library-77`, merged into `main` as `d9ac85f0`.

## What changed

### Build 77's library

1. **Smaller server messages: the client advertises `@instantdb/core` v0.22.75.** Instant's server decides what to send from the core version a client advertises when it connects (`session.clj`). Swift advertised only `InstantDB-Swift 0.1.0`, so every query refresh carried all of Scribe's 447 attribute definitions: about 134 KB of a 151 KB message. `init` now also advertises `@instantdb/core` v0.22.75. Refreshes arrive without the attributes, which the client already caches, and presence arrives as patches. Scribe's messages fell from 173 KB to 44 KB. The advert stops at v0.22.75 because newer versions batch messages into arrays, which Swift does not decode yet. `InstantLiveMessage.defaultVersions` holds the advertised versions.
2. **Caches for attribute work that repeated on every message.**
   - A live refresh keeps its attribute context (the parsed attributes and the schema lookups) while the session's attributes and the local schema stay the same. It used to rebuild them for every message. 50 Scribe-shaped refreshes with 504 attributes took 728 ms of CPU before and 357 ms after (debug build).
   - Saving a live query result reuses the stored attributes. It used to load and decode the whole attribute table inside every server-apply commit, which was 17% of a reading device's CPU in a profile. 100 loads took 1.08 s; 100 reuses take 0.018 s (debug).
3. **No library lock waits for the main thread (`@concurrent`).** The package builds with `NonisolatedNonsendingByDefault`, so `InstantRuntime`'s async methods ran on their caller's executor. A method called from the main actor that held the operation gate (the lock that orders writes, outbox claims, and server applies) could not continue while the main thread was busy. Scribe's first screen held the main thread while `observeAuthSession` held the gate for 23-101 s on a fresh simulator, and every write, claim, and observation waited behind it. All 111 async `InstantRuntime` entry points are now `@concurrent`: they run on the global concurrent executor. In a test, a write from another task that waited 2.82 s behind a blocked main actor no longer waits.
4. **A server timeout no longer freezes a live view (#324).** When a stalled server answered `add-query` with an error such as `500 operation-timed-out`, Swift retired the query for good. Its view stopped updating until relaunch, while writes kept landing. Now the query stays registered and is sent again on the next connection, as upstream does. Only a rejection that repeats, such as a permission error, retires it.
5. **A refused stream subscription ends the reads waiting on it.** A device that subscribes to a stream before the writer creates it gets `Stream is missing`. The library retired the stream's reader but never ended the observations that shared it, so Scribe's media fetch waited forever, and every later recording's media waited behind it. The refusal now ends every observation behind that reader and logs `stream.subscription-refused`, as upstream `Stream.ts` closes its iterator.

### Fixes from builds 62 to 76

6. **A large outbox catches up without replaying itself for every server message (#296).** Each server message that touched the queued writes used to peel them all off and apply them again (a whole-component rebase). Now the library first checks each server fact against the store and against the before-images the queued writes saved, and applies only what actually changes. Most messages need no replay at all:
   - When the server changes a value beneath queued writes, only the first queued writer's saved before-image is updated.
   - Deferred values (such as Scribe's segment text) and links written from the other side are checked the same way.
   - Up to 16 refused writes per message are removed without a replay.
   - A restated server fact that already loses to a newer local value is skipped, as a replay would leave it.

   On a replay of the iPhone's own store through its 103 refusals, 17 of 119 messages needed the full replay, against 118 of 119 on build 73's library.
7. **A refused write leaves nothing behind (#296).** Removing a refused write restores what it overwrote, but those restored values carried this device's timestamps. Instant stamps a value with the time its slot was first set, so a restored value could win against the server's newer value and stay. Restored values now go back stamped at time zero on every removal path, so the server's value wins. Upstream never has the problem, because it simply drops a refused write.
8. **Delivery waits for a server message that is still being applied (#296).** On Recording 023, each reconnect's first query result started a 22-25 s apply. The first write's acknowledgement waited behind it, and the 6 s acknowledgement deadline then reclaimed the write and replaced the connection: 385 times in 84 minutes, and nothing reached the server. While a message is being applied, the library now moves this device's claim deadlines to at least 6 s from now, for at most 120 s per message. Every refusal now logs what it refused (namespace, rule check, entity, attributes) and whether it was a replay of an offer that was never answered.
9. **The connection survives long applies (#296).** URLSession answers the server's pings only while a `receive()` is waiting, and the server closes a client that stays silent for about 20-30 s. The library applied each message before it called `receive()` again, so a 26-37 s apply lost the socket. A reader task now keeps receiving while one applier task applies the messages in order (up to 128 buffered). One lost socket now opens exactly one replacement connection instead of two or three. New writes no longer reset the reconnect backoff; as in upstream, only `init-ok` resets it.
10. **Local writes no longer wait behind server apply (#277).** Committing a server apply took time quadratic in the number of queued writes, and local writes waited for it. At 2,000 queued writes the lock was held 23.5 s; now 0.57 s. The `serial-gate.waited` and `server-apply.operation-gate-held` diagnostics name the lock holder's phase.
11. **Entities stay whole (#296 #259 #274).** An entity that leaves one live query result, while another result still holds some of its facts, stays whole instead of losing the facts only the first result held. Pruning collects whole entities only. An observation of deferred values is no longer dropped as stale after an unrelated write. The live timeout sleep no longer crashes on a far-future deadline (#259).
12. **One bad row no longer fails a whole query (#278).** Typed reads (`query`, `subscribe`, `FetchAll`, `FetchOne` of an entity, `InstantFetchRequest`) decode row by row. A row that fails to decode is left out, reported once with `reportIssue`, and logged as `query.row-decode-quarantined`. `decode(_:)` still throws on the first bad row, and `FetchOne` of one selected field still fails. A one-time migration removes local entities that lost their id fact, so the server delivers them whole again.
13. **Infinite queries keep paging (#300).** A windowed live infinite query stopped loading older pages when rows appeared above its first row. The leading watcher now leaves with the evicted top page, trims cut at page boundaries, an evicted page reloads from its exact boundary, and a page loaded backward starts from the server's answer instead of an earlier stored result.
14. **Auth follows upstream and keeps tokens out of logs (#113).** Magic-code and OAuth sign-in forward the current refresh token only for a guest session, as Instant's TypeScript client does; ID-token sign-in still forwards any token, as upstream does. Auth HTTP failures report Instant's error type and message (`HTTP <status> (<type>): <message>`), never the hint, which can echo tokens. `InstantAuthSession` prints, debug-prints, and reflects with the refresh token redacted and the email shown only as present or absent. A guest's queued writes survive a link into an existing account and are delivered under the new session; this deliberately differs from upstream `Reactor.updateUser`, which drops them.
15. **Two switches on the AuthV3 login screen (#113 #289).** `authV3AllowsDiscardingGuestSession` hides "Discard guest session", and `authV3ShowsDemoCounters` hides the recipe demo counters. Both default to `true`.

## For users of the library

- **API:** additive only. New: `InstantEntityModel.decodeQuarantiningFailures(_:operation:)`, `InstantLiveMessage.defaultVersions`, the environment values `authV3AllowsDiscardingGuestSession` and `authV3ShowsDemoCounters`, and `InstantAuthSession`'s `CustomStringConvertible`, `CustomDebugStringConvertible`, and `CustomReflectable` conformances. Code compiled against 1.7.0 must be rebuilt, because the async `InstantRuntime` methods are now `@concurrent`.
- **Behavior:**
  - Typed reads leave out a row that fails to decode instead of failing the whole query. Use `decode(_:)` when you need every row or none.
  - Async `InstantRuntime` methods run on the global concurrent executor, not on the caller's actor. Callers still `await` them the same way.
  - The client advertises `@instantdb/core` v0.22.75. Pass `versions:` to `InstantLiveMessage.initMessage` to advertise something else.
  - A live query survives transient `add-query` errors.
  - Auth sends a refresh token to magic-code and OAuth sign-in only for a guest. `expectNoDifference` between two sessions that differ only in token or email still fails but shows no visible difference; compare `refreshToken` directly.
- **Storage:** one data migration, `0024_remove_entities_missing_their_id_fact`, runs once at bootstrap. It removes local entities that have facts but no `<namespace>/id` fact, keeps any entity a queued write touches, and skips stores that never synced. The server sends the removed entities again when a query needs them. No table schema changes.
- **Dependencies:** unchanged from 1.7.0.

## Known open items

- #329: a stream written while the socket is closed never reaches the server. A test pins it as a known issue.
- Pattern B: a refused create peeled beneath pruned writes drops fields that no query selects. Two tests declare it as a known issue.
- The server message that adds a new attribute drops its own rows' values for that attribute (already so in build 76's library).
- #304: `typedLookupUpdateCanResolveEntityCreatedEarlierInSameTransaction` fails.
- Each window of refused writes still costs one full replay (16 in the iPhone replay).
- A value this device stamped later than the server's first-set time stays until a new write changes it (FAST-DRAIN.md section 15.7).
- `pruneLiveQueryResults` can hold the operation gate for 5-13 s while a write waits, and `acceptMutation`'s 5-attempt loop can run out and end the receive loop (once, in the first outage pair).
- Stream observers re-read the whole stream on every append, and a finished stream's reader stays registered.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.

- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

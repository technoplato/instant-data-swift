## Release focus

The live connection's status says what the socket is (#1024).

A one-shot query that was cancelled, answered too late or answered with a server error stored the connection's state
as `.errored`, and so did a live observation's encoding, registration or removal failure, a stream reader's, and a
share observation's (`recordConnectionError`). `connectionState` passes a stored `.errored` through whatever the socket
is, and nothing rewrote it until the next connection opened, so one failed query left an open socket reading
`.errored` for as long as it stayed open, and every write's status said so again.

Measured on the consuming app's devices (their mirrored diagnostics, 2026-10-22 and 10-23): every move of the
session-health beat into `conn=failed` without a real drop followed one of these query failures, on builds 114, 115 and
116 alike. Build 116's iPhone, 15:53:10: a lookup the app cancelled two seconds after the socket opened; every beat for
the rest of the session read failed, while 3-19 writes were accepted per 5 s. Build 115's Mac (1.9.13), 14:13:14: a 500
`operation-timed-out` for one add-query; failed for about two hours with no reconnect. In the consuming app `.errored`
reads as offline: its recording, playback and list screens said Offline while every change synced, and its storage
cleanup, which waits for `.authenticated`, never ran in those processes.

Upstream `Reactor.js` sets `ERRORED` only when `init` fails. A `queryOnce` that times out rejects only that query's
promise (`QUERY_ONCE_TIMEOUT`), and a server error for an add-query reaches only that query (`_handleReceiveError`,
`notifyQueryOnceError`). Swift now does the same:

- `queryOnceThroughLive` no longer records its answer wait's failure as the connection's, and a cancellation is not
  logged as `query.live-ack-timeout`. `queryOnce` logs a cancellation at debug as `query-once.cancelled`, not at error
  as `query-once.failed`: the caller cancelled it; nothing failed.
- The live observation, stream reader and share paths log their own event (`query-observation.*`,
  `stream-reader.registration-failed`, `stream-reader.unregister-failed`, `share-observation.failed`), except for a
  cancellation or a send failure the receiver owns, instead of storing `.errored`.

## What stays the same

A socket that drops still reads `.errored` with its own error until the next connection opens (`scheduleReconnect`), as
does an open that fails (`connectLiveSession`) and a synchronization blocker. The explicit flush's configured mutation
transport still records its failures as the connection's and its next success as `.opened`
(`recordMutationTransportFailure`, the former `recordConnectionError`). No public API, schema or persistence change.

Not changed, and a candidate for the same treatment: a stream reader that gives up after 11 file fetches stores
`.errored` through `scheduleReconnect` without reconnecting; upstream `Stream.ts` errors only that reader. Nothing on
the devices showed it.

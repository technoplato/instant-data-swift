## Before you upgrade

No public API change, no storage change.

## Release focus

**A write its own save claims is measured by the body the save encoded, not encoded again** (#1517; red `b3b819b4`,
green `26943d43`).

- Since 1.9.69 a live write is claimed by its own save. The claim then measured the write's projected body by encoding
  it once more, though for a write it claims at its save the projection is the write itself: 27 of the claim at save's
  100 samples in job B's profile (Mac mini, 2026-11-04).
- Now `projectionMetadata` takes the save's sorted-key size of the write and uses it when the projection kept every
  operation as written (an operation-by-operation comparison, which a dropped or hydrated write fails). The claim at save
  passes it only for a pending write with no server transaction id or confirmation source, the fields the stored body
  clears, so both encodings are the same bytes. The pump's claims pass nothing and measure as before; the claim encode
  counter counts only real encodes.

**A test for 1.9.70's receipt fix** (#1523; red store `9b792550`, test `a5c21032`, `e153cf39`): an echo replays two
pending edits under another device's change, and the server apply and the acknowledgements after it find each write's
receipt by its stored bytes, minting no fingerprint again.

**A test restated for 1.9.73's page judgment** (#1513; `ae138f67`, corrected in `0d89c144`):
`InstantStoreTests.storeObservationsHonorRemotePageInfoWindows` expected a write that sorts before an offset page's
waiting and ready windows to publish both. Since 1.9.73's `9fc6eff8` the commit skips the waiting window (it shows no row
while its server page info is awaited) and leaves the ready window's date order to a refresh, which publishes it again
unchanged; the test failed in every whole-bundle run on main since 1.9.73 and now expects that. Each observer is still
handed only its first result (#653).

**The todo seed's hop pin** (#1648; `9930850a`): the seed takes 7 actor hops, not 8, since it is no longer restamped and
prepared a second time.

## Measured

Mac mini M4, build.sh job `653-h-land-check` (2026-11-05 23:06-23:36 EST), release builds of v1.9.75 (`2eba5915`) and of
the lane head (`0d89c144`, this release's sources; `main` since adds only ledger entries) in the same job,
`ContentionExercises.recording` (150 s on the real-size store, 225 writes; the energy meter's CPU per operation):

| | v1.9.75 | this release |
|---|---|---|
| save + claim, a write | 3,922.7 us | 3,042.1 us (-22.4%) |
| write side: save, claim, acknowledgement, encode | 987.8 ms | 802.3 ms (-18.8%) |
| every metered library operation | 4,717.1 ms | 4,492.7 ms (-4.8%) |

The change removes one encode from the save, and the meter's -22.4% is more than that encode cost: in the same job the
operations this release does not touch moved between -5.7% and +12.6% (the acknowledgement 452.1 -> 509.0 us). The job's
60 s profile (`sample` at 1 ms) is closer to the cause: the save fell from 250 to 219 samples (-12.4%), and
`projectionMetadata`, which held the encode this release skips, from 27 to 2. Job `1797-f-claim-measure` (2026-11-05
00:21-00:56) measured the same change against v1.9.70: save + claim 4,058.9 -> 3,643.5 us a write (-10.2%), write side
-8.6%, every metered operation -1.8%. By those two measures the saving is nearer a tenth of a write's save than a fifth
(an inference; one job's meter cannot separate the two).

The pages written are unchanged: in both builds a write's save, claim, acknowledgement and echo write 14.2, 2.0, 4.0 and
18.5 WAL frames (`StorageIOExercises.aLiveWritesStepsByBTree`, 48 writes).

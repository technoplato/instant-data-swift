## 1.2.0 — "Delivered" now means the server said so

Scribe is a live transcription app built on this library. It records
continuously on an iPhone, an iPad and a Mac, all writing into one shared
Instant app. Version 1.1.2 fixed the outage where its outbox stalled and hid
itself. This release is about the class of bug that survived that fix.

The symptom was quieter and worse. Writes reported success. `await`ing a
mutation returned. The UI showed the new value. And sometimes the server had
never accepted any of it. The inverse also happened: a write the server
explicitly *rejected* would leave its optimistic effect on screen indefinitely,
because nothing ever went back and removed it.

What cracked this was not a failing test. It was a passing one. A focused
selector for the acknowledgement path reached 39/39 green across three suites
with zero unexpected failures, and independent review still returned NO-SHIP —
correctly. The green run proved the paths it covered; it said nothing about
delivery completing through manual confirmation, a custom transport, or a
legacy row written before the metadata existed. Every subsequent round repeated
that shape: fix the finding, watch the selector go green, have review find the
next uncovered path. Six rounds, five NO-SHIP verdicts. The lesson worth
carrying out of this release is that a green selector is evidence about its own
coverage and nothing else.

### What was wrong

Five defects, all variations on trusting the wrong witness.

**Local confirmation counted as server durability.** The delivery barrier
resolved on any confirmation it saw, including manual confirmation, a local
drain, and a transport receipt that carried no proof of server acceptance.
`waitForAllPendingMutations` would therefore return success for work the server
had never acknowledged. One diagnostic even labelled a manual confirmation
`transaction.server-accepted`.

**Terminal rejection was not atomic.** When the server rejected a mutation, its
optimistic effects could remain applied. A later mutation built on top of the
rejected one kept an inverse that referenced state that no longer existed, so
rolling back the successor restored the wrong values — and the wrongness
survived relaunch, because the broken inverse was the persisted one.

**Reconciliation over-covered authoritative retracts.** A retract was read as
proof that a whole cardinality-one slot was empty. That is not what upstream's
`retractTriple` means: it removes one exact entity-attribute-value triple. The
first fix made the failing case pass by consulting only the post-transaction
state, and review rejected it, because under that rule an *unrelated* retract —
a no-op upstream — would discard a legitimately accepted write.

**Legacy rows were silently rebased.** Mutations persisted by 1.1.2 and earlier
have no optimistic-overlay or rollback metadata. The client guessed at their
local effect during a server refresh, which means it could quietly corrupt a
row it had no information about.

**Public retry did check-then-act.** `retryFailedMutation` tested for `.failed`
outside the runtime's operation gate, so two concurrent callers could both pass
the check and re-send the same mutation.

### What changed

Delivery now resolves from exactly two things: a WebSocket `transact-ok`, or a
transport receipt that explicitly carries server acceptance. Local, manual and
drain confirmation remain durable and remain wire-sendable — they simply no
longer satisfy the server barrier. The mislabelled diagnostic is renamed.

Terminal rejection is atomic. Known optimistic effects are removed, successor
inverses are rebuilt against the corrected base, structured failure state is
persisted in the same transaction, and retry/discard are exposed as guarded
operations behind the runtime gate with reference-counted reservations, so one
owner cannot release another's protection.

An accepted write reconciles against an authoritative retract only when the
exact EAV value existed in the prepared before-state *and* the key is absent
afterward. This matches `retractTriple`. Unrelated retracts stay no-ops, and a
matching retraction reconciles without resurrecting optimistic JSON.

Deliberately not done: legacy rows without overlay metadata are **not**
repaired by inference. They fail loud and closed — refusing refresh, retry and
discard while leaving cache and outbox untouched — and emit a diagnostic naming
the mutation and the recovery required. Four of the five known issues asserted
by the test suite exist to prove that refusal. Also deliberately not done:
commit `8d02a7a8` was not rewritten when a delayed regression exposed the
retract gap immediately after it landed. `71ccbcf1` appends the correction, and
both SHAs stay in history.

Also in this release, from the same production-readiness effort:

- Native Apple Sign-In and an `ASWebAuthenticationSession` browser OAuth
  authorizer, with atomic guest-to-account promotion and UUID validation on
  `INSTANT_APP_ID`.
- Outbox starvation fix: one-shot queries register before reconnect so a
  persisted backlog cannot starve the session's own queries, and in-flight
  delivery is bounded by both mutation count and 256 low-level transaction
  steps, refilling only on acknowledgement.
- Bounded cold-start decoding: ordered SQLite JSON rows batch into at most
  1,024 rows or ~1 MiB and decode with two concurrent slots. Across three fresh
  copied-backup runs this moved the iPhone median from 4,923 ms to 3,142 ms and
  the iPad from 1,009 ms to 692 ms, at a measured 37,142,528-byte (11.45%)
  transient max-RSS increase.
- Recipes presence fixes: per-broadcast topic event projection (successive
  one-element arrays no longer deduplicate to a single event), visible touch
  cursors on iPhone and iPad, and logical-user deduplication in the avatar
  stack.

### How this was verified

The predecessor commit was reproduced RED: one test, two assertions, an
accepted merge receipt left in the outbox after a matching authoritative
cardinality-one retract. With the fix, the focused pair passes 2/2.

The full coupled selector — `InstantMessageServerAcceptanceTests`,
`InstantFailedMutationDiscardTests`, `MutationDeliveryTests`,
`InstantMutationLifecycleTests`, `V3RecordingActionFixtureTests`,
`V3RecordingsListFixtureTests`, `InstantLiveTransportTests`, plus the
50,000-row rollback-scope and live-query-pruning regressions — passes 139 tests
across eight suites with zero unexpected failures and five asserted known
diagnostics. That run was reproduced independently from a fresh scratch path at
this exact commit. Both `InstantSwiftDataCore` and `InstantSwiftData` build.
Independent hash-anchored review reports no remaining P0, P1 or P2.

Not proven, stated plainly: tracker issue #117 remains open. Its two criteria —
a Swift counterpart for every upstream Instant core delivery/retry/rejection
test, and measured Recipes delivery-throughput and rapid-update latency numbers
— are both still unsatisfied. The startup work is Mac release-harness timing
against copied backups, not installed-device acceptance, and the under-200 ms
target is unmet; reaching it needs a lazy or compact persistent projection, not
faster decoding. Recipes presence fixes passed a 25/25 focused suite but have
no physical two-device acceptance yet.

### Upgrading

Bump the pin to `1.2.0`. Two behavior changes are worth checking before you do.

`waitForAllPendingMutations` is stricter. If your code relied on it returning
after a manual confirm or a local drain, it will now wait for real server
acceptance — or keep waiting, if acceptance never arrives. Custom mutation
transports must report server acceptance explicitly; a receipt without it is
treated as local-only.

Mutations persisted by 1.1.2 or earlier that are still pending or failed at
upgrade have no overlay metadata and will now refuse refresh, retry and discard
rather than being guessed at. This is intentional and loud. Drain the outbox
before upgrading if you want to avoid it, or handle the diagnostic and run an
authoritative recovery that verifies the server effect first.

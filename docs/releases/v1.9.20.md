## Release focus

The energy meter says which way each server apply went (#1011).

`InstantEnergySnapshot.serverApplyPaths` counts, per path, the server applies that committed since launch: `reduced`,
or why the whole component was peeled and replayed (`full rebase: reduction off`, `full rebase: attributes changed`,
`full rebase: confirming apply`, `full rebase: global footprint`, or `full rebase: <why the reduction declined>`). The
names are the `server-apply.operation-gate-held` event's `path`, so a count and an event read the same. A host that
reads the meter once a minute (`snapshot().subtracting(previous)`) can say how often the reduction declined and why,
which the decline's own debug-level event could not tell anyone who forwards only info and above.

## What stays the same

No schema, migration or behavior change: `InstantEnergyMeter.recordServerApply(path:)` runs once per committed apply, at
the start of the gate-held event's recording, as one dictionary update under the meter's lock. `InstantEnergySnapshot`
gains one field with a default, so existing code compiles unchanged.

## Release focus

The runtime's operation gate stops making a transcript write wait for background work, and stops holding callers
while it hydrates or publishes (#473, freeze-185). On Michael's iPhone at 13:17:34 on 2026-10-03 a write held the gate
12.3 s with eight callers queued first come, first served; the hydrate that took the gate next held it through a SQLite
`pread` with seven callers behind it; and publishing to observers was about three quarters of every write's hold (p50
337 ms from gate to published over 633 slow holds). Scribe's save lane (#482 part C) also gets a machine-readable kind
for every write failure and a cheap read of the connection's health.

## What changed

1. **Priority lanes (freeze-185 item 2).** Callers of the operation gate queue as interactive (local writes, reads a
   caller awaits, and server applies), standard, or background (prunes, retry windows, unbounded outbox listings). When
   the gate is handed over, the highest priority goes first; within a priority the queue stays first in, first out. A
   waiter moves up one priority every 2 s it waits, so background work is never starved. A server apply queues with
   local writes because the receiver's later frames, the writes' acknowledgements among them, wait for it, and its
   commit replays every local write admitted while it waits: in the background lane, under a section written every
   25 ms, one held the gate 4.8 s and a write waited 4.7 s (1.9.6: 0.98 s and 0.87 s).
2. **One stall report per holder.** A holder past the 5 s stall threshold is reported once, however long it holds;
   the Mac logged a critical stall line every 5 s through a 331 s server catch-up. The next holder's wait report says
   how long the gate was held.
3. **A gate snapshot without a hop (freeze-185 item 7).** `operationGateSnapshot()` on the runtime and the client:
   the holder, the phase it named last, since when, and the queue behind it, for an app's watchdog.
4. **Hydration off the gate (#473).** A deferred-value emission reads SQLite without the gate, then checks that it is
   still current; when a write holds the gate, the check takes it for a moment, because under the gate no write is
   between its SQLite save and its store commit.
5. **Publication after the gate (#473).** A local write, or a server apply that took the gate itself, commits the store
   under the gate and refreshes its observers after leaving it, as Reactor.js `pushOps` returns before the `notifyOne`
   calls `notifyAll` schedules run. Commits made before a publication are published together, once, and each commit's
   caller gets that publication's emissions. Anything that reads observers' state publishes pending changes first.
6. **Publication counts in the log (freeze-185 item 5).** Each commit keeps its info `store.mutation-published` line
   (Scribe's memory fenceposts and soak sampler read it), and `store.publish-summary` reports publications, commits,
   refreshed observers and slow publications every 30 s. The per-commit line moves to debug once Scribe reads the
   summary.
7. **Durability (freeze-185 item 3).** No change needed: Apple's SQLite already commits a WAL connection with
   `synchronous` NORMAL (`SQLITE_DEFAULT_WAL_SYNCHRONOUS=1` in macOS 26.5's SQLite 3.51.0 and the iOS 27.0 simulator's
   3.54.0), so a commit appends to the WAL without an fsync and only a checkpoint syncs. The store logs its settings at
   open (`sqlite.durability`), so a device's log shows its own.
8. **Write-failure kinds (#482 part C).** `InstantWriteFailureKind(classifying:)` says whether a failed write can
   succeed if tried again: `rejected` with an `InstantWriteRejection` (unknown attribute, invalid value, invalid write,
   permission denied, refused by the server), `transient` (offline, cancelled, a busy or failing local disk, a store
   that kept changing), or `unknown`. Every `InstantError` conforms to `InstantWriteFailureClassifying`, and
   `PendingMutation.failureKind` classifies a failed mutation.
9. **Whose gate waited.** The operation gate's `serial-gate.waited` and `serial-gate.stalled` lines carry `owner`,
   the runtime's app ID, so a log from two runtimes in one process says whose gate it was. Two of the gate tests read
   the process-wide diagnostics and counted other suites' runtimes; they now count only their own.
10. **Connection health (#482 part C).** `connectionHealth()` on the runtime and the client, synchronous: whether the
   live session is open, when a local write last committed, when the server last acknowledged a write and last sent a
   result, and the pending count, from counters kept in memory.

## For users of the library

- **API:** additive. New: `InstantWriteFailureKind`, `InstantWriteRejection`, `InstantWriteFailureClassifying`,
  `PendingMutation.failureKind`, `InstantConnectionHealth` and `connectionHealth()`, `InstantOperationGateSnapshot`
  and `operationGateSnapshot()`, `InstantDiagnostics.isEnabled(at:)`.
- **Behavior:**
  - A transact still returns after its observers have their emissions; the gate is released before they are built.
  - Several commits close together may reach observers as one emission.
  - A queued local write can go ahead of a queued prune, retry window or outbox listing; server applies keep their
    place in line.
- **Storage:** no schema or data migration.
- **Dependencies:** unchanged from 1.9.6.

## A regression found before release

1.9.7's first dev run (dev-197, 2026-10-04 02:18-04:22 EDT, host load 60-180) failed
`InstantServerApplyOperationGateTests.localTransactsDoNotWaitBehindAServerApplyOverAHubComponent`: with 1,000 pending
sections in one recording's component and a new section written every 25 ms, a server apply held the operation gate
**4,816 ms** (catch up 2,431, commit 1,676, patch 691) and the longest local write waited **4,702 ms**, over 375 local
writes. The test requires both under 2,000 ms. 1.9.6's release gate ran the same test at **983 ms** held (catch up 175,
commit 593, patch 208), longest write 866 ms, over 147 writes; the earlier gates held 196-984 ms.

The cause was this release's own priority lanes: both of a server apply's gate entries ("snapshot server apply" and
"catch up server apply") had been put in the background lane. Under continuous writes each waited until aging lifted
it, about 4 s, while every local write admitted in the meantime joined the tail its commit replays under the gate, and
the receiver's later frames, the writes' acknowledgements among them, waited behind it. `c434e244` queues both entries
interactive, first come, first served with local writes, as in 1.9.6; the gate deadline, one stall report per holder,
hydration off the gate and publication after it are unchanged. The release gate below runs this test three extra times.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic
validation/run-performance-gate.sh live
```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

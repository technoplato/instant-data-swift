# Instant Swift Data 1.9.40

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
release is cut at main `a50f7a62`; its last code commit is `37b02865`. It carries 1.9.39.

## Before you upgrade: there is no going back

Once 1.9.40 opens a store, no older build can write to it. Migration 0032 (#1121) rebuilds the fact table keyed by
the fact itself (`WITHOUT ROWID`) with its `json` column computed when read, and an older build's fact writes
(`INSERT ... (json)`) and rowid reads fail to prepare against it; 0030 and 0031 (#1115) change two outbox tables and
indexes the same way. This was reproduced with the `sqlite3` 3.51 CLI on tables of the same shape, not on a device.
An app that keeps its store across installs (Scribe does) must delete its data before an older build is installed over
1.9.40. A store-format guard that refuses a newer store is filed separately; it cannot protect builds already shipped.

## Release focus

Holds of Instant's operation gate that grew with a whole result shrink to a bounded batch, and the store on disk shrinks
by two thirds. Each fix is a red commit, then a green one:

1. **A prune checks a bounded batch of facts at a time** (#1129, second slice; red `8725a7bb`, green `795a6dec`). A
   batch took at least one whole result, so the closed `$files` list's 75,640 facts were one 1.7 s hold. A batch now
   checks at most 5,000 of the facts its results released, whole entities, and leaves the rest to the next batches;
   ownership is read once per 500 entities; the results a batch may drop are decoded on the read connection before the
   gate. Only unloaded results are spread over batches, marked with their removal, so opening the store finishes a
   release a crash cut short.
2. **A server apply's retry stops working its restated results out again under the gate** (#1128; red `a4e08723`,
   green `37b02865`). A retry plans holding the gate; it now reuses the retractions and saves its first attempt worked
   out while the query-result and attribute revisions hold.
3. **Each fact is stored once** (#1121, #1120; red `8e237559`, green `c9403d9e`): migration 0032 keys the fact table
   by the fact and computes its `json` when read; a re-saved fact is upserted where it is.
4. **A write writes fewer b-trees** (#1115, first slice; red `8101f0b9`, green `c343c563`): migration 0030 makes the
   outbox's write keys and effect entities `WITHOUT ROWID`, and 0031 replaces two delivery indexes with one.
5. **The writer checkpoints every 4,000 frames instead of 1,000** (#1118; red `bedd3104`, green `56538ac5`).
6. **A changing result's JSON is written at most every 5 minutes, not every 30 s** (#1123; red `78f625f8`, green
   `ea51a8d8`); a background or terminating app, an unsubscribe and a close still write what waited.
7. **A stream resume asks only for the bytes it has not seen** (#1125; red `c88dc3f4`, green `76ef174a`), with a Range
   request whose Content-Range it checks.
8. **The live socket counts its traffic** (#1124; red `94b8747b`, green `887f3bb2`): frames and bytes per op and
   direction, a `network.wire-summary` entry once a minute, and `InstantWireMeter.snapshot()` (public).
9. **A finished line is prepared once** (#1153; red `6d765ee0`, green `0744cfb1`).
10. **A refreshed page's ownership diff costs the rows that change** (#1147, step 4; refactor `79ea7762`, red
    `164131cd`, green `560540fe`).
11. **A diagnostics entry the floor drops builds nothing** (#1148; red `9d4ca094`, green `97ed60bc`).

Test and harness commits with them: `464e385d` (#1147's cost bounds hold in optimized builds), `c3add517` (#1150's
allocation sites), `acbe277b` and `9a4695e5` (#1123's and #1119's exercise knobs), `63920cb0` (#1148's E09 pass).

## What stays the same

No public API change but one addition (`InstantWireMeter.snapshot()`); `InstantDiagnostics.record`'s message and
metadata became autoclosures, so call sites compile unchanged. The prune unloads and drops the same results and facts,
a reopened query still answers from its stored result before the server does, and a server apply's results are the
same.

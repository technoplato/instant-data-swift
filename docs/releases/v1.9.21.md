they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `9984997d`. It carries 1.9.20 (#1011), 1.9.19 (#1007) and 1.9.18

## Release focus

A read from this device answers from the whole device store, at once (#1006).

After a relaunch the in-memory store holds only the entities a stored query result owns and those an unsent write
touches; the rest of what the device wrote or received stays on disk, where no read reached it. And the reads that
could answer from the device waited: the local reader's one-shot read took the operation gate for its whole read, a
hydration's check after a read without the gate took the gate whenever it was held, and deferred values were read on
the persistence actor behind a server apply's SQLite commit. A long transcript opened with 2 of its 986 lines, behind
server applies that held the gate 4 to 7 seconds at a time.

- **`InstantLocalLookupPolicy`** (new, passed at bootstrap as `localLookup:`): the app names the attributes that scope
  many rows to one parent, such as a parent's id on each child row. A one-shot read through
  `InstantSwiftDataClient.localReader()` whose filters include `attribute == value` for one of them also reads the
  matching entities the device keeps on disk but not in memory, evaluated with the in-memory answer through a
  temporary index and never loaded into the store. A read with a limit ranks the disk's rows by the facts its filters
  and order read and reads full facts only for the rows in its window.
- **No gate, no write, its own connection.** The local reader's one-shot read takes no operation gate and writes no
  query-cache row. Its SQLite reads, and every hydration's deferred values, run on a read-only connection to the
  store's file on its own actor; the file is in WAL mode, so it reads the last committed state while the persistence
  actor writes, as SQLiteData's `DatabasePool` readers do. A failed read there falls back to the persistence actor and
  reopens the connection next time.
- **A hydration waits only for a writer that may be writing what it read.** A gate holder can name the entities it
  writes until its store commit: the server apply names none during its catch-up, its changed entities from its commit
  to its store commit, and none after; a local write names none before its save and its changed entities from the save
  to its store commit. A holder that names nothing still counts as writing everything.
- A cancelled query's failed hydration is recorded at debug instead of reported as an issue.

## What changes on disk

One partial index, `instant_triples_lookup (attribute_id, value_json, entity_id) WHERE attribute_id IN (...)` over the
policy's attributes, is ensured at bootstrap: building it reads the triples table once (one device's store held
1.6 GB), and it is rebuilt only when the policy names other attributes and dropped when it names none. With the policy
empty (the default) nothing is created. No migration and no change to stored rows.

## What stays the same

Live observations, `transact`, the outbox and the server apply behave as before; the in-memory store loads what it
loaded. `localLookup` defaults to none, and `InstantRuntimeConfiguration.localLookup` is a new field with a default, so
existing code compiles unchanged. A read with includes or a cursor reads memory only, as before.

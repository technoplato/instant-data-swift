## Release focus

A device keeps its socket open. Server errors, refusals that only repeat writes the server already took, a cancelled request, and a failed stream write no longer close a healthy connection. Media written offline reaches the server, and a list never shows a row twice.

## What changed

### Reconnects that were not needed

Upstream `Reactor.js` closes its socket only when the socket dies. Swift closed it for several other reasons, and every reconnect re-added every query and re-sent every write in flight. Each one below now keeps the socket, as upstream does:

1. **A write the server answers with a transient error (#376).** A 5xx, 408, 425, or 429 on a write reconnected the socket. The reconnect controller started over at attempt 0 on every connection, so a stalled server saw a new connection about every 0.3 s. The write is now retried on the same socket after a backoff that doubles from 250 ms to at most 5 s, with jitter between 0.5 and 1. While writes are failing, delivery pauses and probes with one write until the server accepts one.
2. **A live query the server fails (#360).** An `add-query` answered with `500 operation-timed-out` stayed registered but was sent again only on the next connection, which a healthy socket never reaches. The query is now sent again on the same socket with the same backoff, and its subscribers see the error while they keep their rows, as upstream's `notifyQueryError` does. Errors appear on `InstantQueryEmission.error`, `FetchSubscription.liveQueryError`, the `loadError` of `FetchAll`, `FetchOne`, and `Fetch` (which keep observing), and the infinite query's snapshot.
3. **An error that no write, query, or stream owns.** For example, an answer to a write this runtime no longer holds. It is logged as `websocket.error-unrouted`, as upstream's `_handleReceiveError` logs it, and the socket stays open.
4. **A refused or unflushed stream append.** An `append-stream` error or `append-failed` restarts only that stream's writer, on the same socket, from the server's offset (upstream `Stream.ts` `onAppendFailed`). A refused `start-stream` is recorded and never asked again.
5. **A caller cancelled while its message was being written.** Cancelling an observation, or retiring an infinite-query chunk, during its `add-query` write ended the socket. A write that began now finishes; upstream's `ws.send` is synchronous.
6. **A refused write recorded while local writes kept landing (#303).** Recording a refusal reloaded state between two holds of the write lock. When this device's own dictation landed in that gap five times, the receive loop ended and the socket reconnected. After five stale attempts, one attempt now holds the lock from load to commit. The exclusive server apply uses the same fallback (merged from `a8030bbe`).

### Refused writes that only repeat accepted ones

7. **A re-sent write that newer accepted writes already cover is not sent again.** The refusals after Recording 023's reconnects were re-sends of writes the server had already applied: their acknowledgements were buffered when the receive loop ended. A pending write whose every attribute a newer accepted write of the same entity covers now resolves as `supersededByAcceptedWrite`, without a round trip. A refused replay whose covering writes are still in flight waits for them (at most 10 minutes), instead of failing.

### Waits that blocked local writes

8. **Pruning inactive live-query results holds the write lock one batch at a time (#303).** In the large-store drop, one prune held the lock 5.8-13.2 s while dictation writes waited. It now removes about 5,000 result triples per hold (`liveQueryResultPruneBatchTripleCount`), and the end state is the same as one prune's.
9. **A one-shot read of rows already on the device answers at once (#317 #307).** `queryOnce` waited up to 5 s for the server, even when the same query was subscribed and answered. Behind a backlog of server frames, that wait failed Scribe's Copy Transcript at 5,004 ms. When the exact subscription was answered on the open socket and has not failed since, `queryOnce` now reads the store.

### Streams

10. **A stream written offline reaches the server (#329, ADR 0017).** A stream's client id names it on every device until the server assigns an id. The id `createStream` returns offline is valid on the writing device only. Once connected, the writer starts the server's copy by client id with a durable reconnect token (migration `0025_stream_writers`) and resends stored chunks from the server's offset. Readers on other devices read by client id. Appends and closes made while the socket is down are kept, and an offline close returns at once.
11. **An append no longer re-reads the whole stream.** Each observation's last read is extended with the new chunk, and every read still holds the content from its offset. With three observations, chunk decodes per append grew 5, 8, ... 122; they are now 0.
12. **A finished stream's reader is retired at done.** It is no longer subscribed again after every reconnect.

### Lists and observations

13. **A live infinite query's snapshot lists each entity once (#388).** A row moving between chunks was listed twice until the slower chunk caught up, and Scribe's recording list trapped on the repeated id (the Mac on build 77, the iPhone on build 76). The copy from the newer store commit wins. A kickstart also keeps the rows it showed until its first forward chunk answers, instead of showing the window empty for about 0.6 s.
14. **An observation ends when its consumer stops iterating (#394).** A consumer that returned out of `for await` on `observe(_:)` left its store observer and live query registered until the runtime closed. Michael's Mac grew from 151 to 405 store observers in 45 minutes. Dropping the stream now ends the observation.

### Account linking (#361)

15. **A second sign-in beside the primary client.** `InstantSecondSignIn` signs another identity in on its own temporary store and connection, so linking never changes the current session.
16. **An app-level `accountLinks` row links one person's Instant identities** (`InstantAccountLinks`), and AuthV3 shows a "Linked sign-ins" card behind `authV3ShowsLinkedSignIns` (off by default). An environment-gated live test links and unlinks against a real server's rules. Nothing in Scribe calls these yet.

### For maintainers

17. **A phone-shaped replay gate (#296).** `PhoneReplayGateTests` plus `scripts/phone-replay/` replay a pulled phone store through its recorded refusals and compare every count with a reference run. On 1.8.0's code it reproduces the published numbers exactly (17 of 119 frames rebased, 26,288 bodies, 2,384 accepted, 103 refused, only `recordings/clipboardEntries` different after a full restatement). The store path is an argument; no data is committed.

## For users of the library

- **API:** additive, with one new enum case.
  - New: `InstantQueryEmission.error`, `FetchSubscription.liveQueryError`, `InstantMutationConfirmationSource.supersededByAcceptedWrite`, and `InstantRuntimeConfiguration.liveServerErrorRetryPolicy`, `liveQueryRetrySleep`, and `liveQueryResultPruneBatchTripleCount`.
  - New for account linking: `InstantSecondSignIn`, the `InstantAccountLinks` API, and the `authV3ShowsLinkedSignIns` environment value (default `false`).
  - A `switch` over `InstantMutationConfirmationSource` without a `default` must handle `supersededByAcceptedWrite`, which proves server acceptance.
  - The stream API's doc comments now say what success waits for.
- **Behavior:**
  - Transient server errors are retried on the same socket. Subscribers see a live query's error and keep their values.
  - `queryOnce` of an answered subscription reads the device.
  - `createStream(clientID:)` succeeds offline with a device-local id. Read another device's stream by client id (`observeStreamContent(clientID:)`). A stream observation ends after its first `done` read, and the writer's own observations read SQLite without subscribing.
  - Dropping an `observe(_:)` stream ends the observation; keep the stream to keep it.
  - An infinite query's snapshot never repeats an entity.
- **Storage:** one migration, `0025_stream_writers` (a table of the streams this device writes). Streams written offline by earlier versions have no writer record and stay on the writing device.
- **Dependencies:** unchanged from 1.8.0.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's values, as upstream does.
- A server error on a write, a live query, or a stream append never closes the socket. An expired acknowledgement deadline and a receive-loop error still do (#402).
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts, and a snapshot lists each entity once.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic
validation/run-performance-gate.sh live
```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

# Instant Swift Data 1.9.9

Status: published by direct maintainer authorization, typed on 2026-10-14 at 16:03 EDT: "Land all this performance
work and then install that in the next build as a developer build and as a production build. So build both. I want to
just compare." The rule for this work, typed the same day at 15:37: "We want to make sure that we're not changing any
functionality, but improving performance." The release gate, `validation/run-performance-gate.sh live`, did not run for
this release; the checks that ran are below, on `d488769b`, the last code commit. The release commit's code equals it.

## Release focus

Less CPU for the same results (#653, #654, #669). A list kept as pages, one live observer per page of the same
filtered, ordered query, paid for every page on every write: a write to one row, and the server's echo of it, re-ran
every page, and every refreshed observer was handed its result again even when nothing in it changed. With 32 page
observers, one write's whole lifecycle (save, send, acknowledge, echo, prune) cost 13 times a write with no pages. Now
a write refreshes only the pages it can reach (#654), and an observer is not handed a result equal to the one it was
last handed, as upstream Reactor.js drops a deep-equal result (#653): that lifecycle went from 5,879.8 M to 374.7 M
instructions (-93.6%), the cost of a write with no pages. The reconnect loop keeps upstream's backoff and makes no
attempt while the network path is missing (#669): replaying a 37-minute outage with 13 minutes off the network, the
attempts made while the path was missing went from 56 to 1. SQLite keeps a bounded page cache and reuses its prepared
statements (#653), and a new energy meter says what each of the library's operations cost (#669).

Every observer still holds exactly what a full re-run of its query gives. One correction a reader can see (#654): an
offset page after an entity that leaves the result set (a delete, or a move out of the filter) now refreshes; before
this release it kept showing what it showed before the change.

## What changed

0. **A write refreshes only the pages it can reach (#654).** The refresh check refreshed every observer whose filters
   admit a changed entity. For a plan that reads only its own namespace's fields (no includes, no link paths), the page
   an observer shows is a function of its ordered result set (the entities its filters admit, ordered by the order value
   and then by id), its window (offset, limit, cursors, the server's page info), and the shown entities' snapshots. The
   check now compares each changed entity's place in that set before and after the publication
   (`TripleIndexes.resultSetMembership`: absent, or a member with its order value), against the store the publication
   started from. When no changed entity is shown and none changed its place, the result cannot change, and the observer
   is not refreshed.
   - The comparison needs the result the observer holds to be exactly what the publication's starting store gives
     (`verifiedEpoch`): set when a result is materialized from the whole store, kept by a splice of a verified result
     and by this skip, and dropped by any store change made without refreshing observers (`replaceSnapshot`,
     `replaceAttributes`, `mergeAttributes`, `prepareSequential`). Such an observer is refreshed by the old check alone
     until it is materialized again.
   - More than 256 changed entities refresh the observer, which then costs less than the comparisons.
   - A changed entity that was in the result set and leaves it now refreshes the observer even when it was not shown.
     The old check asked only whether the entity matches now, so it left the offset pages after it, and the page info
     of windows it was outside, as they were. This is the correction named above.
   - Upstream Reactor.js re-runs every subscribed query after a write and drops equal results; the Swift store keeps
     one store for every query, so it can tell which results a write cannot reach.
1. **An observer is not handed a result equal to the one it was last handed (#653).** Each observer keeps the result
   it was last handed (values and page info). A refreshed observer whose emission equals it is not handed the emission
   again, as upstream Reactor.js `notifyOne` returns without calling a query's callbacks when the new data is deep-equal
   to the previous result. The publication's metrics count these (`unchangedObserverCount`, reported by the
   `store.mutation-published` and `store.publish-summary` lines).
   - Deferred values are not kept in memory, so an entity whose deferred value a commit wrote, retracted or read back
     counts as changed in any result that shows it.
   - Every refreshed observer of a query whose result changed for any of its observers is still handed its emission,
     so the query's refresh sequence moves as before and deferred hydration keeps dropping only superseded emissions.
   - The emissions a commit reports (`InstantStoreMutationResult.emissions`, publication tickets) are unchanged.
2. **SQLite keeps a bounded page cache (#653).** Every connection opened with `PRAGMA cache_size = 0`, and every local
   save and live refresh ran `PRAGMA shrink_memory`. Apple's SQLite caches pages even then: reading a 20,000-fact store
   left 8.8 MB in its cache. Every connection now opens with a 2 MiB cache (`PRAGMA cache_size = -2048`), and a dispatch
   memory-pressure source (warning or critical, no timer) releases it. The large read now stays within 2.5 MiB. CPU and
   bytes written stay about the same; the win is bounded memory and no shrink after every save.
3. **Prepared statements are reused per connection (#653).** A save ran the same few dozen statements and prepared each
   one again. `SQLiteStatementCache` keeps them per connection, keyed by SQL text and prepared with
   `SQLITE_PREPARE_PERSISTENT`: a statement is checked out for one use and checked in reset, with its bindings cleared,
   so an idle statement holds no read snapshot and no bound value. A nested use of the same SQL gets its own statement;
   DDL and statements with more than 32 parameters are not kept; at most 64 idle statements are kept, the least
   recently used finalized past that. `close()` finalizes them before `sqlite3_close_v2`, and a memory warning
   finalizes the idle ones. Ten warm saves now prepare no statement.
4. **The reconnect loop keeps upstream's backoff and makes no attempt while the network path is missing (#669).**
   Upstream Reactor.js keeps its reconnect delay on the reactor: it grows by a second up to ten, resets at `init-ok`
   and on a user change, and the attempt is skipped while the device is offline; its network listener starts the
   socket as soon as the network returns. The Swift controller kept its attempt counter in a local of its run loop, so
   a run that ended without `init-ok` started the next at zero, and it had no network path at all: a device without a
   network created a socket that waited out the 5 s open deadline every 15 s.
   - `InstantRuntimeReconnectController` (now in its own file) keeps the delay; `init-ok` and a user change reset it.
   - While the transport's `InstantNetworkPath` is missing, the scheduled reconnect waits for it, still owning the next
     connection, and attempts at once when it returns, also in the middle of a backoff. The live transport client
     (`InstantLiveTransportClient.live`) reads the system path (one `NWPathMonitor`); watchOS and the simulators read
     it as always there, since a path that wrongly reads as missing would stop every reconnect.
   - An open socket is left to its receive loop, which fails when its route goes away.
5. **The library meters what its operations cost (#669).** `InstantEnergyMeter.snapshot()` returns, since launch, a
   count, the CPU time of the section's thread (`CLOCK_THREAD_CPUTIME_ID`) and the wall time for each
   `InstantEnergyOperation` (`localSave`, `storePrepare`, `observerRefresh`, `outboxClaim`, `mutationEncode`,
   `acknowledgement`, `refreshTranslate`, `serverApplyPlan`, `serverApplyCommit`, `deferredHydrate`, `prune`,
   `connectAttempt`, `frameEncode`, `frameDecode`), plus transactions, outbox rows written and superseded, and
   reconnect attempts. Subtracting an earlier snapshot gives what a minute cost. Sections are synchronous;
   `connectAttempt` spans awaits, so it has a count and wall time only. One unfair lock over fixed arrays, no
   allocation per section. Each section is also a signpost in the `com.instantdb.swift` subsystem's dynamic-tracing
   category, which `os/signpost.h` keeps off until a performance tool records.

## Left out: an identical value keeping its stamp (#653, fix 3)

A third change let an identical cardinality-one value keep the stored fact's stamp instead of taking the writer's
transaction id, so its row was not rewritten (`a2f0e619`). It was reverted before the merge (`71edafd2`). With it,
nine `InstantFastDrainTests` that pass at v1.9.8 failed: a server frame that only restates or confirms what the device
shows rebased the pending writes again (`anUnchangedQueryResultDoesNotRebaseThePendingWrites` peeled all 120 of its
pending writes, where v1.9.8 peels none; `aFrameThatOnlyConfirmsAcceptedWritesDoesNotRebaseThePendingWrites` rebased
30 times, where v1.9.8 rebases 0), and four store tests that pin a writer's stamp on an identical value failed too. A
rebase per restating frame is the reconnect drain's cost that #669 measured, so the change would have done more work,
not less, and it changed what a pending write records about its own effect. It is to be redone only together with the
server-apply planner, which reads a writer's stamp to tell its own writes from the server's.

## For users of the library

- **API:** additive; no public API is removed and existing call sites compile.
  - New: `InstantEnergyMeter.snapshot()`; `InstantEnergySnapshot` (`operations`, `transactions`, `outboxRowsWritten`,
    `outboxRowsSuperseded`, `reconnectAttempts`, a subscript by operation, `subtracting(_:)`, and its `Measure` with
    `count`, `cpuNanoseconds`, `wallNanoseconds`); `InstantEnergyOperation` (the 14 cases above);
    `InstantNetworkPath` (`.alwaysSatisfied`, `.system`) and `InstantLiveTransportClient.networkPath` (default
    `.alwaysSatisfied`; `.live` reads `.system`).
- **Behavior:**
  - An observer is no longer handed an emission equal to the one it was last handed. Code, or a test, that waited for
    an identical repeat must not; three of the library's own tests were brought in line, each with its reason
    (`79ba86f4`). A new observer's first result is always handed.
  - An offset page after an entity that leaves its result set refreshes (the correction above).
  - The live transport makes no connection attempt while the network path is missing, and attempts as soon as it
    returns; the delay between attempts is upstream's (1 s steps to 10 s, reset at `init-ok` and on a user change).
  - Each SQLite connection keeps up to 2 MiB of page cache and up to 64 idle prepared statements, released on a memory
    warning.
- **Updating from 1.9.8:** build clean. An incremental SwiftPM build after this update linked test objects it never
  recompiled against the new type layouts and crashed the test bundles (SIGBUS in `InstantMessageServerAcceptanceTests`,
  and SIGSEGV in a consuming app's tests that open a `SQLitePersistenceStore`).

## Measurements

A release write-path harness on an Apple M1 Max replays a one-hour recording's 4,344 writes (sent, acknowledged and
echoed over a loopback). Instructions are the stable measure; CPU milliseconds move with the machine's load. The
baseline is v1.9.8 with the page cache and the reused statements (items 2 and 3 above), so the rows below are the
equal-result rule and the page refresh together.

| | Before | 1.9.9 |
|---|---|---|
| One interim write's lifecycle, 32 page observers | 5,879.8 M instructions, 481.5 ms CPU | 374.7 M (-93.6%), 48.4 ms |
| Observer emissions per 100 such writes | 3,470 (133,826 values handed) | 269 (31,425 values) |
| The replay's first 300 writes, 32 page observers | 6,384.5 M a write, 535.6 ms; 10,616 emissions | 1,781.6 M (-72.1%), 198.7 ms (-62.9%); 2,947 |
| The whole replay, no page observers (three rounds each) | 427.1-447.1 M a write | 427.8-443.2 M, within one binary's own spread |

At v1.9.8 itself the 32-page lifecycle measured 6,945 M instructions and 673 ms on 2026-10-11, 13 times the 540 M of a
write with no pages.

- **Statements reused** (the page cache alone against the page cache with reused statements, two interleaved rounds):
  the echo of a 32-segment chunk
  184.0 to 177.9 M instructions (-3.3%), the same echo over a pending overlay 175.5 to 167.6 M (-4.5%), an interim
  upsert 164.9 to 163.9 M (-0.6%), the whole replay 1,918 to 1,903 G (-0.8%), bytes written unchanged within noise.
- **Page cache:** no CPU or disk change measured (the replay's 1,997 G instructions and 1,764 MB written became 1,977 G
  and 1,755 MB); the cache is bounded at 2 MiB and nothing shrinks after each save.
- **Reconnect** (a virtual-clock replay of a 37-minute outage with the network path missing for 13 minutes,
  `anOutageWithTheNetworkMissingFor13MinutesMakesNoAttemptsUntilItReturns`): attempts while the path was missing 56 to
  1, in the 37 minutes 152 to 100, in an hour 244 to 192.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Every observer holds what a full re-run of its query gives after every publication (`InstantPageRefreshEnergyTests`).
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic
validation/run-performance-gate.sh live
```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- App-shaped physical-footprint and retained-query memory tests to pass (a long transcript list).
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

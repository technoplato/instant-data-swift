# Instant Swift Data 1.7.0

Status: release document. `v1.7.0` is published only after the gate below passes on the release commit: through `.github/workflows/release-gate.yml` when the home runner is online, otherwise by direct maintainer authorization with the same gate run locally and its results recorded in the tag message and the GitHub release (the `v1.5.7` and `v1.6.0` precedent).

## Release focus

Live refresh does less work per server message, and the diagnostics log stops growing without limit.

An hour-long Scribe recording on an iPhone (2026-09-26) showed two library costs. Every server message was decoded by trying `Bool`, `Int`, and `Double` before `String` for each JSON node, throwing and catching an error each time. Every live refresh rebuilt the schema lookup indexes once per query result. Separately, the library's diagnostics file grew by 27.5 MB in that hour, and nothing ever trimmed it. Most of those entries were exact repeats of the previous snapshot.

## What changed

1. **Server JSON decodes in payload order.** `InstantLiveJSONValue` tries `String`, then `Double`, then arrays, then objects, then `Bool`, in the order they occur in server payloads. `JSONDecoder` never converts between JSON kinds, so exactly one attempt can succeed and the order cannot change the result. A string no longer costs three thrown `DecodingError`s. The separate `Int` attempt is gone: integers and fractions both already became `.number(Double)`.
2. **One schema resolution per live refresh.** `InstantLiveRefreshTranslator` resolves the schema once per refresh instead of once per query result, and merging an empty attribute set is a no-op.
3. **Persisted live-query results sort without string copies.** The sort compares values directly instead of building two `comparableKey` strings per comparison.
4. **Repeating snapshots are recorded only when they change.** A new `InstantDiagnostics.record(_:subsystem:category:event:message:metadata:correlationID:changeKey:)` records an entry only when its metadata differs from the last one recorded for the same `event` and `changeKey`. Infinite-query starter snapshots and remote page-info events use it. On the phone, 97.8% and 79.7% of these events were exact repeats.
5. **The diagnostics file is capped.** `InstantDiagnosticsConfiguration.maximumFileBytes` (default `defaultMaximumFileBytes`, 16 MiB) bounds the log file. When the next entry would exceed it, the file becomes `<name>.previous.jsonl`, replacing the older one, and a new file starts. The log therefore never holds more than twice the cap. `InstantDiagnostics.previousLogFileURL(for:)` names the previous file. Concurrent writers across processes serialize on `flock`, and a writer that opened a file just before another rotated it reopens instead of moving the new file over the previous one.

## For users of the library

- **API:** additive only. New: `InstantDiagnosticsConfiguration.maximumFileBytes`, `InstantDiagnosticsConfiguration.defaultMaximumFileBytes`, the `maximumFileBytes:` initializer parameter (defaulted), `InstantDiagnostics.record(...changeKey:...)`, and `InstantDiagnostics.previousLogFileURL(for:)`. No source changes are required. Code compiled against 1.6.0 must be rebuilt, because the configuration initializer gained a parameter.
- **Behavior:** a configured diagnostics file now rotates at 16 MiB by default. To keep every entry, pass `maximumFileBytes: nil`, or set `INSTANT_SWIFT_DATA_LOG_MAX_BYTES=0` when configuring from the environment. Any positive `INSTANT_SWIFT_DATA_LOG_MAX_BYTES` sets the cap in bytes.
- **Storage:** no SQLite schema change or migration.

## Measured

Thread CPU time, Debug build, Apple M1 Max, ABBA medians of 4 alternating runs against 1.6.0:

| Workload | 1.6.0 | 1.7.0 |
| --- | --- | --- |
| 40 decodes of an 18 KB live refresh | 513 ms | 225 ms |
| Translate 100 refreshes × 8 query results (504 attributes) | 5,123 ms | 1,223 ms |
| Build 200 persisted results of 444 facts | 1,071 ms | 627 ms |
| 1,000 empty attribute merges | 2,856 ms | 0.1 ms |
| Diagnostics record path, per 30 s of Scribe recording | 222 ms | 134 ms |

`InstantLiveJSONValueDecodeCostTests`, `InstantLiveRefreshAttributeCostTests`, and `InstantPersistedLiveQueryResultCostTests` guard the first four with absolute bounds.

Diagnostics file, from the same iPhone hour: 1.6.0 wrote 27.5 MB to one file. 1.7.0 keeps at most 32 MiB on disk (16 MiB current plus 16 MiB previous) however long the app runs, and writes fewer entries, because repeats are skipped. `InstantDiagnosticsTests` covers rotation, the unlimited mode, and concurrent writers across rotations (every kept row whole, none lost).

## Known remaining costs

- Server apply re-decodes pending outbox bodies on every refresh and prunes and fingerprints receipts each time. Measured at about 0.4–0.6 s per 30 s of Scribe recording. Changing it touches the peel-and-replay design, so it needs an ADR 0015 question first.
- The live translator's attribute store is rebuilt per attribute revision (about 120 ms per 30 s).
- Preparing a transaction on an isolated copy of the hot store still copies each large map the write mutates, once per transaction (unchanged from 1.6.0).

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Rolling back a rejected write restores exactly the facts it touched.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic
validation/run-performance-gate.sh live
```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

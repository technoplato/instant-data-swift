# Instant Swift Data 1.9.88

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main`: the only source changes on `main` since `v1.9.87` are this
release's.

## Before you upgrade

Nothing public changes, and nothing a store holds changes: the same rows, the same stored bytes, the same answers.
Each change makes work the library already did cheaper. The consuming app's Power Profiler traces and diskwrites
reports of 2026-11-16 to 2026-11-19 (builds pinning 1.9.86 and 1.9.87) named the costs; each item below gives the trace's
number, the test that pins it, and the before and after the test measures.

## Release focus

Six hot paths of a phone recording all day, each with identical output (#2551).

1. **The live-query owner probe looks results up by key** (#2553). Each fact a refresh takes out of its results asks
   whether a loaded result it does not replace still owns it. The probe named the loaded results with an uncorrelated
   `IN (SELECT query_id ... WHERE unloaded_at_ms IS NULL)`, which SQLite rebuilt by scanning every stored result each
   time: 1,000 stored results on a phone, 56 of 229 refresh-apply samples in a 13-minute trace. It now joins each
   ownership row's result through its integer primary key. Two probes over 200 stored results: 398 full-scan steps
   before, 0 after. A store shaped like the phone's (1,000 results, 57 loaded, 400,000 ownership rows, a 2 MiB page
   cache): 48.1-48.6 us a probe before, 4.6-4.7 us after, the same answers for 5,000 probes.
2. **After a reconnect, the attribute context is reused without comparing every attr again** (#2554). The cache kept
   the attrs array its context was built from, so after a reconnect each refresh compared all of the session's attrs
   value by value (2,283 on a phone; 1.45% of the app in a 3.6-hour trace). It keeps the caller's equal array, so later
   refreshes are identity checks: value comparisons 100 -> 1 for 100 calls, 9 -> 1 in a runtime's reconnect-shaped
   sequence; the context is built once either way.
3. **A prune that removed only facts memory had let go installs the revision it moved** (#2209). The next local write
   then found memory behind SQLite and reloaded every resident fact and rebuilt the hot store's indexes: 0.5-1 s inside a
   save on a phone. After such a prune, a write reconstructs and replaces nothing: 1 -> 0 of each.
4. **An acknowledgement uses the body its save stored** (#1497). It decoded the write's whole stored body (about half
   of an acknowledgement on a phone). The save keeps the body by the digest of the bytes it stored (at most 64, dropped
   at acceptance); a row that still holds those bytes gives it, any other row is decoded. Bodies decoded by an
   acknowledgement of a write saved in the same store: 1 -> 0; the acceptance is the one decoding gives.
5. **A slot's size is compared with a page's without summing all 64 shards** (#2555): a 3,000-ref slot against 30
   entities reads at most 2 shards (the test's bound) instead of 64; the answer is `count > limit` either way.
6. **A save reads the facts it replaces from their columns** (#2556), as every other fact read has since #1150, not the
   generated `json` SQLite builds per row and `JSONDecoder` reads back (6% of a save's samples).

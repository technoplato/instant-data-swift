## Before you upgrade

Public additions only, no storage schema change, no removal. Stored query results and plans from before decode
unchanged, and a plan that counts nothing keeps its cache key.

- `InstantCount<Entity>`: how many children a relation links to each row. Made with `count(where:)` on an
  `InstantReverseRelation` or on a forward many-link (`InstantAttributePath<Parent, InstantID<Child>>`).
- `InstantFetchRequest(_:counting:map:)` with one, two or three counts: the request adds them to the query and hands
  each row's values to the map, positionally.
- `InstantEntityQuery.counting(_:)` and `InstantEntitySnapshot.count(_:)` (with `InstantEntitySnapshot.counts` and
  `InstantLinkedEntitySnapshot.counts`) for requests that decode snapshots.
- `InstantFetchRequest(_:)` (a query's rows), `InstantFetchRequest.map(_:)`, `sectioned(by:)` and
  `sectioned(by:order:)`, returning `InstantResultsSectionCollection<Element, SectionName>` of `InstantResultsSection`
  (SQLiteData's `ResultsSectionCollection` and `ResultsSection` shape).
- `InstantQueryIncludePlan.counts`, `countOnly` and `isCountOnly`, and `InstantQueryIncludeCount`, the plan's form.

Behaviour that changes: none for a query that counts nothing.

## Release focus

**Rows count a relation's children and group into sections when a query is read** (ADR 0015 step L3; red `e8657c69`,
green `fe808434`, docs `e390a165`, merge `306cde58`; design note `docs/adr/0015-sqlite-data-parity-ergonomics/l3-aggregates.md`).

- Why: a consuming app's list row wants its picture and thread counts without a second stored copy that every capture,
  drop, trash, restore and thread open must keep in sync.
- Upstream: Instant's server answers aggregates for admin queries only (`instaql.clj`), so the store counts the children
  the query brings down, as upstream's client applies a nested `limit` itself (`queryValidation.ts`). A counted include
  goes on the wire without its nested bound (the nested-limit pass trims stored results by the wire's bounds) and
  narrowed to the fields its counts read.

## Checks

- **Green** (Mac mini job `2005-l3-bench-release`, debug, the green tree `fe808434`): 18 tests in 4 suites pass:
  `InstantAggregateFetchTests` (9: counts of a reverse relation, of a forward many-link, with predicates, before an
  include's limit, live through a write, an edit of the counted field and a delete; sections in first-appearance order
  and by name, an empty result; the grouped counts a list row reads of its threads, live), `InstantCountedIncludeTests`
  (6: the wire form, a plan stored before counts, the store's counts, the digest, sections, the benchmark),
  `InstantIncludedMapFetchTests` (2) and `InstantNestedIncludeLimit` (1), the suites the change builds on.
- **Red** (the same job, red `e8657c69`'s stubs on the same tests): 13 of the 15 new tests fail with 34 issues (every
  count reads 0, no rows group, the counted include goes up with its limit and without its counted field, the digest
  ignores counts; the two live tests reach their one-minute limit waiting for counts); the two that pass check what the
  stub already had (an empty result has no sections; a plan stored before counts decodes).
- **Benchmark** (debug, one thread, the in-memory store, 1,000 rows and 10,000 children, median of 5): counting two
  counts (all, and one kind) 46.5 ms and 232,803 allocations (17.0 MB allocated); linking every child as rows, the shape
  a row read before counts, 80.5 ms and 409,683 (32.3 MB); 10,000 rows into 100 sections 2.9 ms and 20,816. Red's stub
  (the same plan with no counting) took 5.7 ms and 61,739, so counting itself cost about 41 ms and 17 allocations a
  child in a debug build. The optimized run follows in the design note.

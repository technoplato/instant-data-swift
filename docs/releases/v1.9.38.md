Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The last
code commit is `8b08fa51`; the budget commit `3c9fbe76` tightens a test. It carries 1.9.37, 1.9.36 and 1.9.35.

## Release focus

Three more costs that grew with the store or the outbox instead of the change, each red, then green:

1. **A write's tail-replacement check reads only its own attributes** (#1108; red `440e32c6`, green `d094932c`).
   Every transact asked whether it may replace the outbox's tail, and the check built a dictionary of every attribute
   in the schema first, though most writes (merges, a line linked to its recording) can never replace a tail. It now
   collects the attributes the write inserts, stops at the first operation that is not an insert, and reads the schema
   once for those alone.
2. **The delivery's overlay check and the supersession tail read no longer walk every outbox row** (#1108, #1114; red
   `1807ddee`, green `aacf4b3e`). The overlay check of every claim pass tested `optimistic_overlay_active != 0`, which
   no index can seek, and scanned the outbox, each refused write's late columns read through its body; it tests `= 1`
   (the flag holds only 0 and 1) and searches `instant_outbox_global_effect_order_idx`. The tail read before every
   eligible write chose the newest row with its body size, a table scan and a sort; it takes the newest id from a
   covering index first and then reads that one row by its key.
3. **A discard of a refused write that left no effect removes its row alone** (#1103; red `8956bb6a`, green
   `8b08fa51`). Such a discard (a live refusal's rollback already ran, so the store does not change) loaded the whole
   durable outbox, copied and diffed every resident fact, bumped three revisions and dropped the cache, so the next read
   rebuilt the store from SQLite. It now reads its one row, validates that row's receipt, deletes it under the same
   revision checks, bumps only the outbox revision and keeps the cache. Anything it cannot prove takes the general path
   as before.

## Measured

On #1072's real-size fixture (version 3: integer transaction ids), Mac mini M4, release unless it says debug, except
the first line, which is a unit test on synthetic schemas (labels corrected on main after the tag; the numbers are
unchanged):

- **The tail-replacement check** (`OutboxSupersessionSchemaCostTests`, not the fixture): 1.6 MB allocated per check
  with 2,283 attributes against 12.5 KB with 16 (debug); now the same bytes with either schema, for a merge in every
  build and for an upsert in release.
- **The overlay check** (`OutboxClaimScaleTests`, the fixture at a hundredth of the phone's size): 5,709 SQLite steps
  beside 400 refused writes against 58 beside 7; now the same.
- **The tail read**: 1,336 page reads on a copy of the phone-shaped store against 24.
- **Delivery's reads of the outbox per write** (#1076's `liveWritesOnThePhoneShapedStore`, phone shape): 1,866 KB on
  1.9.37 (after 1.9.36's claim fix), now below the exercise's report threshold, and the echo's 0 KB: #1114's criterion
  (under 1 MB of `instant_outbox` per write in delivery and in the echo) is met.
- **A recording's minutes** (`RealSizeRecordingReport`, the consuming app's shape): over minutes 1-10, the claim's
  operation-gate time 90 ms a minute (267 ms on 1.9.36, 569 ms on 1.9.35) and the gate's whole hold 306 ms a minute
  (682 ms on 1.9.36, 898 ms on 1.9.35). Later minutes ran beside other builds on the same machine and read higher.
- **A discard of a refused write**: 0.33 ms, 1,641 allocations and 0.34 ms of the gate at a quarter of the phone's size
  and at its full size alike; 112 ms, 585,459 allocations and 112 ms of the gate before on the store as launched, and
  1.7 s once the whole `$files` list had loaded. The consuming app's recovery discards up to 32 at a time.

## What stays the same

No schema, migration or public API change. The tail read returns the same row; the overlay check matches the same rows;
a discard of a write with a materialized effect, an unknown receipt or an untrusted one takes the same general path,
with the same errors.

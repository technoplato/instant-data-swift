# Instant Swift Data 1.9.13

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `9e813943`.

## Release focus

Three changes, from two issues, that keep every result and every write exactly as before:

1. A delete of a row the store no longer holds refreshes no observer that cannot show it (#1007).
2. Materializing an entity sorts its link sets without building two key strings per comparison (#1007).
3. A closed query's stored result answers its reopening before the server does (#1006).

## 1. A gone row refreshes no verified observer (#1007)

A commit publishes to the store's observers; each one skips, splices the changed rows into its last result, or
re-materializes its page from the store. A delete reports the deleted id as changed even when the store holds no fact
of it, and `install` returned no namespaces for an entity with no facts and no references before or after the commit,
which made every observer re-materialize from the whole store, and the gone id kept every observer from splicing. An app
that deletes a short-lived row with the write that ends it (a line in progress, deleted by the line's final) pays that
on every server apply that replays a pending final, because the row is already gone on both sides, and for every line
that never had the short-lived row.

`install` now returns the changed entities it found in no namespace beside the namespaces. A publication keeps those it
also finds in no namespace before its first commit and after its last (one publication can cover several commits, so a
real delete followed by a repeated delete stays a change): such an entity had no facts and no references either side, so
no result showed it and none can show it. A verified observer that does not show one judges the change without it, so it
skips, or splices the other changed rows in place. An observer whose result may be stale (#654), or that still shows the
entity, refreshes from the whole change as before.

## 2. A link set sorts by its ids (#1007)

A forward link keeps every linked id as one value of a many-cardinality attribute on the linking entity, so an entity
can hold thousands of ids per link. `TripleIndexes.materializedValue` sorted them with
`{ $0.comparableKey < $1.comparableKey }`, and `comparableKey` builds a new string on every call, so a 2,000-id link cost
about 44,000 string allocations per read. Every read paid it: a cached snapshot of a namespace with a many-cardinality
attribute is re-merged through `internedSnapshotByMergingManyCardinality`, which sorts again, and an ordered page
materializes every candidate before it applies its limit. Device time profiles of a consuming app put this sort at 23%
of the whole process's CPU while idle on a list.

`TripleIndexes.sortedByComparableKey` sorts a set of refs only (every forward link) by the ids themselves: a ref's key is
`"5:"` and its id, Swift compares strings by their NFC forms, and `:` composes with nothing after it, so the shared
prefix decides nothing and distinct refs keep exactly the order their keys gave them. Any other mix builds each key once
and sorts by those keys. `normalizedSlot` uses the same helper, and the live-query retraction sort uses the
field-by-field comparator instead of `(entityID, attributeID, key)` tuples, which built both keys before comparing the
entity ids.

## 3. A closed query's stored result answers its reopening before the server does (#1006)

The session prune deleted a closed query's result and every entity only that result held (`6c6760b4`), so reopening a
long paged list waited on the server for every page. Upstream `PersistedObject.unloadKey` unloads a closed query from
memory and keeps its stored copy until the age, entry and size limits collect it; a later subscription loads it back and
answers from it first.

- The session prune moves a closed query's result into a new table, `instant_unloaded_live_query_results` (migration
  0027), instead of deleting it. Its facts leave the store as before, so memory and bootstrap stay as bounded as they
  were, and every existing reader of `instant_live_query_results` sees it as removed.
- A live observation of the same key (standard, or an infinite-query chunk that seeds from a stored result) moves it
  back under the operation gate it already holds: the result owns its facts again, and its entities that left the store
  come back, from SQLite when it still holds them, else from the result (deferred payloads back to SQLite only). Its
  stored page info lets every cursor page answer locally.
- The policy (1 year, 1,000 results, 1,000,000 triples) counts unloaded results and collects them first, oldest first; a
  saved result supersedes its unloaded copy; schema reconciliation and application migrations drop the unloaded copies.

## What stays the same

No public API changes. Every observer holds and is handed exactly what a fresh read returns (1); every link set lists the
same values in the same order (2); the outbox, delivery, acknowledgements, server applies, the operation gate and the
prune's cadence are unchanged. Migration 0027 adds one table (3).

  fail on 1.9.12 (every observer re-materialized for a delete of a row the store does not hold; four for a line's final
  whose short-lived row is gone, where two can change; no splice for an update beside a gone row); the test of an
  observer whose result may be stale, and a random test over six seeds (finals, interims, renames and deletes, some of
  rows already gone, alone and batched, every observer compared with a fresh materialization after every step), pass

  with 4,000 linked ids cost 27.9 times the CPU of building one key per id on the same thread (bound 10; keys built once

  query (page size 2, 5 rows) reopened with the server silent showed 0 rows after 5 s on 1.9.12, and all 5 rows in

## Not changed here

- An observer of a plan with includes still re-materializes whenever a change reaches its namespaces, even when no
  changed entity is shown or linked to a shown one (#1007, the next library fix).
- A server apply still peels and replays every pending write that shares an entity with the refreshed result, so its
  cost grows with the pending count (#1007, #932, #998).

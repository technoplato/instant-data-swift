## Release focus

A page that selects fields materializes only the fields it reads (#1007).

A page that selects fields built every field of each row it read and cut the row to its selection afterwards. A
consuming app's queries over its recordings select a few scalar fields, while a recording holds thousands of refs in its
link sets (its lines, attachments, events, chunks), so each re-read of a recording built and sorted all of them for
nothing. A list that filters on a field no index covers (here "not in Recently Deleted", `deletedAtMs` is null) reads
every candidate row to test the filter, so it built every candidate recording whole, not only the rows it shows.

Now a candidate row is materialized with only the fields the page's filters and order read, and a row the page shows
with those, its selected fields and the links its includes follow (`TripleIndexes.shownFields` and `candidateFields`).
A candidate built with fewer fields is built again if the page keeps it. A page that selects every field (no selection)
materializes rows whole, as before; a splice of a selecting observer reads its shown fields.

## What stays the same

No public API, schema or migration change. Every page holds exactly what it held: the values it selects, its links and
its page info. Filters, orders, windows and includes read the same values as before, from the same facts.

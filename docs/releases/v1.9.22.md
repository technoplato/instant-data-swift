# Instant Swift Data 1.9.22

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `73ed07b8`. It carries 1.9.21 (#1006: local reads answer from the
whole device store on a read connection beside the writer) and 1.9.20 (#1011: the energy meter's server-apply paths).

## Release focus

The local cache gives back the pages it frees (#1015).

SQLite reuses a free page before it grows its file, but a file in `auto_vacuum = NONE`, the mode every cache had, never
shrinks, and nothing ran `VACUUM`. On one iPhone (2026-10-23, 1.9.13) the cache was a 916 MB file of which 676 MB,
165,125 of 223,571 pages, were free: the high-water mark of past deletes (session prunes, acknowledged writes, the
ownership migration of #704).

`compactLocalCache(holdingWhile:)`, on `InstantRuntime` and `InstantSwiftDataClient`, rewrites the file without its free
pages with one `VACUUM` when at least a quarter of the file and 64 MB are free. It takes the operation gate at
background priority, behind every other caller, so never while a server apply holds it, and looks again under the gate.
It does not start while the device is hot (thermal state serious or critical), in Low Power Mode, short of disk for a
copy of the live pages and a WAL as large, or cancelled, or while the app's `hold` gives a reason (a consuming app passes
its recording). The `VACUUM` bounds its dirty pages with `cache_spill = 256` for itself alone: Apple's SQLite keeps up to
20,000 dirty pages in memory before it spills, whatever `cache_size` says, and the `VACUUM` alone peaked at 194 MB. The
storage snapshot reports the file's pages, free pages and mode (`InstantStorageSnapshot.localCacheFile`), and the energy
meter names the `VACUUM` (`localCacheVacuum`).

Why not `auto_vacuum = INCREMENTAL`, which gives free pages back in small steps: it keeps pointer-map pages that every
page allocation, free and balance updates. On the library's own write path (`InstantLocalCacheWriteCostTests`, below) it
wrote 2.97% more on a server apply and transacts and 5.80% more on a drain of acknowledgements and refreshes, on every
write, while one `VACUUM` of the phone's live pages writes about 620 MB once in a long while. New caches stay in
`auto_vacuum = NONE`.

## What stays the same

No schema or migration change, and no change to any write, read or sync path: compaction runs only when an app calls it.
`InstantStorageSnapshot` gains an optional field; its initializer's new parameter has a default. Every row is kept: a
`VACUUM` copies every table and index, and a table with an `INTEGER PRIMARY KEY` keeps its ids (the stored results'
`query_id`).

## Checks

- **Red, then green.** `InstantLocalCacheCompactionTests` (red `d3da7a73`, green `73ed07b8`; 9 tests): a cache mostly free
  is rewritten without its free pages, every table's rows hashed the same before and after, the file on disk at its new
  size, `cache_spill` as it was, and a second call finds nothing to do; the `VACUUM` holds the operation gate (phase
  "vacuum") and a write started meanwhile lands after it; a cache within its allowance is left alone; nothing runs while
  the device is hot, in Low Power Mode, held by the app, cancelled, or short of disk; the storage snapshot reports the
  file; a new cache keeps `auto_vacuum = NONE`.
- **Related suites** (a Mac mini M4, Xcode 27 beta, debug, on 1.9.21): the storage snapshot, energy meter and local
  read suites pass with it (#1006's read connection reads beside the `VACUUM`, which runs on the writer).
- **The whole suite on the same machine**, on 1.9.19's main plus #1007's parser and #932's commits (`f7035742`), with
  and without this change, at load 18-66 from other sessions' builds: 1,365 tests fail 167 test names without it; 1,376
  fail 180 with it. Of the 21 that fail only with it, all pass alone but one, the binary-framing speed comparison that
  fails 1 run in 3 alone on both trees (1.9.18's release notes); 8 fail only without it. Compaction runs only when an
  app calls it.
- **Measured: the write cost of each mode** (`InstantLocalCacheWriteCostTests.measureWritesInEachAutoVacuumMode`, env
  `INSTANT_LOCAL_CACHE_WRITE_COST=1`; FastDrainFixture with the consuming app's links, deferred text and live lines: a
  300-segment server-history apply and 1,200 transacts, then 120 drain frames of acknowledgement and refresh; the cache
  created in each mode; three alternating rounds, spread under 0.3%):

  | Logical bytes written | `auto_vacuum = NONE` | `INCREMENTAL` |
  | --- | --- | --- |
  | Apply and transacts, 3 rounds | 601,031 KB | 618,887 KB (+2.97%) |
  | Drain, 3 rounds | 86,247 KB | 91,251 KB (+5.80%) |

- **Measured: compaction on a phone-shaped cache** (`measureCompactionOnAStoreCopy`, env
  `INSTANT_LOCAL_CACHE_COMPACTION_STORE`; the phone's 265,187 rows recovered from a copy torn mid-checkpoint, 9 rows with
  torn JSON dropped, laid out with 166,543 free pages scattered between them; the runtime's own `compactLocalCache`, the
  Mac mini's real thermal and disk state): 838.3 MB -> 182.3 MB, no free page left, `VACUUM` 1.2 s, 617 MB written, CPU
  0.93 s, the process's peak memory unchanged (56.5 MB), every table's rows the same.
- **Measured with Apple's SQLite 3.54 alone** (the same store shapes; Python's sqlite3 on the mini): `VACUUM` in place
  0.79-1.03 s and 630-645 MB written for 197 MB of live pages, 382-393 MB of extra disk while it runs, 194 MB of memory
  unbounded and 20.6 MB with `cache_spill = 256`; `VACUUM INTO` and a rename 0.33-0.57 s and 244-254 MB (1.3x the live
  bytes) but it needs every connection closed; `PRAGMA incremental_vacuum` of 64 pages a step 0.84 ms at the median and
  13 ms at p99, 3.4 KB written per page given back.
- **Not covered by this release's checks:** Swift→TypeScript and TypeScript→Swift boundary runs, the memory and

# Instant Swift Data 1.9.73

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." Tagged from `main` (9d76a581 plus its ledger and this record): every source
change on `main` since `v1.9.72` is now marked ready for a build. It carries 1.9.72 (#1500, the memory lane), 1.9.71
(#1796) and 1.9.70.

## Before you upgrade

No public API change, no storage change. The persistence actor keeps in memory, for each stored result a server apply
saved since the last other writer of ownership rows, one fingerprint per entity of the facts it stores (two 64-bit sums
and a count): memory in proportion to the entities of the results the server restates.

## Release focus

**An infinite query's frozen pages skip a line past their cursors** (#1513; red `f23d0f69`, green `9fc6eff8`).

- An infinite query freezes each full page as a live query between two cursors with no limit (upstream
  `freezeForward`), so a long transcript is many frozen pages (256 lines, 4,864 facts each in the phone store copy of
  2026-11-02). A new line of the recording matches every page's filter, so the publication judged it as entering each
  page and materialized every frozen page again, for a line none of them could show.
- A page whose rows follow the server's page info shows only the rows between its start and end cursors (as
  `paginate` and the bounded selection compare them) and reports the server's page info; while that page info is
  awaited, or names no first row, it shows none. A change outside those rows before and after it now skips the page.
  A line written inside a page's cursors still refreshes it. A date order, whose index normalizes values, is left to a
  refresh.

**A page with no limit, ordered by an indexed field, orders only its filter's rows** (#1513; red `dbc50672`, green
`88b3c633`).

- `materializeOrderedSnapshots` ordered and materialized every entity of the namespace and only then applied the
  filter: a recording's attachments page (`recordingID = X`, newest first, no limit) read every attachment the device
  holds, and a frozen page that did refresh read every line. It now orders the indexed equality filters' hits when they
  are fewer, with the same comparator, and still matches each against every filter.

**An observer keeps what its plan depends on** (#1513; red `76950aca`, green `5ccfb473`): worked out once when it
registers, instead of every judgment and splice walking the plan and building each include's plan again (93 of the
observer refreshes' 725 ms in the build-251 speech trace).

**The nested-limit pass reads a schema indexed once** (#1109; red `d4e335ac`, green `0ff1bd60`, test `2c0b7d7e`): 374 ms
of the pass, 258 ms of it walking all 2,283 attributes per call, 1.1% of the app's CPU in the same trace.

**A server apply finds the cascading links without sorting the schema** (#1109; red `2521dbcb`, green `c3693f35`):
37 ms per 90 s, every sample in that sort.

**A text frame from the socket takes its UTF-8 in one pass** (#1109; red `132e23dc`, green `053e7ecb`): 84 of the frame
decode's 155 ms were a character-at-a-time copy out of the socket's NSString.

**A refresh compares only the entities it changed with a stored result's rows** (#1116, #1109, #1147; red `0aa0363c`,
green `b95e87f9`).

- Since 1.9.68 a server apply compared each restated result with its stored ownership rows once, but that once still
  read every row and encoded every restated value: 6.39 ms of `serverApplyRetractions` per refresh-ok on the phone
  (the consuming app's build 253, 192.5 minutes, 1,596 frames), for pages most of whose lines had not changed.
- Each stored result now keeps, in the persistence actor's memory, one fingerprint per entity of the facts its last
  save stored, tagged with the query-result revision that save's commit left and the header it wrote. A refresh whose
  read checked that revision reads and encodes only the entities that joined, left or changed, through the ownership
  table's key; the others hold the same facts as their rows. A 32-line page with one line changed: 96 rows read and 96
  values encoded before, 3 and 3 now. Memory: an entry per entity of each result refreshed since the last prune.
- Validity rests on the invariant the server apply's plan already relies on (#932): every writer of ownership rows
  bumps the query-result revision in its transaction. Only a server apply's own commit carries fingerprints forward;
  after any other writer (a prune, a release, an unload or reload) the next refresh compares in full once.
- A value goes into its entity's fingerprint as exactly as the store keeps its text (red `22c0d486`, green `949064a2`):
  strings as their UTF-8 bytes, numbers and dates as their bits, a JSON object's members in the order of their keys'
  bytes. Through `Hashable`, a composed and a decomposed "é", and 0 and -0, folded alike while the store keeps
  different text for them and SQLite compares it byte for byte, so a value restated in the other bytes would have kept
  its old text in the rows. Caught before release by a test that holds the rows' bytes to the full comparison's.

**A server refresh saves what its translation limited, without limiting it again** (#1109; red `aa7132d7`, green
`2ce76178`).

- The live-refresh translator limits each restated result's nested includes (InstaQL `$limit` per parent), and the
  planning read's save ran the same pass over every restated fact again, as a defense. Those saves run only for a frame
  that merges no attributes, and the commit checks the attribute revision, so for every save that commits the
  translation's schema is the store's and the limit kept every fact. The phone's speech trace (build 251, 90 s): the
  save's pass was 150 ms, 106 of it the schema walk removed above, about 44 ms the pass itself.
- `applyLiveRefresh` names the attribute revision its translation's schema came from; a save at that revision takes the
  results as they are. Every other save still limits (the commit's, after merged attributes; a retry after the revision
  moved; results no translation limited).

- The seeded differential (3 seeds, 60 frames of two pages edited, grown, shrunk and reordered, a prune every 20) keeps

- The whole debug bundle (1,700 tests) against `Tests/known-failing.txt`: new failures were two schema-index tests that

  it passed alone in the same job; the memory lane saw 0.366 on its tree).

## Not run

The release gate, `validation/run-performance-gate.sh live`, did not run (the maintainer's authorization quoted above).
This release changes which observers a publication refreshes, how the store materializes and decodes, how a refresh
compares a restated result with its stored rows and when its save limits nested includes, not the wire or the stored
format. The phone's before/after waits for an hour of recording on the consuming app's build that pins this release.

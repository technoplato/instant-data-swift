## 1.5.1 — Short live infinite pages no longer thrash canLoadNextPage open

Scribe Shared on iPad, pinned to **1.5.0**, started a recording and died
within about a minute. Tailnet diagnostics showed physical memory climbing
from ~50 MB to **~4 GB**, then silence — classic Jetsam. The same sessions
logged dozens of `recording.query.list.next-page.requested` events with only
7–8 recordings loaded (page size 50) and `canLoadNextPage` stuck `true`.

**1.5.0** expanded pre-kickstart infinite queries from the local store so a
full first page could still page before liveTuple cursors arrived. That path
also began trusting remote `hasNextPage` on the starter chunk. When the
server claimed another page but the local window was short of `pageSize`,
kickstart never ran (it requires a full page plus liveTuple). `loadNextPage`
could not advance cursors; it only re-expanded local data. The app list UI
swapped a “Load older” button for a ProgressView on each request, so
`onAppear` re-fired as soon as loading cleared — an infinite loop until the
kernel killed the process.

**1.5.1** restores the 1.4.0 safety property for pre-kickstart pages: only
**local fullness** (`count >= pageSize`) can leave `canLoadNextPage` true.
Closed short windows no-op further expands (still republish so UI leaves
loading). A live parity test seeds three rows under limit 10, injects remote
`has-next-page: true`, and asserts repeated `loadNextPage` never reopens
paging.

Pin `exact: "1.5.1"`. Keep the 1.5.0 blank-detail optimistic protection;
this release is a paging thrash patch only.

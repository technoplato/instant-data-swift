## Release focus

The energy meter names more of the library's CPU (#1011).

1. **Each operation says how much of its CPU ran on the main thread.** `InstantEnergySnapshot.Measure` gains
   `mainThreadCPUNanoseconds`: at a section's end the meter reads one flag (`pthread_main_np`) and adds the section's
   thread CPU to it when the section ran on the main thread. A host that reads the main thread's own CPU clock can then
   take the library's share (the observer refresh runs there) and name what is left on the main thread, the user
   interface, without counting the refresh twice.
2. **The server apply's staging has its own name.** `stageServerApplyBodyPage` was metered as `serverApplyPlan`; it is
   `serverApplyStage` now, so `serverApplyPlan` drops by the staging's share. A disk-write report's heaviest stack ended
   in it.
3. **A server result's retractions have a name.** `liveQueryReplacementRetractions` ran outside every operation; it is
   `serverApplyRetractions` now.

## What stays the same

No schema, migration or behavior change: the meter's counters are the only output that moves. `InstantEnergyOperation`
gains two cases and `Measure` one field with a default, so existing code compiles unchanged; a host that switches over
`InstantEnergyOperation` exhaustively needs the two new cases.

## Cost

At -O on a Mac mini (M4), thread CPU per call, fastest of 20 batches: `pthread_main_np` 1.2 ns, and the extra counter
addition under the meter's lock 0.7 ns, against the 171 ns of the two thread-CPU clock reads every section already makes:
about 1% of a section's cost.

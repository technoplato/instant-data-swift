they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `022495f9`. It carries 1.9.24 and 1.9.23 (#1007), and #1012's red

## Release focus

A server apply holds the operation gate for less of its work and writes less, and an app can choose the priority of
the runtime's steady-state sync (#932, #590).

Three of these changes shipped inside 1.9.20 without a description there; they are described here.

1. **A refresh's restated results are prepared before the gate** (in 1.9.20; red `e8def33c`, green `91c7e83f`). Every
   refresh restates whole query results, and the commit diffed each one against its stored ownership rows under the
   operation gate, reading every row and encoding every value. Each attempt now works out, before the gate and at the
   query-result revision the commit checks (every writer of those rows bumps it), the result as stored, the ownership
   rows that leave and join, and the JSON when the commit would write it. On a copy of a real store (nothing pending,
   7,287 restated facts a frame) the gate went from 87-140 ms to 1-2 ms a frame on a Mac mini. The phone's commits
   with nothing pending took 1-4 s; whether they fall the same way has not been measured on the device.
2. **The commit updates changed outbox rows from one join** (in 1.9.20; `41960a8b`). It read each changed row's fifteen
   staged columns through fifteen correlated lookups, each walking the staging row's bodies, which sat before its small
   columns; the staging table now keeps its bodies last, and the commit's closure re-plan no longer reads every body's
   size. At 2,580 pending writes, every frame a full rebase: the commit's outbox part ~280 -> ~90 ms, the gate hold
   ~507 -> ~337 ms (median, Mac mini).
3. **A retried apply holds the gate only while it plans** (in 1.9.20; red `6453a0c9`, green `aced3508`; its clock
   `855b082c`). When local writes landed between an attempt's seed and its plan, every attempt went stale and, after
   five, the apply ran again holding the gate from seed to commit (25 `server-apply.exclusive-fallback` events on one
   phone in a day). Attempts after the first now hold it from their seed to their plan; writes that land later are
   replayed by the catch-up. The gate-held event's `planningHeldMilliseconds` now counts from entering the gate, so it
   reports the hold and not the wait for it.
4. **`InstantRuntimeConfiguration.liveSyncTaskPriority`** (red `84919a03`, green `748f107e`). The automatic
   connection, the live session's reader and frame applier, reconnects, the mutation delivery pump and stream catch-up
   start at this priority. `nil`, the default, keeps today's behavior: they start at the priority of the task that
   opened or connected the runtime (user-initiated in an app that opens it from a user-initiated task, so they ran on
   the performance cores for the process's life; one phone spent 64 of 125 CPU-seconds there while recording). Local
   writes and reads keep their callers' priority either way. `.utility` moves the sync tasks toward the efficiency
   cores, and also behind every busier task, so an app should set it only after it measures, on the device, that a
   write still reaches the server and a server change still reaches the screen as fast. A loopback bench on a Mac mini
   (release build; 150 writes 60 ms apart into 2,500 segments, three observers; three rounds each, beside other agents'
   work at load 36-52 on 10 cores) shows why the default stays `nil`: with ten user-initiated busy threads in the same
   process, a write reached the server in a median 14-30 ms at user-initiated and 24-27 s at utility, and its
   acknowledgement came in 29-65 ms against 31-34 s (at user-initiated the bench timed the acknowledgement of 62-85 of
   the 150 writes). With no busy threads, the median was 11-15 ms at both priorities
   in two rounds of three; in the other, utility's median was 62 ms and its p95 2.4 s.
5. **A full rebase's staging keeps no copy of each planned body** (`022495f9`). The reverse pass copied every peeled
   body into its staging row, the forward pass and the stage read that copy, and the stage then rewrote the row whole.
   Both passes and the stage now read the outbox's body: every statement that rewrites an outbox body bumps the row's
   revision, and each page compares its rows with the plan in the transaction that reads them, so the forward pass
   reads the body the reverse pass read or the page is stale. With the cost harness at 2,580 pending writes, every
   frame a full rebase, on a Mac mini (debug, on 1.9.23 without and with it): 674,024 KB -> 524,952 KB written over
   7 frames (-22%, about 96 -> 75 MB a frame), and 992,218 M -> 955,411 M instructions (-3.7%). The saving grows with
   the bodies' size, since each copy was written twice.

## What stays the same

No schema or migration change: the staging tables are temporary and created per connection. One public addition,
`liveSyncTaskPriority`, whose default changes nothing. What every observer is shown, and what reaches the server and
when, is unchanged. The persistence decode queue keeps its user-initiated QoS (without one of its own, its batches
inherited the cooperative caller's, and a test bundle stopped with every cooperative thread waiting on a dispatch group
whose work never got a thread).

## Not changed here

- A frame the reduction declines still peels, re-stamps and rewrites every pending body, so a full rebase still writes
  about 75 MB a frame in the harness above.
- `TripleIndexes.newestTransactionTimeMilliseconds` still walks the whole store once per replayed write.
- Reads that need the persistence actor (connection status, a deferred value outside the local reader) can still wait
  behind a server apply's work on that actor; #1006's read connection serves the local reader.

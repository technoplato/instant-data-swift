# Instant Swift Data 1.9.29

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `10345339`.

## Release focus

A write the server refuses is rolled back at the cost of the rows it touched, not of the whole store (#1035).

A consuming app on a phone had the server refuse the same two writes about 20 times a minute for six minutes. Each
refusal made the store reload every fact it held from SQLite (39,507 facts, 12.9 MB decoded, 242-338 ms each) and
replace its in-memory store, and the rollback itself copied the store twice more. The phone spent 87-130% of one core
and 1.7-2.6 W on it at thermal state serious.

1. **The rollback advances the memory cache** (red `99459a0a`, green `fcced1ec`). `commitClaimedTerminalFailure`
   bumped the store revision and dropped `cachedState`, leaving `cachedMaterializedStore` one revision behind the
   runtime's hot store. The next state read saw the cache as stale, rebuilt every fact from SQLite and replaced the hot
   store. The commit now advances the cached revision domains with the rollback's changed facts
   (`advanceCachedRevisionDomains`), as the server-apply and local-write commits already did, reading the outbox and
   query-result revisions inside its own transaction.
2. **The rollback is prepared from the hot store, not from a copy** (red `4ff7f805`, green `10345339`).
   `failClaimedMutationAttempt` took `InstantStore.snapshot()` under the operation gate (every fact materialized, every
   entity sorted) and indexed that copy again before applying a one-row rollback. It now takes an
   `InstantStorePreparationBase`: the store's `AttributeStore` and `TripleIndexes` as the gate leaves them. Both are
   copy-on-write values, so the base is the same moment the snapshot captured, at no cost until the rollback changes its
   own copy. Deferred values join that copy as `prepareCurrent(_:hydratingDeferredValues:)` adds them for a local write.

## What stays the same

The rollback restores the same facts in memory and in SQLite, its successors are peeled and replayed in the same
order, and the commit still proves the store revision and the component rows it was prepared against: a local write
that lands between the preparation and the commit still makes the attempt retry. A refusal is still recorded, logged
with its namespace, entity, attributes and values, and published to the write's lifecycle.

## Checks

- **Red, then green.** `InstantPersistenceCacheResidencyTests/aRefusedWriteRollsBackWithoutReloadingTheLargeStore`:
  a 10,000-fact store, one claimed write refused, then a local write: residency metrics 1/1/1 (a full SQLite load, a
  full reconstruction, a hot-store replacement), now 0/0/0, with the refused fact gone from memory and SQLite.
  `aRefusedWritesRollbackCopiesNoFactOfTheLargeStore`: 2 full copies of the store for one rollback, now 0, with the fact
  the refused write replaced restored.

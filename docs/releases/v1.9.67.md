## Before you upgrade

No public API change, no storage change.

## Release focus

**A restated unset field reduces on a schema whose deletes cascade into it** (#1756; red `831ee0bf`, green `dbc7d5d0`,
guard `29a2837a`; merge `be720d8e`).

- A list preview selects an optional field no write sets, and the server restates it as `null` on each new preview row
  while that row's writes are pending. 1.9.52 (#1378) lets such a frame reduce: the slot is proved unwritten, so the
  server's fact lands where the whole-component rebase would leave it. It left out every namespace a delete can
  cascade into, because a pending delete there could remove the slot on the rebase's replay, and the consuming app's
  recording cascades to its lines. On its schema every such frame still peeled and replayed the component.
- On 2026-11-04 a tablet that had recorded for 7.4 hours held about 12,000 unsent writes. Overnight 80 of its server
  applies over 1 s took that full rebase (`changesShadowedFact` on the preview's unset field, about 7,600 replayed
  writes each); with the per-write walk that 1.9.66 removed, its receive loop fell minutes behind, query answers took
  up to 18 minutes and the queue barely drained. On 1.9.66 the same frame still came every 10-20 s: 60 in ten minutes,
  about 6,000 replayed writes each, one core busy and the device hot.
- Now such a slot qualifies on a cascading namespace too, unless a surviving write on its entity deletes an entity of
  a namespace whose deletes can reach the slot's namespace through cascading links
  (`InstantServerApplyCascade.sources(into:attributes:)`), or deletes one without naming its namespace. A write whose
  replay cascades into the entity names it in its effect footprint (its rollback restores the entity), so it is among
  the writes the reduction context already reads for the slot.

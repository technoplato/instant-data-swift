## Release focus

**A server fact on a slot no pending write sets, and the store leaves empty, no longer peels and replays the queue**
(#1378). One device's outbox grew from 29 to 524 pending writes in eight minutes after a relaunch mid-recording, and
past 4,000 within the hour. Every gate-held line said `full rebase: changesShadowedFact` on one attribute, and each frame
peeled and replayed 139 to 2,827 pending writes (0.3-3.1 s of the operation gate each). The app's list query selects an
optional field that no write sets, and the server restates it as `null` on each entity the list newly shows. While a
pending write still shadows that entity (here, the write that moves the list's preview slot on: its receipt restores
the old link), the reduction (#296) found no writer of the slot and a store that did not show the server's value, and
declined. Its rule assumed the full rebase runs once and the next frame's restatement holds; a list whose newest row
changes with every write names a new entity on every frame, so every frame declined and its cost grew with the queue
(F65). With a short queue the entity's writes were answered before its frame came and the rebases were small; the
backlog after a relaunch tipped it.

Now the reduction keeps such a fact when the slot is empty and no surviving write on the entity inserts, merges or
retracts the slot, or deletes the entity: the full rebase would leave the server's fact there too (the peel leaves the
slot empty, the replay does not touch it). The loader proves it from those writes' bodies, at most 64 per entity
(`InstantServerApplyReductionLimits.maximumWritesProvingAnEmptySlot`), and only in namespaces no delete can cascade into;
deletes and retracts leave no write keys, so the bodies are the only proof. Past the bound, or with a resident value in
the slot (#431), the full rebase decides, as before. The kept fact stays out of the plan's footprint, so it pulls no
pending write into the plan, and when the entity's first pending write created it, that write's receipt is patched the
way the full rebase's replay would rewrite it.

Measured on a Mac mini, debug, the fast-drain fixture with the list preview's unset field: the frame that restates a new
preview segment took 0.16 s and replayed 98 writes at 102 pending, 1.71 s and 998 at 1,002, 3.94 s and 2,000 at 2,004
before; 4.7 ms, 11.6 ms and 12.1 ms after, with none replayed.

## Known

#1383: once frames take longer than `acknowledgementDeferralLimitMilliseconds` (120 s), the acknowledgements queued
behind them expire, the live session is replaced, and older writes stay unconfirmed beneath confirmed newer ones, so
every later frame takes the full rebase (`nonPrefixWatermark`) until they are resolved. This release removes the trigger
that grew one device's queue to that size; whether a large queue left by any cause drains is #1383.

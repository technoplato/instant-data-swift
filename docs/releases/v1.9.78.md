## Before you upgrade

One public API addition, source compatible: `InstantProgressiveMediaReader.finishedRereadInterval` (2 s). A reader's
first `refresh()` of a stream now also calls its source's `fileURLs` once, while `segments` or `segmentsAt` runs, so a
custom `Source` may see those calls overlap. No storage change, no row change, no schema change.

## Release focus

**A player opening a progressive media stream waits for two reads in a row, not five** (#1916; red `b42666e7`, green
`4294224f`, ADR 0021 amendment `fa809f1c`).

- Before: a player made five reads in a row before it was ready: the stream's row and its listing for the first
  playlist request, the stream's row again for AVPlayer's second playlist request, the initialization segment's URL,
  then the first segments' URLs. Measured on a consuming app with 1.9.77, 2026-11-06: while a long stream was open and
  another device wrote, every one-shot read waited 2-3 s for the client's operation gate, so an 81-minute stream's
  first try failed after AVFoundation's 20 s and a 12.8-hour one loaded on its third try.
- Now: the first `refresh()` reads the URLs a player asks for first alongside the listing, in one `$files` read: the
  initialization segment's, the first page's, and while the stream records the page at its live edge, where a player
  of a live playlist starts. Their paths follow the stream's own naming (`segmentPath`), so the stream's row is enough
  to know them. The read is best effort: a player's own read of the same URL reports any failure. A refresh within 2 s
  of one that found the stream finished and wholly listed reads nothing.

```swift
let reader = InstantProgressiveMediaReader(streamID: stream.id, source: .live(client))
_ = try await reader.refresh()               // the row, then the listing and the first URLs together
let url = try await reader.url(forSegment: 0)  // kept: no read
```

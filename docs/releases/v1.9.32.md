## Release focus

**Progressive media's writer tries a failed row write again** (#1012; red `e1fd868d`, green `9e07d624`).

`InstantProgressiveMediaWriter.deliver()` stored each segment's file with a retry (1 s doubling to 60 s, reset only by
a success, no attempt while the network path is down), but wrote the segment's rows once: when `transact` threw, the
error ended delivery, and nothing after that segment was ever stored. `transact` fails only on the device, and one
way it does is a store that does not know the namespaces yet: the client learns an app's attributes from the server at
each `init-ok` and keeps them, so a fresh store's first rows, before its first connection, were refused with "does not
exist in the local schema". Every row write now goes through the same backoff as an upload, and nothing after it moves
first. A refusal (`permissionRejected`) still ends delivery, as a refused file does.

An app avoids the window altogether by declaring the rows' attributes in its runtime's `initialAttributes`
(`InstantProgressiveMediaStreamRow.instantAttributes`, `InstantProgressiveMediaSegmentRow.instantAttributes`); the
consuming app does so from its next build.

## What stays the same

No schema, migration or public API change. The spool's format is the same; a stream that a 1.9.26-1.9.31 writer left
with an unwritten row delivers it on its next `deliver()`.

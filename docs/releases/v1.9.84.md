## Before you upgrade

No public API change, no storage schema change, no behaviour change. One diagnostic gains fields:
`outbox.mutation.refused-write` (and so `session.health`'s last refusal) now names a validation refusal.

## Release focus

**A validation refusal names what the server found missing and the write it refused** (#2046; red `468d4ce2`, green
`3ae53b77`, merge on `main`).

- Why: a consuming app's device refused a write on its first offer with "Missing required attribute
  `recordings/startedAtMs`: f592cdd1 ..." (type `validation-failed`). The server's hint for that error is
  `{"records": [{"etype", "entity_id", "label", "attr_id", "is_required"}]}` (upstream `triple.clj`
  `validate-required!`), not a rule's `expected` and `input`, so `InstantMutationRefusal` read nothing from it and the
  log line carried `refusedNamespace`, `refusedCheck`, `refusedEntityIDs`, `refusedAttributes` and `refusedValues` all
  empty. The refused write (a row whose link is declared forward on the missing row, so its fact lives there) was
  named only by reading the device's store.
- Now: the records give the namespace, the entities and the missing attributes (`refusedCheck` reads
  `required attributes`); every refusal also names the namespaces the write set (`refusedWriteNamespaces`) and the links
  it made, `entity-prefix/label->target-prefix` (`refusedWriteLinks`, at most 4). For the case above:
  `refusedNamespace recordings`, `refusedEntityIDs f592cdd1-...`, `refusedAttributes
  durationSeconds,id,startedAtMs,title,updatedAtMs`, `refusedWriteNamespaces recordingRuntimeEvents`,
  `refusedWriteLinks 506054f4/recording->f592cdd1`.
- Upstream: Reactor.js orders its outbox by commit (`pushOps`: `order = max + 1`), so a link committed after the row it
  links to is sent after it; the consuming app's fix for this refusal (its writes waited on a queue time stamped before
  the operation gate) is in the app, which stops passing an explicit `createdAt` for those writes.

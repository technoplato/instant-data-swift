# Instant Swift Data 1.9.23

Status: published under the maintainer's standing authorization for fixes, typed on 2026-10-15: "Fix things when
they're broken. Don't ask me permission." and the instruction of 2026-10-23 to land every green step on main. The
checks that ran are below; the last code commit is `c2582e4b`. It carries 1.9.22 (#1015), 1.9.21 (#1006) and 1.9.20
(#1011, with #1007's frame parser).

## Release focus

Preparing a write no longer copies the store's indexes, and the store says which calls write its disk bytes (#1007).

1. **The store's indexes keep their entries in shards** (red `a540e9b6`, green `538de961`). A write is prepared on a
   copy of the store's indexes that shares their storage with the store, so its first change to each map copied that
   map whole: every entity's facts, every reverse ref, and each indexed attribute's value and entity maps (a Time
   Profiler trace of the test put 84% of a prepare in copying the indexed maps). A write therefore cost in proportion to
   the store, and a store grows as a recording does. `ShardedSet` and `ShardedDictionary` hold entries in 64
   copy-on-write shards chosen by each key's hash (canonically equivalent strings share a shard), so a prepared write
   copies the array of shards and the shards it changes. Coding converts to and from the plain dictionaries, so the
   stored form is unchanged.
2. **The storage write meter** (red `05bcafd7`, green `c2582e4b`). Every write transaction counts the pages SQLite
   wrote between `BEGIN` and `COMMIT` or `ROLLBACK` (`SQLITE_DBSTATUS_CACHE_WRITE`: the write-ahead log and the
   temporary file) under the store call that ran it, in `InstantStorageWriteMeter` (public, beside the energy meter). At
   most every 30 s the store logs `persistence.write-summary` at info: the bytes and transactions since the last summary
   and the twelve calls that wrote the most (`byCall`, `call=pages/transactions`).

## What stays the same

No schema or migration change, and no change to what any query, observer or write holds: the sharded collections answer
every question as `Set` and `Dictionary` do. The meter adds two counter reads per write transaction.

## Checks

- **Red, then green.** `InstantPrepareCopyCostTests`: twenty prepares of one line's write into 20,000 lines took 318.6
  ms against 32.7 ms into 2,000 (ratio 9.7); now 2.4 ms against 1.3 ms (ratio 1.9). `ShardedCollectionsTests`: random
  inserts, removals, defaults and copies over three seeds each answer as `Set` and `Dictionary` do, canonically
  equivalent strings and both zeros included. `InstantStorageWriteMeterTests`: a 200-fact snapshot save is counted
  under `saveStoreSnapshot(_:)`.
- **The whole suite** (a Mac mini, Xcode 27 beta, InstantSwiftDataCoreTests built alone) on main with the sharded
  indexes: 1,368 tests, no failure outside the baseline. The meter adds two counter reads and one counted update to the
  persistence transaction wrapper; its test and the page-churn and live-query result suites pass (10 tests). The whole
  bundle with the meter waits in the laptop's build queue (the Mac mini's disk is full); its result goes on #1007 and in
  the audit ledger.
- **Measured: the write harness** (release, a Mac mini, load 5-8; Recording 211's first 300 writes and a heartbeat every
  5 s against a 2,500-line recording, 40 bystander observers, the recordings list as seven pages shaped as the
  consuming app's list query; two interleaved rounds against main before the shards):

  | | before | this release |
  | --- | --- | --- |
  | 4 lines per other recording: instructions | 132.0, 131.9 G | 103.5, 106.5 G |
  | 4 lines: store prepare per write | 3.7, 3.2 ms | 0.7, 0.5 ms |
  | 200 lines per other recording: instructions | 233.4, 235.4 G | 130.3, 128.4 G |
  | 200 lines: store prepare per write | 19.0, 9.6 ms | 0.9, 0.6 ms |
  | 200 lines: per final, per interim | 1,496-1,525, 406-411 M | 679-737, 249-260 M |

  Observer refresh is the same (5.5-5.8 ms per write at 4 lines, 6.5-7.8 at 200): the hash a lookup takes to find its
  shard costs nothing measurable. The storage meter on the same harness: 309 KB of log pages per write, of which the
  server apply's commit 117 KB, the local save 112 KB, the acknowledgement 51 KB and the two claims 27 KB.
- **Not yet:** a device check. On a device, `instant:storePrepare` should fall, and `persistence.write-summary` names the
  store calls behind the tens of megabytes a minute a recording writes beyond its audio.

## Not changed here

- The outbox's insert, claim, acknowledgement and delete still move each row through up to nine indexes.
- A one-shot query rewrites its whole cached result on every call, unchanged or not.

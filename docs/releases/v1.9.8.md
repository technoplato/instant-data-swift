## Release focus

A refreshed live query's result is no longer rewritten to SQLite as one whole JSON blob on every refresh (#566): on
build 90 Michael's iPhone dirtied 1,074 MB in 185 s after launch, with 92 of 99 samples in the server apply's commit.
A dead socket no longer keeps the app applying its old frames before it reconnects (#474); an infinite query keeps
the pages its window loaded from the local store when the server first answers (#516); a typed decode that meets a
field the local store does not hold says so (#522); and live room presence and topics behave as upstream Reactor.js
keeps them, off the operation gate and out of SQLite (#461).

## What changed

0. **A live result's JSON is written at most once per query per 30 s (#566).** Every server apply upserted each
   refreshed query's whole result as one JSON blob (`instant_live_query_results.json`), and the WAL again. Upstream
   Reactor.js writes only the query subscriptions that changed, throttled (100 ms, then an idle callback up to 1 s),
   and flushes before unload. Now a refresh whose facts and page info match the stored JSON writes only the row's
   count and time, which #441's refusal resolution reads. A changed result's JSON is written at most once per query
   per 30 s; meanwhile the newest result is kept in the persistence actor, where every reader in the process reads it
   (the retraction diff, the prune, page info), and the ownership rows stay exact on every refresh. A waiting result
   is written when it is due, by a timer one interval later, when its query unsubscribes, when the connection closes,
   and by the new `flushPendingLiveQueryResults()` on the runtime and the client, which the app calls on background
   and terminate. Each waiting result is marked in `instant_sync_metadata`, and the next bootstrap rebuilds a marked
   result from its ownership rows before anything reads it, so a kill between writes cannot keep a fact the server
   deleted. Measured on a 1,100-row query refreshed 100 times about 1 s apart, each refresh changing one row (debug build,
   `aLongRecordingsRefreshesWriteLittleResultJSON`; the table is under "Red on 1.9.7, green here"): 100 result JSON writes
   became 3, 2.03 MB of JSON per refresh became 61 KB, and 515 SQLite pages per refresh (2.1 MB) became 33 (136 KB).
   #567 tracks persisting per-fact deltas, as Reactor.js persists only changed keys.
1. **A dead connection's buffered query results are skipped (#474).** On the Mac on 2026-10-03 (Scribe 0.1 (82),
   library 1.9.2) the socket was reset at 11:52:48 with frames waiting in the live session's receive buffer, which
   handed the reader's error to the applier only after every frame received before it; the app applied 125 more
   frames over 18.5 minutes, offline throughout. Now, when the reader's error arrives, the buffer drops the waiting
   query results (`add-query-ok`, `add-query-exists`, `refresh-ok`), which the next connection's `add-query` answers
   replace, as Reactor.js drops a replaced transport's messages, and the socket reconnects once the frame being
   applied ends. The answers to this device's writes and every other frame are still applied in order. Logged as
   `websocket.dead-connection-results-dropped`.
2. **The kickstart keeps the window's pages (#516).** An infinite query pages from the local store until the server
   answers. At its kickstart it dropped those pages and subscribed one live page, so a window loaded to two pages fell
   back to one: live-stamp's trace (session 5216df8d, 08:07:20 on 2026-10-04) showed Michael's list go from 24 rows
   to 12. Now the kickstart loads as many live pages as the window showed, as `loadNextPage` would, and the last
   snapshot stays until the last of them answers. Logged as `infinite.kickstart.restore-page` (info), which is how the
   fix is confirmed on a device: its test does not fail on v1.9.7 (see below), and #575 tracks one that reproduces
   live-stamp's trace.
3. **A missing field is reported as missing (#522).** A query that selects some fields stores only those facts, so
   another query that decodes the whole entity can meet it without one. The decode error now says the local store
   has no value for the field and why, and its recovery names `decodeQuarantiningFailures(_:)`, instead of "Expected
   string". `InstantRowQuarantine` is public (`init()`, `decode(_:as:operation:)`), so a caller that decodes the same
   rows again and again (Scribe's media retry scan, every 5-7 s) reports a damaged row once.
4. **Rooms as Reactor.js keeps them (#461).** Room peers are keyed by session, so two sessions of one user are two
   members. A live runtime keeps presence and topic messages in memory, without SQLite or the operation gate, and
   applies room frames beside the query applier. Presence observations can select keys, peers and the local session,
   and `isRoomJoined(_:)` says whether the server confirmed the join on the current connection (Reactor.js
   `isLoading`). ADR 0019 records the parity.
5. **One ordered lane per room (#461).** Off the operation gate each send writes from its own task, so two presence
   writes, or two topic publishes, could reach the socket in either order: `racingPresencePublishesLeaveTheNewestOnTheWire`
   failed 1 of 3 runs in this release's first dev run, and v1.9.5 had serialized topic publishes under the gate.
   Reactor.js writes with a synchronous `ws.send`, in call order. Each room's presence writes and broadcasts now take
   one lane, first in, first out, in the order the live session recorded them. The `join-room-ok` flush holds the lane
   across the room's newest presence and the broadcasts queued before the join; a presence write queued behind it with
   an older publication is skipped, so peers never see 3, 2, 3; broadcasts are never skipped. A write that wakes to a
   closed socket or a room left and rejoined does not write: a broadcast goes back among the queued ones in
   publication order for the next join, or is dropped when its room was left, as Reactor.js's `publishTopic` returns.
   A queued broadcast whose write fails is queued again instead of dropping the rest; a direct publish whose own write
   fails throws to its caller, as before. ADR 0019 decision 9 records the lane.

## For users of the library

- **API:** additive; no public API is removed and existing call sites compile.
  - New: `flushPendingLiveQueryResults()` on `InstantRuntime` and the client (call it on background and terminate);
    `InstantRowQuarantine` (`init()`, `decode(_:as:operation:)`); `InstantRoomPresenceSelection` (`keys`,
    `peerIDs`, `includesLocal`, `.all`, `apply(to:)`, `changed(from:to:)`); `peerID` and `isLocal` on room members
    and topic messages; `isRoomJoined(_:)` on the runtime and the client; the client's
    `observeRoomPresence(room:selection:)`; the runtime's `observeRoomTopicEvents(room:topic:)`.
  - Changed signatures, with defaults: `InstantRuntime.observeRoomPresence(room:)` gained
    `selection: InstantRoomPresenceSelection = .all`; the `InstantRoomPresenceMember` and `InstantRoomTopicMessage`
    initializers gained `peerID: String? = nil`.
- **Behavior:**
  - A refreshed live query's stored result may lag its newest result by up to 30 s while the app runs; nothing in the
    process reads the older copy, and the next launch rebuilds a result the app did not flush.
  - After a socket dies, the runtime reconnects as soon as the frame it is applying ends; query results the dead
    socket had buffered are not applied, and the new connection's answers replace them.
  - An infinite query whose window showed several pages before the server answered keeps them at the kickstart.
  - A typed decode's missing-field error has a new message and recovery.
  - Rooms: each session is its own member, so an app that filtered out its own presence by user ID now also sees its
    own other sessions; a peer member's `id` is `…:peer:<session id>`; `observeRoomTopicMessages` emits the most
    recent 128 messages; with a live connection, presence and topics are no longer stored in SQLite (the CLI's local
    cache keeps them).
- **Storage:** no schema or data migration.
- **Dependencies:** unchanged from 1.9.7.

## Correctness contract

- Local writes complete after local materialization and durable outbox persistence, never after an implicit cloud wait.
- Offline writes survive relaunch, drain in order, and preserve newer optimistic state during server refresh.
- Rejection is isolated per mutation, query, stream, and media item. Removing a refused write leaves the server's
  values, as upstream does.
- Rapid open-segment rewrites remain monotonic through finalization.
- Swift→TypeScript and TypeScript→Swift lanes must report zero lost, duplicate, reordered, or finalized-regression
  updates.
- Linked and infinite-query fixtures must preserve bounded result cardinality and deterministic result counts.
- Entity delivery and progressive audio/media transfer remain independent.

## Performance contract

Run:

```bash
validation/run-performance-gate.sh deterministic
validation/run-performance-gate.sh live
```

Default policy requires:

- Swift p50 and p95 latency no slower than the pinned TypeScript core.
- Swift throughput at least equal to TypeScript for equivalent work.
- Scribe-shaped physical-footprint and retained-query memory tests to pass.
- Durable enqueue, offline restore, and reconnect drain to meet the same ratio policy.
- Compiler and runtime warnings to remain at zero.
- Every correctness and performance comparison to emit zero failures.

# What a local write's gate hold measures on the Mac mini (#1491)

2026-10-31. Library at `main` `13cdf499` (1.9.56 plus ledgers) and earlier commits, the `recording` contention exercise
of #1074 (`Tests/InstantSwiftDataCoreTests/RealSize/ContentionExercises.swift`, fixture version 3), Mac mini M4 (4
performance and 6 efficiency cores), release. Follows the #1482 audit's finding F0.

## Bottom line

F0 said a local write holds the operation gate 4.6 times longer at 1.9.56 than at the 2026-10-24 baseline (steady p50
1.58 ms at `287f77d1`, 7.22 ms at `0ddbaa62`) and a bisect by day put the jump on 2026-10-26. **The baseline commit run
alone on the mini holds 5.02 ms** (12:44, nothing else in a build slot). The 1.58 ms ran beside another job's cold
build. The day bisect compared runs from different jobs in different machine states, and none of 10-26's code runs in
the exercise. What moved the number was the machine, not a commit; the one-job A/B below says how much, if any, is the
code's.

**What the write's own cost did, measured in one job (perf-gate-1491-final, 16:11-16:37):** three wastes inside the
write are gone, and the same transact in a tight loop went from **0.476 ms at `13cdf499` to 0.389 ms at `4ff5e5c4`
(-18%)**, each of three runs within 0.011 ms. Beside load the steady hold went 3.00 -> 2.69 ms (one round). The issue's
target of 2.5 ms came from the confounded 1.58 ms; alone, every commit holds 4-7 ms, because the hold is mostly CPU at
the clock an idle machine's cores run at, and nothing in a later commit put it there.

## Why the machine state moves the number 3-5x

- Every job on the mini runs under `nice -n 10 taskpolicy -c utility` (build.sh's mini runner), so every thread of the
  exercise is clamped to utility QoS.
- The exercise writes one transcript line every 667 ms; each write is a burst of a few milliseconds after an idle gap.
  With nothing else running, the burst starts on idle, clocked-down cores, mostly efficiency cores under the utility
  clamp. Beside another job the clusters are already busy and clocked up.
- So a run beside a build measures warm cores and a run alone cold ones. Between d1025 (beside a UI test) and d1026
  (alone) every line slowed together, including `read.local`, which never takes the gate: 0.67 -> 3.34 ms; the claim
  1.04 -> 4.45 ms; the plan 0.54 -> 2.29 ms.
- The same transact in a tight loop (the cross-SDK runtime benchmark, 300 back to back) takes 0.456 ms on the idle mini
  (#1482 M4): a loop keeps the cores busy.
- The exercise's runs all print the same setup shape (recordings=352 lines=8712 ... closed_result_facts=75640).

other slot):

## What changed in the write itself

The write's own CPU is about 3 ms on the M4 in the #1482 sample (`performTransact` 237 ms of samples over 90 writes,
its persistence and store turns inline). Three costs inside it were waste and are gone:

- `02b7cf8a`: the admission encoded the whole mutation to sorted-key JSON to count its bytes against the 8 MiB limit,
  then the save encoded the same body again. The bound now reads the bytes the save writes: one encode a write
  (`InstantLocalWriteEncodeTests`: 10 writes, 10 body encodes, was 20).
- `d564a099`: the two SHA-256 digests a save writes (its receipt and its wire intent) formatted each byte with
  `String(format:)` and joined them: 333 allocations a digest (laptop, debug; the `d564a099` message says the mini, which
  is wrong), about 70 of them CryptoKit's own hash. The
  digest's bytes are now read in place and their hex written into one string; the text is the same.
- `4ff5e5c4`: the save computed the forward wire-intent fingerprint (a sorted-key encode of the transport mutation and a
  SHA-256) for every row it wrote, but it decides only a row that already holds a server acceptance or was offered to
  delivery. A new write's row holds neither, so it is no longer computed for it; the stored body's decode is unchanged.

The receipt fingerprint itself (a sorted-key encode of the transaction and its rollback, and a SHA-256, about 0.38 ms a
write in the sample) is #1497's, as is the acknowledgement's re-encode.

perf-gate-1491-final measured each step in one job on the mini (release; debug suites first: 125 tests in 8 suites
passed, 15 known issues as on main; the wire red `aa18c4af` failed its count and `4ff5e5c4` passed). The cross-SDK
runtime benchmark's transact, p50 of three runs of 300, and the recording exercise's steady transact hold p50, one
round:

| Commit | Tight-loop transact | Hold alone | Hold beside six busy loops | Reconnect drain |
| --- | --- | --- | --- | --- |
| `13cdf499` (main before) | 0.477, 0.476, 0.472 ms | 6.83 ms | 3.00 ms | 0.88 ms |
| `02b7cf8a` (one encode a write) | 0.452, 0.452, 0.442 | 6.56 | 3.07 | 0.88 |
| `aa18c4af` (the hex; the wire red) | 0.420, 0.411, 0.406 | 6.40 | 3.21 | 0.80 |
| `4ff5e5c4` (no wire fingerprint for a new row) | 0.389, 0.392, 0.389 | 4.08 | 2.69 | 0.79 |

The tight loop is the write's own cost: -18% from main. One round alone cannot tell 4.08 from the others' spread
(mediaanalysisd used 20-160% of a core beside the alone runs); beside load the hold fell 0.3 ms. Evidence:
`~/Sync/audit/perf-gate-1491/mini/ab-1491c/`.

The same runs' energy lines (#1492's, the library's meter over the exercise's minute) say what the hold is made of, and
why alone is slower. The durable save (`localSave`, one per write, 90 a run) is on the CPU for all but 5-10% of its
wall time, and it takes twice the CPU time alone:

| Run | `localSave` CPU a call | Its wall a call | Steady transact hold p50 |
| --- | --- | --- | --- |
| `aa18c4af` alone | 3.47 ms | 3.63 ms | 6.40 ms |
| `aa18c4af` beside load | 1.58 ms | 1.70 ms | 3.21 ms |
| `4ff5e5c4` alone | 3.22 ms | 3.39 ms | 4.08 ms |
| `4ff5e5c4` beside load | 1.50 ms | 1.64 ms | 2.69 ms |

So the hold is mostly the save's own CPU, and alone the same instructions take 2.1-2.2 times the CPU time: the write
runs slower, it does not wait (measured). Which cores ran it was not recorded; the likely mechanism is the job's utility
QoS keeping an idle machine's work on its efficiency cores while six busy loops push it onto the performance cores
(inference). Either way it is the machine's state, as F0's 4.6x was, and #1514's cause. The save here
is a transcript line's (about 50 operations and an 18 KB body, #1510's table), where the tight loop saves one todo:
beside load the save is 1.6 of the hold's 2.7 ms, the store's prepare about 0.3 ms, and the reads, the commit, the status
read and the hops the rest. Inside the save, the receipt fingerprint (#1497) and the SQLite pages (#1510) are the other
lanes' work.

## What is still in the hold

The M6 sample's write, after these three: the receipt fingerprint (#1497), the SQLite commit's log writes (about 0.3
ms), the store's prepare (0.2 ms), the status read (0.12 ms) and one read that grows with the outbox: the creation cursor,
the outbox's newest row in delivery order, which no index holds in that order. SQLite scans every row of the
global-effect index and sorts for it (`SCAN ... USE TEMP B-TREE FOR ORDER BY`), as do the server apply plan's begin and
extend: 39 samples a minute in M6, 18 of them inside the transact's hold. On the outbox's schema with the phone-shaped
store's 700 rows a read takes 291 us, 29 us with an index, and 2.25 ms at 5,400 rows, an hour of lines written offline
(laptop, Python sqlite3). That index is #1491's amendment 3, measured on its own.

## Amendment 3: the outbox tail is one entry of a creation-order index

`e712d3e3` puts a full index on (`created_at_ms`, `mutation_id`) in place at every open; the three tail reads keep
their SQL. Measured on the Mac mini (release) in one job, perf-gate-1491-tail-ab (19:25-19:43), `e10668ae` (the red:
the same SQL, no index) against `d8185dde`, the recording exercise twice alone and twice beside six busy loops:

| Line (steady p50, means of two rounds) | Before | After |
| --- | --- | --- |
| Transact hold beside load | 2.70 ms (2.65, 2.75) | 2.60 ms (2.36, 2.83) |
| `write.line` beside load | 3.38 ms | 3.08 ms |
| "plan server apply" hold beside load | 1.35 ms | 1.04 ms |
| `serverApplyPlan` CPU a call alone (energy lines, about 860 calls) | 852 us | 807 us |
| Pages a step (the storage exercise, 120 writes): save, claim, ack, echo | 16.79, 2, 4, 19.97 | 17.79, 2, 4, 20.97 |

The tight loop (one todo, a small outbox) moved 0.680 -> 0.674 ms: the scan grows with the outbox, and the exercise's
outbox holds the phone-shaped store's 663 refused writes. The holds' spreads overlap at two rounds; the plan's CPU per
call, about 45 us less, is what an index in place of a 700-row scan and sort predicts (two tail reads a frame over about
six plan calls). The cost is the index's page on the save and on the echo: #1115's budget of 24 outbox frames a write
is 25 now (23.0 -> 25.0, `aWritesOutboxRowsWriteNoBTreeTwice`), and a claim and an acknowledgement write none of it.
A guard plans every statement a recording's live writes run with the index and without it: 4 of 66 changed, the two
tail reads (no sort), the catch-up's whole count (it scans the smaller index) and its count of the writes appended after
the plan's tail (a range search where it scanned the outbox); none reads more. Offline, where every new line stays in
the outbox, each read grew by about 0.42 us a row (laptop); it no longer grows. Evidence:
`~/Sync/audit/perf-gate-1491/mini/ab-1491e/`.

The metered VFS (#1245), which F0 listed at 136 ms a minute: in the M6 sample its frames hold 549 samples, 539 of them
the I/O it wraps (pread 249, the checkpoint's F_FULLFSYNC 160, pwrite 130), about 8 its own. It costs about 8 ms of one
core a minute here, so it is not a #1285 problem.

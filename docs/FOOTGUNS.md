# Footguns: traps found while building on this library, each with its cost, its rule and its guard

Every entry below was found by measurement after it cost a consuming app energy, disk, bytes or time: a live query that
restated a megabyte per write, a write that rewrote fourteen b-trees, a gate held for a whole result, a connection left
on cellular for an hour. Each entry says what you see, what it cost and under which conditions, the rule that avoids it,
the issues that hold the history, and the test that keeps it from coming back (#1244).

Read an entry before you add a live query, a write path, an index, a wait or a file transfer. When you find a new trap,
add it here with its number, its rule and a guard test in the same change.

How an entry reads:

- **Symptom**: what you see.
- **Measured cost**: the number, its conditions (machine, configuration, store size) and its source.
- **Rule**: what avoids it.
- **Issues**: the issues and the library commits that fixed or guarded it.
- **Guard**: the test that fails when the footgun comes back, with its gate, or a proposed guard where none exists.
- **Upstream**: the vendored Instant source the behavior comes from, when it comes from the server or `Reactor.js`.

Gates (how much a guard guards):

- **always**: a plain `swift test` asserts it.
- **measurement pass**: skipped unless `INSTANT_SWIFT_DATA_MEASUREMENTS=1` (the second, serial pass of
  `scripts/known-failing-tests.sh run`).
- **release only**: runs in debug but asserts only when optimized (`RealSizeBudget.isOptimized` or `.isEnabled`; the
  release gate `validation/run-performance-gate.sh`).
- **exercise only**: an env-gated exercise that prints numbers and asserts little; nothing fails when the footgun
  returns.
- **known issue**: the test records the cost with `withKnownIssue` until the fix lands, so the fix flips it.
- **partial**: a test holds part of the rule; the entry says which part is unguarded.

Where a cost is "on the phone-shaped store", it was measured on `RealSizeShape.phone` (one device's counts: 352
recordings, 8,712 lines, 9,455 account files, 2,283 attributes), generated by `RealSizeFixture`. "A device store copy" is
a read-only copy of a store a device held. The appendix lists the fixtures a guard can use.

## Read path

### Live queries and refreshes

<a id="f1"></a>
#### F1. Size a live query for its refresh, not its first load

- Symptom: every transaction that changes a row a live query shows makes the server resend that query's whole result
  (`refresh-ok`), so bytes received per write follow the result's size, not the change. The writing session receives
  its own echo too.
- Measured cost: library exercise `eachStepOfALiveWrite` (release, synthetic store): a 256-line page receives
  126.07 KB per write for 9 changed facts (895 triples restated), 759 MB over a simulated hour against 6.1 MB sent; a
  64-line page 41.77 KB; a 16-line page 12.60 KB (93 triples), and the echo's CPU falls 6.83 -> 1.59 ms (#1117,
  `docs/audits/2026-10-24-storage-io-baseline.txt`). On a device recording with a 64-line window plus list queries:
  ~700 MB an hour of `refresh-ok` (130-270 KB a frame); with a 16-line window, a 4-line write-time tail and #1239's
  split, 122.8 MB in an hour (4,899 frames). Client work also followed the page: 32/64/128/256-line refresh with one
  line changed = 13,877/23,555/43,159/85,300 allocations (E03, before #1147).
- Rule: keep what changes in a small bounded window (newest N, N about 16) and read history as one-shot or frozen
  pages that stop changing. Before shipping a live query, read its bytes per write by shape from the wire meter.
- Issues: #1117, #1116, #1147, #653, #1124. Library f52532b2 / 9936ffe4 (per-query wire meter, v1.9.45); consuming app
  564fd1ddc (16-line window + 4-line tail).
- Guard: `Tests/InstantSwiftDataCoreTests/InstantWireMeterTests.swift: InstantWireMeterTests/aRefreshCountsEachComputationUnderItsQueryShape`
  (always; proves the meter, no budget); `Tests/InstantSwiftDataCoreTests/RefreshCostTests.swift:
  RefreshCostTests/decodingARefreshFrameCostsLittlePerLine` (always; decode allocations per line, not bytes);
  `StorageIOExercises/eachStepOfALiveWrite` (exercise-only). Consuming app: `ScribeRecordingTimelineQueryTests`,
  `ScribeRecordingWholeTimelineTests` (always; pin the 16 + 4 shape). No always-run bytes-per-write budget. Propose
  `InstantRefreshBytesBudgetTests/aWriteToALongRecordingReceivesWhatTheWindowHolds` (always):
  ```swift
  let meter = InstantWireMeterStorage()
  let fixture = try await FastDrainFixture.make(suffix: "bytes", serverSegmentCount: 400, timelineWindow: 16, wireMeter: meter)
  try await fixture.writeSegments(1)                    // warm: registration + first answer
  let before = meter.snapshot()
  try await fixture.writeSegments(8)
  let perWrite = (meter.snapshot() - before).receivedByQuery["transcriptionSegments/16[recordingID]"]!.bytes / 8
  #expect(perWrite < 16 * 1_200, "a write received \(perWrite) B for a 16-line window")   // 400 or 4,000 lines: same
  ```
  (`FastDrainFixture` needs a `wireMeter:` parameter; the frames already go through `InstantLiveMessage.decoded(fromFrame:meter:)`.)
- Upstream: `upstream/instant/server/src/instant/reactive/session.clj:467-534` (`handle-refresh!`: recompute every
  stale query of the session, `group-by :result-changed?`, send each changed computation whole).

<a id="f2"></a>
#### F2. Never rely on a nested `limit`: the server sends every child

- Symptom: an include written with `limit 1` / `limit 2` / `limit 24` arrives with every child of every parent on
  every refresh. The library trims to the limit after decode, so the screen looks right while the wire, the frame
  parse and the store walk pay for all children.
- Measured cost: a list of 12 recordings with 240 images each: 2,892 attachment rows and 1,666,864 bytes per refresh
  with a nested limit of 24, against 24 rows and 13,216 bytes through two has-one links; 1 recording with 2,400
  images: 1,390,607 -> 1,120 bytes (#1100, admin queries on a throwaway app). In production 34 recordings held more
  than 24 attachments (max 550), and a live row's heartbeat refreshed that page every 5 s. Earlier the same trap on
  `segments.limit(2)` made memory and CPU grow with recording length until preview has-one slots replaced it (#044).
  Still open: the list's `transcriptions` include ("limit 1") sends every transcription of every row (bounded only by
  the data, at most 2 a recording).
- Rule: bound a list row's children with has-one links written in the child's own transaction (preview slots), or
  with a top-level query; treat a nested `limit` as a client-side trim only. An architecture test lists every
  has-many include of a list query with its reason.
- Issues: #1100, #044, #155, #1147. Library 7c567126 (docs: nested limits do not bound the network), 48456fac /
  94f9ff30 (trim persisted children per parent); consuming app 7fb9ea4a8 (preview slots), deb9caa74 (has-one
  `audioAttachment`/`previewImage`).
- Guard: consuming app `Tests/ScribeSharedSupportTests/ScribeRecordingListPreviewLinksTests.swift:
  ScribeRecordingListPreviewLinksTests/everyIncludeOfTheListsQueriesIsBoundedOnTheServer` (always; allowlists
  `transcriptions`). Library `Tests/InstantSwiftDataCoreTests/InstantLiveQueryNestedLimitMemoryTests.swift:
  nestedLimitIsPerParentNotGlobal`, `nestedLimitFollowsRecordingIDStringWhenRefTriplesAreAbsent` (always; the local
  trim, not the wire). Missing in the library: a test that a scripted refresh carrying 50 children for a `limit 2`
  include still meters every child's bytes, so nobody "fixes" the docs into a promise. Propose
  `InstantNestedIncludeLimitTests/aNestedLimitTrimsTheStoreButNotTheWire` (always): `LiveReactorParitySession` answers
  a `limit 2` include with 50 children; assert the emission holds 2 and the wire meter's `receivedBytes` grows
  linearly with 50 (20 vs 50 children).
- Upstream: `upstream/instant/server/src/instant/db/instaql.clj:924-928` (`page-info-of-form` orders and pages only
  when `(= level 0)`); `upstream/instant/client/www/app/docs/instaql/page.md:422` ("limit is only supported for
  top-level namespaces right now").

<a id="f3"></a>
#### F3. Select `fields` on every live query that should not hear unrelated writes

- Symptom: a query without `fields` reads every attribute of its rows, so a write to any attribute (a duration tick,
  a JSON summary, a timestamp) invalidates it and, if the result changed, resends it whole.
- Measured cost: the title-number query selects only id, title and startedAtMs, so per-final `speakers` and duration
  writes do not refresh its 300 KB (about 500 rows) result; the list queries without a narrow selection carry a
  14.7 KB build-info JSON per recording and again per nested transcription, 83% of the list results' value bytes,
  and refresh on every final's summary write (store copy; build 144 ledger: the list page holding the live recording
  53.8 MB in 916 refreshes over about two hours). Client side, before #1007 a page that selected a few fields still
  materialized every field and link set of its rows.
- Rule: give every live query a `.select` of what its reader draws, at every include level, so writes to other
  attributes neither invalidate it nor ride its refresh. A select must still hold every field a strict decoder of that
  namespace requires (next entry but one).
- Issues: #1007, #1239, #1244. Library 73a836cb (a page that selects fields materializes only those), 023ff4af.
- Guard: library `Tests/InstantSwiftDataCoreTests/InstantLiveQuerySelectedAttributesTests.swift:
  aLevelWithoutFieldsSelectsEverySingleValueAttributeOfItsNamespace` (always; pins the server rule locally) and
  `InstantSelectedFieldsMaterializationTests/aPageThatSelectsFewFieldsCostsTheSameWhateverLinksItsRowsHold` (always).
  Nothing guards the consuming app's list selection (build-info rides today). Propose an architecture test in the app:
  `ListSelectionBudgetTests/theListRowSelectsNoFieldItNeverDraws` (always): take
  `ScribeRecordingListRequest.listQuery(viewer:).plan`, collect `fields` at every level, and
  `expectNoDifference(Set(fields).intersection(["buildInfo","configurationJSON","clipboardEntries","systemAudioContextEntries","media","captureGapsJSON"]), [])`
  with an allowlist carrying the reason for each field kept.
- Upstream: `upstream/instant/server/src/instant/db/instaql.clj:1142-1158` (`etype-attr-ids`: with `fields`, only
  those attribute ids plus id; without, every attribute of the namespace).

<a id="f4"></a>
#### F4. Keep a live query's key stable: a key that changes re-downloads everything

- Symptom: a query whose InstaQL changes with app state (a limit computed as 5,000 x N recordings; a `$in` over the
  12 newest rooms) is a new subscription each time N or the set changes: the server answers the whole result again,
  and each old generation stays on disk as an unloaded result.
- Measured cost: `lineSpeakers/{5000 x N}`: the largest held result, 2.33 MB at N=42, plus seven closed generations
  (`/175000` .. `/205000`) of 2.28 MB each in the unloaded-result table, re-downloaded about seven times in two
  days; each change inside it restates 1.35 MB. `recordingSpeakers/{256 x N}`: eight generations, 0.24-0.27 MB each.
  `agentResponses/24` over the 12 newest rooms: a new key per new recording, 22 closed generations (1.0 MB) in the
  same table. Separately, a client that registers new keys forever grows session maps (one acknowledgement entry per
  key ever registered, about 380 restarts in 16 minutes); E06 measured 3,151 B of heap kept per closed lease over 300
  distinct queries (#541, #1075). #541's fix was never merged (see Guard).
- Rule: build a live query's key from stable inputs (the owner, a fixed page size), and filter or cap in the reader;
  when the input set must change, page or query per item instead of re-keying one big query. Count distinct keys per
  shape in a session.
- Issues: #541, #1075, #1244 (filed findings), #1081. Library red 60770190 / fix 36c4dc4d (interner rebuilt past
  twice the live ids, acknowledgement forgotten on unregister) sit only on branch
  `agent/claude-opus-5.5/library-79-199`: not ancestors of main (checked at 486accdd).
- Guard: NONE on main: `InstantSessionMapBoundsTests` exists only on that unmerged branch; merging it is the cheapest
  guard on this list. Nothing guards a key that changes with N. Propose in the consuming app `LiveQueryKeyStabilityTests/aLearnersKeyDoesNotGrowWithTheRecordingsItHeard`
  (always): build the learner's line query for 3 and for 40 recordings and `expectNoDifference` the two plans'
  `limit` (and, library side, an `InstantRuntime` debug counter `distinctKeysByShape` that a test asserts stays 1
  while N grows).
- Upstream: `upstream/instant/server/src/instant/reactive/session.clj` (`add-query` keys a subscription by its whole
  InstaQL); the client's `Reactor.js` likewise keys `querySubs` by the query hash.

<a id="f5"></a>
#### F5. Do not hold a list query over the row every write touches

- Symptom: a list (or a "follow these ids" query) that includes the row a recording writes on every final or
  heartbeat is restated whole per write: one row's change costs the whole page or set.
- Measured cost: a "Without Audio" follow over 86 recordings with their previews restated about 1.15 MB per final
  plus about 1 MB a minute (the minute's duration write): ~85% of the socket's bytes, 294.5 MB in 25 minutes, until
  the live recording moved to a small group of its own (#1239; then ~32 KB per final). After that fix the list page
  holding the live recording was still 42% of `refresh-ok` bytes in an hour (51.2 MB / 858 refreshes) and the
  remaining follow group 22%: ~64% of bytes are recording rows restated in list queries because each final rewrites
  the recording's summary fields. A 5 s duration heartbeat as a durable write refreshed every subscribed list 12 times
  a minute on every device (#1097) and made another device's list re-render ~50 times a minute (#1154: 35.6% of a
  core on the follower).
- Rule: keep per-write summary fields (counts, durations, previews) off rows that list queries hold, or isolate the
  live row in its own one-row query; send heartbeats as room presence, not durable writes.
- Issues: #1239, #1117, #1097, #1154, #1195. Consuming app 9286432e4 (follow split), 71b91e816 / 98bd3191a (beat as
  presence, duration once a minute).
- Guard: consuming app `Tests/ScribeSharedSupportTests/RecordingsWithoutAudioFollowTests.swift:
  aRecordingWrittenInTheLastMinutesIsFollowedInAQueryOfItsOwn`, `theRecentQueryHoldsAtMostEightRecordings`
  (always). Library `Tests/InstantSwiftDataCoreTests/InstantIncludePlanSkipTests.swift:
  aHeartbeatRefreshesOnlyThePageThatShowsTheRecording` (always; the local side only: other pages skip the change).
  Nothing bounds the server side. Propose `RecordingListRefreshBytesTests/aFinalRestatesOneRow` in the app's store
  harness: count the triples of the result a final's summary transaction changes for the list page; assert at most
  one recording's triples are restated, or record a known issue with #1239.
- Upstream: `reactive/session.clj:467-534` (whole changed result per refresh).

<a id="f6"></a>
#### F6. Select fields inside every include, not only at the top level

- Symptom: an include without its own `.select` brings whole child entities, so every JSON blob on the child rides
  every refresh of the parent query (a list row carries its transcription's build info and configuration JSON, and
  whole attachment rows).
- Measured cost: in the list-shaped live results on a device store copy, the recording's and its transcription's
  build-info JSON are 40-45% each of the bytes (83% of the list results' value bytes together); a 12-row page is
  561 KB stored (946 triples) and a frozen page 597 KB, where the drawn fields are a small fraction. Each refresh of
  the page holding a live row resends all of it.
- Rule: give each include level a selection of the fields its reader draws, and keep large JSON (build info,
  configuration, context windows) on a detail query that only a detail screen opens.
- Issues: #1244 (finding 1), #1100, #1007. No fix landed yet for the transcription include's whole-entity read.
- Guard: NONE for the consuming app's includes. Library `InstantLiveQuerySelectedAttributesTests/anIncludeSelectsForTheNamespaceItsLinkLeadsTo`
  (always) pins how selection resolves per level. Propose extending the app's
  `ScribeRecordingListPreviewLinksTests` with `everyIncludeOfTheListsQueriesSelectsItsFields` (always): for each list
  plan, `#expect(include.fields != nil, "\(name).\(include.name) reads every attribute")` with an allowlist and reason.
- Upstream: `upstream/instant/server/src/instant/db/instaql.clj:1142-1158` (each form, child forms included, reads
  `etype-attr-ids` of its own `fields`).

### Infinite and paged queries

<a id="f7"></a>
#### F7. Expect an infinite query to download its first page three times

- Symptom: opening an infinite query subscribes a starter page; when it answers full, the coordinator retires it and
  subscribes a forward chunk from the same start cursor (the same rows again) and a reverse watcher; when the window
  pages on, the forward chunk is frozen by re-subscribing its range with `after`/`before` and no limit (the same rows
  a third time). Every later page is downloaded twice (live, then frozen).
- Measured cost: a device's first minute on the consuming app's build 144: the list's live chunk shape 6 answers /
  1,516,147 B and its frozen shape 4 answers / 1,284,137 B; stored, one 12-row page is 561 KB live and 597 KB frozen,
  so page 1 alone costs about 1.7 MB at launch where one answer would be 0.6 MB.
- Rule: keep infinite-query pages small and narrowly selected (the cost is multiplied by three); do not open an
  infinite query for a list that fits one bounded page; when changing the coordinator, count add-query answers per
  row at launch.
- Issues: #1244 (query inventory B1 suspect 5), #516, #388, #070, #1030. Library 3fd98ded (#516: keep the pages a
  pre-bootstrap window loaded), b465ae14 (#388: one entity listed once).
- Guard: `Tests/InstantSwiftDataCoreTests/InstantInfiniteQueryLeadingRowsTests.swift:
  aWindowLoadedPastOnePageBeforeTheServerAnswersKeepsItsPagesAtTheKickstart` (always; correctness of the hand-over,
  not its cost). No guard counts downloads. Propose `InstantInfiniteQueryWireTests/theFirstPageIsAnsweredAtMostTwiceAtLaunch`
  (always): a `LiveReactorParitySession` serving 40 rows, page size 10; open, `loadNextPage()` once, wait for the
  snapshot; sum the rows across every `add-query-ok` the session answered; `#expect(rowsAnswered <= 2 * 20)` as a
  known issue today (it is 3x), so a fix flips it.
- Upstream: `upstream/instant/client/packages/core/src/infiniteQuery.ts:453-506` (starter, then `pushNewForward(startCursor, true)`
  and `pushNewReverse`), `:365-395` (`freezeForward` re-subscribes the chunk's range). The library mirrors it

### One-shot reads and the result caches

<a id="f8"></a>
#### F8. Never loop one-shot reads: each answer is a server apply and a stored result

- Symptom: `queryOnce` through the socket registers a query, applies its answer like a live result (a server-apply
  commit) and leaves the answer stored; after the query ends, the next prune copies it into the unloaded-result table.
  A reader that re-asks on every answer turns into a write storm.
- Measured cost: a played-lines reader asked about 5 times a second while media played: 9,315 server applies and
  10.23 GB written to flash in 21 minutes (650-875 MB a minute against 14-27 MB normally), CPU 27.5% of a core against
  12.7%; about 1.09 MB physical per commit for a 164.6 KB passage; 810 one-shot answers (66.9 MB) left in the unloaded
  table. A later store copy still held 248 + 249 such answers (39.1 MB).
- Rule: read ahead in large spans and treat what was read as read; answer repeat questions from memory or the local
  reader (`queryLocally`); count one-shot reads per minute per shape and alarm on a loop.
- Issues: #1215, #1134, #932, #317. Consuming app 184472527 (a read ahead of the player counts as read); library
  7e8460c5 / 8aa690b0 (one-shot reads off the operation gate), f8f39ca0 / 7699425a (an answer that lands after its
  one-shot ended is not applied), 6dce825d (answer from the device when the exact subscription is already answered).
- Guard: `Tests/InstantSwiftDataCoreTests/InstantOneShotReadGateTests.swift: aOneShotReadAnswersWhileAnotherCallerHoldsTheGate`,
  `aOneShotReadStillCachesItsAnswer` (always); `InstantStoredFileLookupTests/answerAfterTheOneShotQueryEndedIsNotApplied`
  (always). Consuming app `PlayedLinesStateTests/aReadAheadOfThePlayerCountsAsRead` (always). Nothing bounds one-shot
  reads per minute. Propose a library counter guard `InstantOneShotStorageTests/aOneShotAnswerLeavesNoLiveResultBehind`
  (always): offline-free runtime with a scripted socket, run `queryOnce` 20 times for 20 distinct keys, prune, and
  assert the unloaded table holds at most the query cache's bound (or that one-shot answers go only to
  `instant_query_cache`, which is byte-bounded).
- Upstream: `Reactor.js` keeps a one-shot's `querySubs` entry like a subscription's (the GC in the next entry).

<a id="f9"></a>
#### F9. Bound the result caches by bytes, not by triple count

- Symptom: closed and one-shot results move to `instant_unloaded_live_query_results` and stay up to a year, collected
  only past 1,000 entries or 1,000,000 triples; a result of 11 triples holding one large JSON value counts as 11.
- Measured cost: a device store copy: the unloaded table is the largest b-tree in the file, 112.76 MB (959 results,
  111.66 MB of JSON) against 97.87 MB of facts; 248 one-shot results of 11 triples each hold 38.71 MB. Unloading also
  copies each closed result whole: 61.7 MB of log and 1.1 s of CPU to unload 47 results on the phone-shaped fixture;
  on a real store copy the first prune after open wrote 35.6 MB of WAL and read 111.8 MB (#1122). Every copy leaves
  free pages the file never returns (#1015).
- Rule: collect unloaded results by stored bytes and age measured in days, and keep one-shot answers in the
  byte-bounded query cache (`maxEncodedJSONBytes: 1_000_000`) instead of the live-result tables.
- Issues: #1122, #1107, #1015, #1215, #1129. Library ffd14777 (#1131: a closed result reloads in bounded holds),
  6590a7e4 (#1129: 1,000-fact prune batches).
- Guard: NONE on the bound. `InstantInactiveLiveQueryPruneMemoryTests/sessionPruneUnloadsInactivePagesWhileOutboxHasOptimisticOverlay`
  (always) covers what is unloaded, not how much stays. Propose `InstantUnloadedResultBoundTests/largeResultsAreCollectedByBytes`
  (always): a store with policy `maxEntries: 1_000, maxTripleCount: 1_000_000` and a new `maxEncodedJSONBytes: 2_000_000`;
  persist and close 20 results of 11 triples with a 200 KB string each; prune; assert
  `SUM(LENGTH(json)) FROM instant_unloaded_live_query_results <= 2_000_000`.
- Upstream: `upstream/instant/client/packages/core/src/Reactor.js:468-471` (`querySubs` GC: `maxAgeMs` one year,
  `maxEntries: 1000`, `maxSize: 1_000_000` triples) and `utils/PersistedObject.ts:355-450`; the library copies the
  defaults (`Sources/InstantSwiftDataCore/InstantRuntime.swift:465-469`). A browser's IndexedDB is not a phone's
  flash; a byte bound is an adaptation to document.

<a id="f10"></a>
#### F10. Let one subscription feed many observers, but count the observers too

- Symptom: identical InstaQL is one server subscription (registrations are ref-counted by the encoded query), but
  each observer keeps its own local store observation, and every publication walks every observer.
- Measured cost: one account-access query observed by about 10-14 local observers and one list-scope query by four;
  62-74 observers open while recording; the walk over every observer (`observerRefresh`) cost 1.23% of a core
  recording in front and 0.31% in the background (#1081); before #654/#1007 skipped observers that cannot show a
  change, `observerRefresh` averaged 20% of a core (85% at peak minutes) while recording (#1007).
- Rule: share one observation per query in the app (one stream, many readers) and end per-minute scan observations at
  Stop; in the library, a publication must skip observers whose result the change cannot reach.
- Issues: #1081, #1007, #654, #653. Library c086d927 (#654: refresh only observers that show the change),
  47333e5e (#1007: an entity held neither before nor after refreshes nobody), b7e619bf (#1007: a page with includes
  skips a change it cannot show), 8d912a74 (#653: an observer is not handed an equal result, as Reactor.js
  `notifyOne` drops a deep-equal result).
- Guard: `Tests/InstantSwiftDataCoreTests/InstantPageRefreshEnergyTests.swift:
  anUpdateThatKeepsAnEntitysPlaceRefreshesOnlyThePageThatShowsIt` (always), `InstantIncludePlanSkipTests/aNewLineRefreshesOnlyThePageThatShowsItsRecording`,
  `anAttachmentNoPageCanReachRefreshesNoPage` (always), `InstantUnresolvedEntityRefreshTests` (always). Nothing counts
  duplicate observers in the consuming app. Propose an app test `ScopeObservationSharingTests/theFourListClientsShareOneScopeObservation`
  (always): start list, Without Audio, title numbers and Recently Deleted against a counting fake client and
  `#expect(fake.observeCalls(for: accessQuery) == 1)`.
- Upstream: `Reactor.js` (`querySubs` keyed by query hash, `notifyOne` drops deep-equal results).

<a id="f11"></a>
#### F11. Key result-cache rows by a small id, never by the query's text

- Symptom: every ownership row of the live-result cache repeated its query's whole InstaQL JSON as its key, and both
  indexes over it held that key too, so each index entry spilled to its own overflow page.
- Measured cost: a device store grew 197.5 MB -> 546.7 MB within minutes of a release's first connect: 32,555
  ownership rows (17,698 distinct triples, 40 query keys) took 328.9 MB with their two indexes; keys averaged 1,671
  bytes (max 4,306), 54.4 MB of key text, 26,596 overflow pages per index with 64.6 MB of each unused (#704).
- Rule: give each cached result an integer id and key every per-row table by it; keep the query text in one row.
- Issues: #704. Library 2f776bb5 (red), a6fa6662 (green: `query_id INTEGER PRIMARY KEY`, ownership `WITHOUT ROWID`),
  released in 1.9.11.
- Guard: `Tests/InstantSwiftDataCoreTests/InstantLiveQueryCompactOwnershipTests.swift:
  aNewStoreKeysOwnershipByAnIntegerQueryID`, `aLongKeyedResultsOwnershipStaysUnderTheIssuesBound` (always);
  `aDevicesStoreConvertsAndAnswersEveryOwnershipReadAsBefore` (exercise-only, `INSTANT_704_DEVICE_STORE`).
- Upstream: - (the client keeps `querySubs` in IndexedDB keyed by hash; the SQLite layout is the library's own).

### Decoding and the stored value encoding

<a id="f12"></a>
#### F12. Do not let a synthesized `Codable` shape become the storage format

- Symptom: every stored value is written as Swift's synthesized enum coding, the case name wrapping the value under
  `_0` (`{"string":{"_0":"..."}}`, `{"number":{"_0":1}}`), and that text is part of the fact table's `WITHOUT ROWID`
  primary key (`entity_id, attribute_id, value_json`) and of the lookup index, so the wrapper is paid in the table, in
  every index entry and on every comparison.
- Measured cost: a device store copy: `instant_triples` 402,191 rows, 25.19 MB of value text against 17.21 MB as plain
  JSON (+46%); `instant_live_query_triples` 21,606 rows, 2.46 vs 1.53 MB (+60%).
- Rule: choose a stored value encoding on purpose (a type tag column plus the plain JSON value, or a compact tagged
  form), version it with a migration, and keep `Codable` synthesis for API types only.
- Issues: #1244 (finding 2), #1121 (the table layout that holds the key). No fix yet.
- Guard: `Tests/InstantSwiftDataCoreTests/FootgunGuardTests.swift: FootgunGuardTests/aStoredStringCostsItsJSONPlusAShortTag` (always; a known issue, #1251, until the stored encoding changes; added with this page). Earlier: NONE on size. `Tests/InstantSwiftDataCoreTests/InstantStoredJSONTests.swift:
  theStoredTextIsJSONEncodersText` (always) pins the wrapper byte for byte (compatibility, not cost). Propose
  `InstantStoredJSONTests/aStoredStringCostsItsJSONPlusAFewBytes` (always), a known issue until the format changes:
  ```swift
  let stored = try InstantStoredJSON.stored(.string("abc"), using: JSONEncoder())   // {"string":{"_0":"abc"}}
  withKnownIssue("#1244: the synthesized wrapper adds 18 bytes to a string") {
    #expect(stored.utf8.count <= #""abc""#.utf8.count + 4)
  }
  ```
- Upstream: - (the wire carries plain JSON values in `[e, a, v, t]` triples; the wrapper is the Swift client's own).

<a id="f13"></a>
#### F13. Select every field a strict decoder of that namespace requires

- Symptom: a field-limited query stores its rows with only the selected fields; the device keeps one row per entity,
  so a later strict decode of the same entity by any reader fails on a field the store never got.
- Measured cost: one partial attachment row (no `fileExtension`, stored by a lookup that selected 5 fields) failed
  every media retry scan for two builds, on two devices, so no pending upload or download after it was retried (#522);
  not measured in bytes.
- Rule: a `.select` keeps every required field of its namespace, or the query is listed as knowingly partial with its
  reason; decode a list with quarantine (`decodeQuarantiningFailures`) so one bad row cannot fail the rest.
- Issues: #522, #483. Library 5797457f (a missing field is named as missing, pointing at quarantine), 07ce2e5d
  (`InstantRowQuarantine` public).
- Guard: consuming app `Tests/ArchitectureTests/FieldLimitedInstantQueryTests.swift:
  everyFieldLimitedQuerySelectsEveryFieldItsSchemaRequires`, `everyKnownPartialQueryStillLeavesFieldsOut` (always);
  library `Tests/InstantSwiftDataTests/InstantRowQuarantineTests.swift` (always).
- Upstream: - (the browser client keeps one entity map per store too; strict typed decoding is the Swift client's).

<a id="f14"></a>
#### F14. Check query shape against the server's schema, not a test store

- Symptom: a local or test store accepts query shapes the server refuses: ordering by an attribute that is not
  indexed and typed, or naming a link in a field selection. The refusal shows only on a device, as a failed query.
- Measured cost: ordering `settingsDevices` by an unindexed `createdAtMs` was refused on every device of one build, so
  no settings row was ever saved and production held none (#551); a recovery read selecting a link label failed on a
  device with "selected field 'recording' references an undeclared field" (#557). Not measured in bytes.
- Rule: run an architecture scan that checks every `.order` attribute is indexed and typed and every `.select` names
  only attributes in the checked-in schema; keep schema drift a build failure.
- Issues: #551, #557.
- Guard: consuming app `Tests/ArchitectureTests/InstantQueryOrderIndexTests.swift:
  everyAttributeAQueryOrdersByIsIndexedAndTyped` and `Tests/ArchitectureTests/FieldLimitedInstantQueryTests.swift:
  noFieldSelectionNamesALink` (always). The library's local query engine accepts both shapes; a library-side check
  in `InstantQueryPlan` validation against the init-ok attributes (`indexed`, `checked-data-type`) would catch it for
  every consumer (proposal).
- Upstream: `upstream/instant/server/src/instant/db/instaql.clj:960-966` (order validation: "Only indexed and typed
  attributes can be used to order by", cardinality one only).

### SQLite read plans and indexes

<a id="f15"></a>
#### F15. Repeat a partial index's condition word for word, and force it with `INDEXED BY`

- Symptom: the store's lookup index is partial (`WHERE attribute_id IN (...)`, five attributes); a lookup whose SQL
  does not repeat that condition cannot use it, and SQLite scans the fact table. The store has never been `ANALYZE`d
  (no `sqlite_stat1`), so the planner has no statistics to fall back on.
- Measured cost: a plain lookup on a device store copy scans about 380,000 rows (53 ms on a Mac) where the indexed one
  reads a handful (#1244 finding 4, `scripts/perf/query-plans.py` in the consuming app). Building the index reads the
  whole table once (one device's store held 1.6 GB at the time).
- Rule: build lookup SQL from the same function that builds the index's condition and add `INDEXED BY`, so a mismatch
  fails at prepare instead of scanning; `EXPLAIN QUERY PLAN` every hot statement in a test; decide about
  `ANALYZE`/`PRAGMA optimize` deliberately.
- Issues: #1006, #1244, #1245. The library already does this (`SQLiteReadConnection.entityIDs`,
  `SQLitePersistenceStore.lookupIndexCondition`).
- Guard: `Tests/InstantSwiftDataCoreTests/FootgunGuardTests.swift: FootgunGuardTests/aLookupReadsThePartialIndexAndTheSameLookupWithoutItsConditionScans` (always; added with this page: the library's lookup statement plans as a search of `instant_triples_lookup`, the same lookup without the index's condition as a scan of the table). Earlier: `Tests/InstantSwiftDataCoreTests/InstantLocalReadTests.swift: aRelaunchedStoreReadsTheLinesItKeepsOnDisk`
  (always; reaches the `INDEXED BY` lookup, which fails to prepare if the condition drifts). No plan assertion. Propose
  `InstantLookupPlanTests/theLookupSearchesThePartialIndex` (always), using the `queryPlan(_:in:)` helper from
  `RealSize/OutboxClaimScaleTests.swift` on a fixture with `lookup: true`: `#expect(plan.contains { $0.contains("USING INDEX instant_triples_lookup") })`
  and `#expect(!plan.contains { $0.hasPrefix("SCAN instant_triples") })` (needs an `entityIDsSQLForTesting` accessor).
- Upstream: -.

<a id="f16"></a>
#### F16. Keep big sorts out of launch: an `OR` of `IN` lists sorts in a temp b-tree

- Symptom: the launch's resident-fact load selects `entity_id IN (<retained ids>) OR entity_id IN (SELECT ... FROM
  instant_outbox_effect_entities) ORDER BY entity_id, attribute_id, value_json`; SQLite plans it as `MULTI-INDEX OR`
  plus `USE TEMP B-TREE FOR ORDER BY`, so every launch writes a sort of every resident fact to temp storage.
- Measured cost: on a clone of a device store (2,475 retained entity ids, 66,110 facts, 13.9 MB; read connection's
  `cache_size -2048`): 14.0 MB physical / 17.5 MB logical written by the sort in 0.47 s. Launch at the phone's size:
  553 ms, 2.3M allocations, 583 MB allocated, 22 MB written (#1107, before #1149).
- Rule: read retained facts by joining a temporary table or `json_each` of ids in key order, with no `OR` and no
  `ORDER BY` the index does not already give; check launch statements with `EXPLAIN QUERY PLAN` for `TEMP B-TREE`.
- Issues: #1107, #1149, #1245. Library 4c190959 (#1149 step 1: facts read from columns; E07 allocations 3.24M -> 1.65M)
  leaves the sort.
- Guard: NONE on the plan. `RealSize/MemoryExercises.swift` E07 asserts the launch's allocations and retained bytes
  (exercise-only, `INSTANT_MEMORY_EXERCISES=1`). Propose `InstantLaunchPlanTests/theResidentFactLoadNeedsNoTempSort`
  (always): expose the load's SQL (`loadStateTriplesSQLForTesting`), run `EXPLAIN QUERY PLAN` on a small store and
  `#expect(!plan.contains { $0.contains("USE TEMP B-TREE") })`.
- Upstream: `upstream/instant/client/packages/core/src/Reactor.js:466` (`preloadEntryCount: 10`: the client loads ten
  stored results at start and any other only when its query subscribes).

<a id="f17"></a>
#### F17. Advertise a client version that lets the server skip `attrs` on every refresh

- Symptom: the server picks session features from the `@instantdb/core` version the client advertises; a client that
  advertised only its own name got the whole attribute list (`attrs`) inside every `refresh-ok`, and parsed and
  re-resolved it per frame.
- Measured cost: 447 attributes were about 134 KB of a 151 KB frame; frames fell from 173 KB to 43.6 KB once the
  version was advertised. Rebuilding the schema lookups per frame cost 728 ms CPU for 50 refreshes against 357 ms with
  a cached context (debug) (#303).
- Rule: advertise the newest `@instantdb/core` version whose features the client decodes (v0.22.75 here; above it the
  server batches messages, which this client does not decode), and cache the attribute context per session revision.
- Issues: #303, #1111. Library 778c793b (advertise v0.22.75), f5fed905 (reuse the attribute context).
- Guard: `Tests/InstantSwiftDataCoreTests/InstantReactorParityTests.swift: theInitAdvertisesTheCoreVersionThatSkipsAttrs`,
  `aReconnectsInitAttrsReplaceTheCachedAttrs` (always); `Tests/InstantSwiftDataCoreTests/InstantLiveRefreshAttributeCostTests.swift:
  translatingARefreshResolvesTheSchemaOncePerRefresh` (always).
- Upstream: `upstream/instant/server/src/instant/reactive/session.clj:96-118` (features by client version,
  `supports-skip-attrs?`) and `:520-530` (`attrs` added only when the session cannot skip them or they changed).

### Observation, first emission and deferred hydration

<a id="f18"></a>
#### F18. Pay for the schema once per attribute revision, not per observe or read

- Symptom: every `observe`, `queryOnce` and local read built an attribute store of the whole schema and validated
  against it; each refresh rebuilt nested-limit maps of every attribute; so the cost of opening a 32-line observation
  followed the schema's size (2,283 attributes in the consuming app), not the answer.
- Measured cost: observation first emission of 32 lines: 7,866 allocations / 81M instructions with 571 attributes
  against 15,272 / 212M with 2,283; a local read of the same 32 lines 28.6M against 85.2M instructions; observing and
  closing one query 14.1 MB and 5,144 allocations at 2,283 attributes against 1.6 MB at 170 (E06); the nested-limit pass
  3.2 MB for a 64-row page with no nested include (#1111, #1147). After the fix the local read is 714 allocations,
  119 KB, 0.46 ms at both sizes (was 5,127, 12,443 KB, 5.22 ms).
- Rule: keep one indexed attribute store per attribute revision and share it across validation, sends, refreshes and
  hydration; never sort or map the schema inside a per-call path.
- Issues: #1111, #1150, #1147. Library a641f2ea (observation open and local read take the store's attribute index),
  a9751099 (nested-limit pass without schema maps), 553cb332 (hydration finds its attributes in one pass), f834c614
  (budget tightened). Still open: `queryOnce`'s gate path and the send resolver.
- Guard: `Tests/InstantSwiftDataCoreTests/RealSize/RealSizeBudgetTests.swift: RealSizeBudgetTests/budgetsAtTheRealSize`
  rules `queryLocally.first-32` (1,500 allocations) and `observe.first-emission-32` (known issue #1111) (release-only);
  `RefreshCostTests/aPageWithNoNestedIncludePassesThroughTheNestedLimitPass`, `hydratingAnEmissionDoesNotMapTheSchema`
  (bounds release-only). Propose an always-run twin: `ObservationSchemaCostTests/openingAnObservationCostsTheSameWith16Or2283Attributes`,
  one-thread allocations (`RealSizeAllocations.start(onCurrentThreadOnly: true)`) of `prepareObservation` on two
  in-memory stores declaring 16 and 2,283 attributes; `#expect(big <= small * 3 / 2)` (a ratio, so load-proof).
- Upstream: `Reactor.js` `_setAttrs` keeps one attribute store per session.

<a id="f19"></a>
#### F19. Register an observer without holding the store across its send and its reload

- Symptom: registering an observer held the one operation gate across its `add-query` socket send and the reload of
  its unloaded result, so every write and read queued behind a screen opening.
- Measured cost: gate holds of 5.0-7.8 s on devices across six builds, 1.8 s for one whole-file-list registration in
  the exercise; over a 150 ms socket each registration held the gate p50 154 ms and writes waited p50 77 ms (#1131).

  24 ms). A later build still logged one 46.9 s hold by "observe standard live query" at a first launch after a
  migration (cause not known).
- Rule: record the registration under the gate, send and reload outside it, in bounded chunks; log every hold over
  250 ms with its holder and what waits.
- Issues: #1131, #1134, #1074. Library 0b0650d9, ffd14777, 821e592a.
- Guard: `Tests/InstantSwiftDataCoreTests/InstantObserverRegistrationGateTests.swift: anObserversAddQuerySendHoldsNoGate`,
  `aClosedResultsReloadReadsOutsideTheGate`, `aClosedResultReloadsInBoundedHolds` (always).
- Upstream: - (the browser client runs on one thread and has no store-wide gate; the gate is this library's own).

<a id="f20"></a>
#### F20. Hydrate deferred values for what changed, not for every row of every emission

- Symptom: large text and words JSON are deferred (kept out of the hot store and read from SQLite when an emission
  needs them), but each hydrating emission re-reads every row's deferred values, so a one-line change re-reads the

- Issues: #1110, #1147, #044, #1006, #1133. Library 437ee8fb (deferred residency), e7dacb2d and ffbd3e87 (deferred
  values read from columns), 553cb332. Open: per-emission re-read (#1110).

  `text`, take `runtime.persistence.deferredValueDecodeMetricsForTesting().valueCount`, write one row, await the
  emission, `#expect(delta <= 2)` under `withKnownIssue("#1110")` until fixed.

  long-running recorder).

<a id="f21"></a>
#### F21. Make a page refresh cost its change on the client too

- Symptom: applying a `refresh-ok` rebuilt the previous result to diff it, re-materialized and re-hydrated the whole

- Issues: #1147, #1109, #1116, #654. Library a9751099, 553cb332, 3e787d2d, 560540fe, ffbd3e87.

#### F22. End a screen's live queries when it leaves the screen or the app leaves the foreground

  one-shot "first answer" reads with a helper that cancels.
- Issues: #655, #394, #1102, #1100. Library 18e52df0 (an observation ends when its consumer stops iterating).

### Memory

<a id="f23"></a>
#### F23. Load what stored results own at launch, and let go of what no result owns

- Symptom: the hot (in-memory) store was the whole database at first; once scoped to what stored results own, it still
  keeps every row the session wrote, so resident facts grow at the write rate until relaunch; and the launch decoded
  every stored result to find what to keep.
- Measured cost: scoping the bootstrap to live-query entities plus pending writes took a test corpus from 1,000 to 32

## Write path

### Writes and the outbox

<a id="f26"></a>
#### F26. Keep the outbox row's b-trees to what a live write needs

- Symptom: every queued write's row is inserted, claimed (two updates), acknowledged (the whole encoded body re-encoded and rewritten) and deleted at the echo; with the table, its key, eight indexes, a rowid write-key table and a rowid effect-entity table, each step rewrote pages of up to 14 b-trees, and most of a write's log went to bookkeeping, not facts.
- Measured cost: 34.0 of a write's 62.5 log frames (54%; about 140 of 251 KB of log) per logical write on the synthetic 7,000-line store (`eachStepOfALiveWrite`, `steps-outbox all outboxFramesPerWrite=34.00`, Mac mini M4, release, Apple SQLite 3.54.0); 60.68 of 145.70 frames on the phone-shaped store; on a real 19.9 KB row a claim dirties 9 pages and an acknowledgement 11 where a same-size update dirties 2 (`phone-store-pages.sh` E2). An index added to speed the claim (#1108) cost 2 more frames (8 KB of log) on every write. Fixed in two slices: 36 -> 30 -> 23 outbox frames per write; all log frames 64.5 -> 44.9; with the other storage fixes the simulated hour's SQLite writes went 1,157.8 -> 1,006.5 MB and full fsyncs 211 -> 184 for slice 2 alone (`docs/audits/2026-10-24-storage-io-fixes.txt`).
- Rule: every index on a hot table costs a page write on every row change, so keep only the indexes a hot statement uses (prove each with `EXPLAIN QUERY PLAN`), make rare-state indexes partial on literal predicates, key whole-row tables `WITHOUT ROWID`, and keep mutable delivery state out of the encoded body.
- Issues: #1115, #1076, #1108, #653; library red 8101f0b9 / green c343c563 (slice 1), red 84a6195b / green 12f487e1 (slice 2). The bodies-in-their-own-table slice is unbuilt (a live body averages about 4 KB).

#### F29. Keep server-apply staging out of SQLite temp files

### The operation gate and Swift concurrency

<a id="f33"></a>
#### F33. Hold the operation gate only for work in proportion to the change

- Symptom: nearly everything (local writes, reads, observer registration, acknowledgements, server applies, prunes, compaction) passes one serial operation gate; a server apply's plan decoded and encoded every restated fact under it, a prune released a closed result as one batch checking ownership one fact at a time inside the frame applier, and a refused write's discard copied, diffed and reloaded the whole store, so every writer, acknowledgement and status read waited the whole hold, and gate-free reads waited on the same actors.

#### F37. Do not run blocking SQLite on the cooperative pool, and donate priority through the gate

### Found with SQLite's own counters (#1245)

<a id="f59"></a>
#### F59. Keep small mutable columns out of a row that holds a large blob

- Symptom: a claim or an acceptance that changes a delivery column's size rewrites the row's whole overflow chain:
  SQLite overwrites a record in place only when its payload size is unchanged. `instant_outbox` stores its delivery
  columns after `json`; `instant_live_query_results` keeps its count and time beside the result JSON.
- Measured cost: 55% of the claim and acceptance frames in a device store copy's write-ahead log (#1245).
- Rule: keep columns that change on every step in a narrow row of their own, or in fixed-size encodings before the
  blob, so a step rewrites one leaf page and never the overflow chain.
- Issues: #1245, #1115, #1123.
- Guard: none yet. Proposed (always): on `StorageIOWriteCycle`, a claim and an acceptance write no overflow page

### The queue and the server apply (#1270)

<a id="f65"></a>
#### F65. Never let a server frame's cost grow with the outbox: a queue that slows its own drain never recovers

- Symptom: one device's outbox grew from 0-1 to 2,316 pending writes in two hours of recording and never drained. Every
  frame that restated the recording peeled and replayed every pending write, so each accepted write cost more the
  longer the queue was; acknowledgements, reads and local writes queued behind the operation gate, live queries timed
  out, and 2-14 writes were accepted a minute while recording wrote 45-85. A drain rate that falls as the queue grows
  has a tipping point: once it is below the write rate, the queue grows, which lowers the drain rate further.
- Measured cost: device (2026-10-27 16:47-19:00, three builds): 49 of 51 gate-held lines `full rebase:
  changesShadowedFact`, 1,073-2,093 writes replayed for one frame, holds 700-5,347 ms. The trigger: the outbox keeps a
  write's keys under the names the write used, and a link the server issued an id for (`recordings/previewImage`) is
  written under its forward identity and held, in the store and in every frame, under the id. The reduction (#296)
  looked the slot's pending writers up by the id, found none, saw the store not showing the server's value (it showed
  the newest pending screenshot), and declined; the replay put the pending value back, so the next frame declined the
  same way. Laptop, debug, the fast-drain fixture in the device's write shape: one frame 0.25 s at 105 pending, 2.8 s at
  1,001, 7.0 s at 2,002, every pending write replayed every time; a drain of 60 accepted writes from 1,001 pending
  replayed 58,290 writes in 173 s. The device's own store through the phone-replay gate: the first window's 75-fact
  frame declined on the same attribute id and replayed 1,093 writes (44 s in debug). After the fix (1.9.48): one
  frame 4-9 ms at 105-2,002 pending, none replayed; the 2,002-write drain 24.7 s applying (60 accepted writes took
  410 s before); a recording minute at 70 writes on 2,002 pending: 2,002 -> 7 (the whole-component rebase: 2,002 ->
  2,063); the device's store drains 1,241 -> 0 in 9.9 s, 78 frames, none rebased.
- Second trigger (#1378, 2026-10-29, 1.9.50): the same device's queue grew from 29 to 524 pending writes in eight
  minutes after a relaunch mid-recording, and past 3,000 within the hour, with every gate-held line `full rebase:
  changesShadowedFact` on `transcriptionSegments/retiredAtMs` (139-2,827 writes replayed per frame, 0.3-3.1 s). The
  app's list preview selects an optional field no write sets, and the server restates it as `null` on each segment the
  list newly shows. While a pending write shadows that segment (the summary that moves the preview slot on restores the
  link to it), the no-writer branch found nothing in the store and declined. "The rebase runs once: the next frame
  holds" was true per entity, but a live recording names a new entity on every line, so every line's frame declined.
  Before the relaunch the queue held 0-16 and each such rebase was small; the relaunch's backlog tipped it.
- Rule: a server frame's work is in proportion to what it changes, never to the queue. Look an outbox key up under
  every name a write can give the slot (`AttributeStore.forwardWriteNames(of:)`), or key it by the slot the store and
  the server use. A decline into the whole-component rebase must not repeat on the next frame for the same reason, and
  not on the next entity either: when it does, it is a bug in the reduction. A slot the store leaves empty that no
  surviving write sets or removes takes the server's fact without the rebase (1.9.51): the full rebase would leave the
  same fact there. The gate-held line names the reason (#932) and, from 1.9.48, the
  attribute that decided it (`declinedAttributeID`), so a device's own logs say which slot keeps declining.
- Issues: #1270, #1378, #296, #932.
- Guard: `InstantFastDrainTests/aLinkWrittenUnderItsNameDoesNotForceARebase`,
  `theReducedApplyObservesWhatTheFullRebaseObservesWithAttachments` and `aDeclinedFrameNamesItsAttributeInTheGateHeldLine`
  (always); `measureOneFrameAgainstTheQueue`,
  `measureTheDrainOfTheQueue` and `aMinuteOfRecordingShrinksAQueueOf2000` (measurement pass); the phone-replay gate,
  whose model server now resolves a link's written name to its id (it kept the name, so no replay could show this).
  #1378: `thePreviewsUnsetFieldDoesNotForceARebase`, `aPendingRemovalOfThePreviewsUnsetFieldLeavesWhatTheFullRebaseLeaves`
  and `theReducedApplyObservesWhatTheFullRebaseObservesWithThePreviewsUnsetField` (always);
  `measureANewPreviewSegmentsFramesAgainstTheQueue` (measurement pass).
- Upstream: `Reactor.js` `dataForQuery` reapplies every pending mutation to each query's server result on each change
  (`_applyOptimisticUpdates`), in memory; this library keeps one materialized store and replays durable receipts under
  its operation gate, so the same queue-sized work costs disk and the gate. The reduction exists to keep it off the
  common frame.

## Appendix: measuring a footgun, the fixtures a guard can use

Every path below is under `Tests/InstantSwiftDataCoreTests/` unless it
says otherwise. "Always runs" means a plain `swift test` runs and asserts it. Four gates decide whether a guard actually
guards:

| Gate | What it means | Where it runs |
| --- | --- | --- |
| none | runs and asserts in every `swift test` | every bundle run, `scripts/known-failing-tests.sh run` |
| `.measurement` trait (`InstantTestMeasurement.swift`) | skipped unless `INSTANT_SWIFT_DATA_MEASUREMENTS=1`; whole-process CPU, footprint, wall-clock or diagnostics-hub counts | the second, serial pass of `scripts/known-failing-tests.sh run` |
| `guard RealSizeBudget.isOptimized else { return }` | the test runs in debug but asserts nothing; the bounds were measured in release | `swift test -c release` (`validation/run-performance-gate.sh` runs the whole package in release with `--no-parallel`) |
| `.enabled(if: RealSizeBudget.isEnabled)` | the real-size budgets: on in optimized builds, `INSTANT_REAL_SIZE_BUDGETS=1` forces, `=0` disables | release runs; the release gate runs it with `INSTANT_REAL_SIZE_BUDGETS=1` |
| env-gated exercise (`STORAGEIO_EXERCISES=1`, `INSTANT_MEMORY_EXERCISES`, `INSTANT_CONTENTION=1`, `INSTANT_MEMORY_REPLAY`, `INSTANT_REAL_SIZE_REPORT`, `INSTANT_MEMORY_SITES`, device-store paths like `INSTANT_1121_STORE`) | prints `KEY key=value` lines for before/after diffs; asserts little or nothing | by hand, through `scripts/storage-io/`, `scripts/memory-exercises/`, `scripts/contention-exercises/` |

A footgun whose only cover is an env-gated exercise is listed as guarded "by exercise only" in the ledger: nothing
fails when it comes back.

### Disk: the counting VFS (`RealSize/StorageIOCounters.swift`, `RealSize/StorageIOExercises.swift`)

- **What it measures.** A pass-through SQLite VFS in front of `unix`. Per file kind (`.database`, `.wal`,
  `.temporary`, `.temporaryJournal`, `.transient`, statement journal): write calls and bytes, reads, syncs and full
  syncs with their time, truncates, deletes; every write-ahead-log frame with the page behind it
  (`walFrames`, `walFramesByPage`); pages a checkpoint copies (`databasePagesWritten`); pages read from the database
  (`databaseReadsByPage`). `StorageIOPageMap.read(store:)` maps pages to b-tree names through `dbstat`, so a count
  can be asserted per table or index (`map.byName(snapshot.walFramesByPage)["instant_outbox"]`).
- **How a guard calls it (always-run pattern, no env needed).** Copy `OutboxBTreeFrames.measure(label:)` in
  `InstantOutboxBTreeWritesTests.swift` or `TemporaryFiles.measure(label:_:)` in
  `InstantServerApplyTempJournalTests.swift`:

  ```swift
  StorageIOCounters.install(asDefault: false)
  let run = try StorageIORun(label: label); defer { run.remove() }
  StorageIOCounters.watch(directory: run.directory); defer { StorageIOCounters.watch(directory: nil) }
  let settings = StorageIOExerciseSettings(stepLines: 4, recordingLines: 30, pageLines: 16, minutes: 1,
                                           linesPerMinute: 15, fixtureScale: 1)
  var cycle = try await SQLitePersistenceStore.$connectionVFSForTesting.withValue(StorageIOCounters.vfsName) {
    try await StorageIOWriteCycle.make(label: label, directory: run.directory, settings: settings)
  }
  try await cycle.writeLine(into: StorageIOLedger())          // warm: statements prepared
  let ledger = StorageIOLedger()
  for _ in 0..<4 { try await cycle.writeLine(into: ledger) }  // or writeLine(into:overlapping: true), prune(into:),
                                                              // echoTheFirstOfABacklog(lines:into:)
  let echo = ledger.io(.echo)                                 // steps: .save, .claim, .ack, .echo (and the prune)
  ```

  `StorageIOWriteCycle` drives the consuming app's line writes (three interims, the final, the summary, the duration
  tick) through a real `InstantRuntime`, answered by `FastDrainServer` with an acknowledgement and a `refresh-ok`
  carrying full results. Suites that use the shim are extensions of `StorageIOExercises` (`@Suite(.serialized)`)
  because the counters are process-wide.
- **Examples that always run:** `StorageIOExercises/theCountersSeeWhatSQLiteWrites` (the shim's self-check),
  `aWritesOutboxRowsWriteNoBTreeTwice`, `aLiveWriteWritesNoRareStateIndex`, `anEchoWithAWritePendingWritesNoTemporaryFile`,
  `aBacklogsFirstEchoWritesNoTemporaryFile`, `aReSavedEntityWritesOnlyTheLeafItsFactsShare`,
  `aPowerLossWithALongLogKeepsEveryWriteTheLastCheckpointSynced`.
- **Opt-in exercises** (`STORAGEIO_EXERCISES=1 swift test -c release -Xswiftc -enable-testing --filter StorageIOExercises`):
  `eachStepOfALiveWrite`, `theStoreOverASimulatedHour`, `liveWritesOnThePhoneShapedStore`,

### Query plans and SQLite steps (`RealSize/OutboxClaimScaleTests.swift`)

- `queryPlan(_ sql:, in url:)` (private there; copy it): `EXPLAIN QUERY PLAN` through a read-only connection of its
  own, one detail line each. Assert `plan.filter { $0.hasPrefix("SCAN instant_outbox") && !$0.contains("COVERING INDEX") }`

  `SQLitePersistenceStore.immediateSupersessionTailSQL`; a dynamically built statement needs a `...SQLForTesting`
  accessor.
- SQLite virtual-machine step counters on the persistence actor: `automaticDeliveryCandidateReadStepsForTesting()`,
  `unknownActiveOverlayCheckStepsForTesting()`. The pattern "N rows of junk cost what 7 do" (`manySteps <= fewSteps + 50`)
  is load-proof and fast on `RealSizeShape.phone.scaled(0.01)`.
- Prepared statements: `runtime.persistence.preparedStatementCountForTesting()` (`InstantWritePathEnergyTests/
  repeatedSavesReuseTheirPreparedStatements`: warm, write 10, assert the count did not move).

### Phone-shaped store and its meter (`RealSize/RealSizeFixture.swift`, `RealSize/RealSizeMeter.swift`, `RealSize/RealSizeBudgetTests.swift`)

- `RealSizeFixture.open(_ shape: RealSizeShape = .phone, label:) -> RealSizeSession`, then
  `try await session.closing { ... session.runtime ... }`. `RealSizeShape.phone` is one phone's counts (352
  recordings, 8,712 lines, 9,455 account files, 4,264 device file records, 663 refused writes, 48 open and 355 closed
  queries, 2,283 attributes); `.scaled(0.25)` and `.scaled(0.01)` for fast tests; fields such as `refusedWrites` can be
  set. Generated through the runtime and a scripted server with integer transaction ids (fixture version 3), cached by
  version and shape. `RealSizeFixtureSmokeTests/aTinyFixtureGeneratesOpensAndMeters` always runs and asserts the
  fixture's own sanity (no accepted write left waiting in the outbox).
- `RealSizeMeter.measure(_ operation:, label:, iterations:, warmup:, gateProbe:, gate:, counters:, prepare:) { index in ... }
  -> RealSizeMeasurement`: median wall time, CPU, instructions retired, logical bytes written, heap allocations and
  bytes (libmalloc's `malloc_logger` hook), net live and peak live bytes, footprint, and with `gate: session.gate` the
  operation gate's holds and waits in the window.
- `RealSizeBudgetTests/budgetsAtTheRealSize` ("No operation costs more on a store four times larger, and each stays under
  its ceiling at the phone's size"): adding a guard is adding a `RealSizeBudget.Rule(operation:ceiling:knownIssue:)`
  for an operation `RealSizeOperations` already meters. Scale rule: allocations and instructions at full size over a
  quarter size stay under 1.5x; ceiling: about 2x the measured allocations and 10x the median wall time. Known issues
  today: #1108 (transact, refused-write; intermittent), #1111 (observe first emission), #1104 (evictions, storage
  snapshot), #1106 (failed-write supersessions).
- One-thread allocation counts for synchronous work, immune to a parallel bundle:
  `RealSizeAllocations.start(onCurrentThreadOnly: true)` ... `RealSizeAllocations.stop().allocatedBytes` (wrapped as
  `RefreshCostTests.bytesAllocated(iterations:_:)`). Bounds measured in release go behind
  `guard RealSizeBudget.isOptimized else { return }`.

### Work counters (`InstantEnergyMeterTests.swift`)

- `InstantEnergyMeter.snapshot()` / `.subtracting(before)`: per-operation counts, thread CPU and wall time

  apply paths by name (`delta.serverApplyPaths["full rebase: reduction off"]`), transactions, outbox rows,
  supersessions, reconnect attempts. Count assertions ("a final line prepares once") are load-proof; CPU ones need

### The operation gate (`AsyncSerialGateTimelineTests.swift`, `InstantHydrationRecheckHolderTests.swift`, `RealSize/ContentionExercises.swift`)

  `gate.wait`, `gate.hold`, `gate.behind`, executor `probe` and per-caller `call` latencies on the phone-shaped store.
  Opt-in only.
